# v0.31.0

This release ties a session, its seal and its caller to a scope identifier. A session is of one
scope identifier on every storage kind, and the seal of a scoped session names it under the
signature, in a seal of version 2 (#477; ADR-0036). A caller is held to the scope identifiers its
token's `scope_ids` claim names and the configuration grants its subject, at engine configuration
version 27; the check is the default (#481; ADR-0037). The MCP server serves platforms fixed to a
scope identifier, the scope taken from its configuration or from the caller's token, at engine
configuration version 28 (#482; ADR-0038). Receipts keep their form; the seal of a session of no
scope, and every store an earlier gateway wrote, keep their bytes and verify as before. The DCO
check no longer misses a sign-off on a broken pipe (#484). The release review's fixes are in the
pull request for #485: among them, an action's citations are resolved within the caller's reach.
The release tag is also the milestone; #386 and #476, closed in it, were done in v0.30.0 (#471,
#473). The implementation rows are
[#477](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/477),
[#481](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/481),
[#482](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/482),
[#484](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/484) and the pre-release batch
for [#485](https://github.com/Judgment-Pack/judgment-pack-gateway/issues/485).

## Compatibility

| With | What holds |
|---|---|
| An engine configuration | Versions 27 and 28 are added: `identity.callerScopes` (item 1) and `mcp`'s `scope` and `scopeFrom` (item 3). A configuration that loaded under v0.30.0 loads as before, but where it has `identity` its callers are now held to scope identifiers by default (items 1 and 2). From version 27 a platform whose `scope` is `"unscoped"` is refused. A v0.30.0 gateway refuses a version-27 or version-28 file by its number. |
| A PostgreSQL store of v0.30.0 (schema version 6) | Is served as it is: no migration. But once this release writes a seal of version 2, no gateway of v0.30.0 or earlier may run on the store (item 4). |
| The format | Receipt versions 2 and 3 and the witness statement are unchanged. A session of a scope identifier is sealed by a seal of version 2 (`sealVersion` `"2"`, `scope`, signed under `judgment-pack-gateway/seal-version/2:`), and its seal after an interruption carries the same two members beside §3c's eight, under `judgment-pack-gateway/seal-after-interruption/2:`. The seal names the scope by a digest in the session, never by the identifier. A session of no scope is sealed in the earlier forms, byte for byte. One finding is added, `seal-scope-mismatch`: an accepted receipt whose `scope` is not its seal's. SPEC.md §3, §3c and §6 changed (§6 adds "Caller scope identifiers" and "The MCP server on scoped platforms"). |
| The corpus | Thirteen store vectors `v3-seal-scope-*` are added, signed by an independent signer that shares no code with the gateway. |
| The Go verifier and verify-ts of v0.30.0 | Read a store with no session of a scope identifier as this release's verifiers do. They read a seal of version 2 as nothing: a session it seals is `unregistered-session`, and a session so sealed and then deleted whole, with no removal record, is not reported at all, where this release reports it `sealed-session-missing`. Readers of a store with scoped sessions need this release's verifiers. verify-ts changed. |
| Receipts and stores written before this release | Keep their bytes and verify as before: a store v0.30.0 wrote verifies to v0.30.0's report, byte for byte. A session an earlier gateway left open over receipts of one scope identifier is sealed after an interruption with a seal of version 2. |
| Judgment Pack Runner and other `/acquire` clients | Under `identity` with caller scopes checked (the default), a token its subject's entry does not grant is refused `401` on every token route, in one of two sentences the Runner gives byte for byte (item 2). A request for a scope identifier the caller does not reach gets the wrong-scope `400`; an acquisition into a session of another scope, or of none into a scoped one, is refused `400` before the source runs (item 5). The filesystem kind and the PostgreSQL kind answer alike. |
| MCP clients | A server without `scope` or `scopeFrom` serves as before, except that under checked caller scopes its HTTP transport refuses `401` a token the signer would refuse (item 3). |
| The runtime in the engine image | Unchanged: the `Dockerfile` pins `0.46.0`, as in v0.30.0. |
| PostgreSQL | 16 is the version tested: CI runs PostgreSQL 16.15 pinned by digest. |

## Changes for operators upgrading from v0.30.0

1. **Write `identity.callerScopes` before the upgrade, where `identity` serves scoped sources**
   (#481; ADR-0037; engine configuration version 27). The steps are in
   [`docs/design/engine-config.md`, "Caller scope identifiers (engine version 27)"](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/v0.31.0/docs/design/engine-config.md#caller-scope-identifiers-engine-version-27).
   - The check is the default, at every version. Without `identity.callerScopes`, every subject
     is `"unscoped"`: it reaches the sources of no scope identifier alone, so **a source fixed to
     a scope identifier serves nobody** until the entries are written, at `engineVersion` `"27"`,
     or `"callerScopes": "unchecked"` is, which keeps the behavior before.
   - An entry is `"unscoped"`, `"installation"` (every source, for an installation's own caller
     such as a Runner), or a list of 1 to 256 scope identifiers that may hold the marker
     `"unscoped"`. A subject with no entry is `"unscoped"`. The token names what it is for in
     `scope_ids`, the claim the Runner reads; a claim wider than its entry is refused, never
     narrowed.
   - The start and `/posture` (`caller-scope-identifiers`) say which rule holds.
2. **A token its entry does not grant is refused `401`, even with no scoped platform.** Under
   `identity`, with caller scopes checked, a token whose `scope_ids` its subject's entry does not
   grant, or a claimless token whose entry is a list without `"unscoped"`, is refused `401` on
   every route that takes a token, and over the MCP server's HTTP transport, whether or not any
   platform is fixed to a scope identifier. This is the case where the issuer is shared with the
   Runner and a caller's tokens gain `scope_ids` for it: before upgrading, write an entry for each
   such subject granting what its tokens name (`"installation"` for a Runner), have the issuer
   leave the claim out of this gateway's tokens, or write `"unchecked"`. The two sentences are
   `the token's scope_ids names a scope identifier the configuration does not grant its subject`
   and `the token's scope_ids is not 1 to 256 scope identifiers, each once`; neither names a
   scope identifier or the subject.
3. **The MCP server on scoped platforms** (#482; ADR-0038, proposed; engine configuration
   version 28). It was refused before. To serve a scoped platform over MCP, raise `engineVersion`
   to `"28"` and write one of:
   - `mcp.scope`, a scope identifier: the server serves the live tools of the platforms fixed to
     it alone, and every forward names it; over `--http` and `--stdio`;
   - `mcp.scopeFrom: "caller"`: the server serves every platform, each forward naming its tool's
     platform's scope identifier. It needs `identity` with caller scopes checked, and `--http`:
     over `--stdio` the start is refused.

   In both, a caller is listed, and may call, only the tools of the sources its token reaches;
   any other is answered `unknown tool`, and nothing is forwarded. No tool's input names a scope
   identifier. No write tool is served.
4. **Seals of version 2: no going back, and no older instance beside this one** (#477; #485).
   - From the first seal of version 2, there is no rollback to v0.30.0 or earlier. A gateway of
     v0.30.0 or earlier reads no seal of version 2 and finds the session open: its
     `gateway seal-open`, or its start with `sealOpenAtStart`, seals the session again in the
     earlier form, and this release then reports the session `seal-conflict`, for good. Nothing
     refuses the older gateway on the store: the schema is the same.
   - So stop every v0.30.0 instance, and wait for each to exit, before the first v0.31.0
     instance serves; where instances serve one database beside one another, do not start a
     v0.30.0 one again once a v0.31.0 one has served, even after its lease expired; and never run
     an older `gateway seal-open` against the store.
     [`docs/postgresql-store.md`, "Several instances on one database"](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/v0.31.0/docs/postgresql-store.md#several-instances-on-one-database)
     and the engine configuration reference say so.
   - Verifiers of v0.30.0 or earlier report a v2-sealed session `unregistered-session`, and do
     not notice one deleted whole without a removal record. Give the store's readers this release's verifiers.
5. **The routes, under checked caller scopes** (#477, #481, #485).
   - `/acquire`: a scope identifier the caller does not reach is answered with the wrong-scope
     sentence, before the trail, the policy, the grant, the admission or the source; so is a
     source no platform gives, to a caller that does not reach every source. A session is of the
     scope of its first acquisition: one of another scope, or of none into a scoped session, is
     refused `400`, with one sentence that names neither scope.
   - `/seal` answers a session of a scope the caller does not reach `no such session`, as for a
     session the gateway does not hold.
   - `/verify` is refused `403` unless the caller reaches every source; where no source is fixed
     to a scope identifier and the store holds no session of one, a caller that reaches the
     sources of none is served too.
   - `/act` is refused `403`, `refusedAt: "scope-identifier"`, before its body is read, unless
     the caller reaches the sources of none: a write source and an action receipt are of no scope
     identifier. An action into a scoped session is refused at its session step.
   - `/registry` and `/publickey` stay open and whole. A seal of version 2 names its scope by a
     digest over the scope identifier and the session's id, which is not keyed: anyone who reads
     `/registry` and guesses a scope identifier can test it, and learn which sealed sessions are
     of it, with their final counts and seal times. **Choose scope identifiers with at least 128
     bits of entropy** (22 or more characters drawn at random from a 64-character alphabet, say),
     and keep the names people read outside the identifier.
6. **Fixed from the release review** (#485).
   - An action's citations are resolved within the caller's reach. A caller that reaches the
     sources of none, but not every source, had each citation resolved against any session in the
     store: it could tell another scope's sessions from absent ones, with their receipt counts;
     cite another scope's last receipt by the `headSignature` that `/registry` lists for a seal of
     version 2, and have an unscoped action recorded; and so make `gateway store remove-scope` for
     that scope identifier refuse as a whole. A cited session of a scope the caller does not reach
     is now answered `no such session` before its receipts are counted or a signature compared,
     and so is a cited receipt of such a scope. The filesystem kind; on the PostgreSQL kind `/act`
     is refused before its body is read.
   - With caller scopes checked, `/posture`'s `programs` names only the sources the caller
     reaches, as `/acquire` does not tell another scope's sources from unknown ones. The
     installation's caller, `"unchecked"` and a gateway without `identity` read every source; the
     protection lines are judged over every source, whoever asks.
   - The one-way upgrade (item 4) is now written in the PostgreSQL store guide and the engine
     configuration reference.

## Decisions

- ADR-0036: a session is of one scope identifier on every storage kind, and the seal of a scoped
  session names it by a digest under the signature; `gateway verify` and `gateway export` stay
  whole-store, since a cut by scope cannot be shown whole against seals that name none. Accepted
  under the maintainer's standing delegation; the maintainer may revise it.
- ADR-0037: a caller is held to the scope identifiers its token and the configuration both
  allow, by default. Accepted the same way. Its `/act` paragraph now says that an action's
  citations are resolved within the caller's reach (#485).
- ADR-0038: the MCP server on platforms fixed to a scope identifier, in two forms. Proposed; it
  supersedes decision 4 of ADR-0026 in part (the refusal of `scope` beside `mcp` holds only
  beside an `mcp` of neither form).

## What this release does not establish

- A verdict, or an export, of one scope identifier: `gateway verify` and `gateway export` read
  the whole store and the whole registry (#478).
- The digest by which a seal of version 2 names its scope is not a secret: a guessed scope
  identifier can be tested against `/registry` (item 5).
- A verifier of v0.30.0 or earlier does not read seals of version 2, and nothing stops an older
  gateway from running on a store this release has sealed (item 4).
- A seal of the earlier forms, every seal an earlier gateway wrote among them, names no scope, so
  of such a session only its receipts say which scope identifiers it holds.
- The MCP server in the caller form bounds its listing over every scope's platforms, and a front
  fixed to one scope forwards `engine.seal` for a session of another scope the caller's token
  reaches; both are open (#483).
- With caller scopes checked, `/posture`'s protection lines are judged over every source, and a
  line that names the sources it judges (one that runs as the signer's own user, say) names them
  to any authenticated caller; only `programs` is cut to the caller's reach.
- Instances on separate hosts, a router in front of the instances, and throughput under the
  registry's append lock are still not tested; a call to an instance other than its session's
  holder is refused, not forwarded.
- Open review items on the PostgreSQL kind remain in #440, #444 and #447, and the waiting
  start's fixed `503` body in #474.
- Whether the launcher should keep a mount-namespace boundary without a fresh `/proc` is still
  open (#450).
