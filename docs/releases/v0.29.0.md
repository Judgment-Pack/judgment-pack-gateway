# v0.29.0

This release removes one scope identifier's records from a store (#434). `gateway remove-scope`
does it on the filesystem kind and `gateway store remove-scope` on the PostgreSQL kind. Each signs
a record of what it removed, and the verifiers read those records: a removed sealed session is
observed `session-removed` and is no finding (#460, #462). The PostgreSQL kind's start now holds
every column, constraint and index of the schema to a list the binary carries, and the schema
holds the registry to one chain (#459). Three review findings on the kind were fixed (#454). The
storage scenario holds the PostgreSQL kind's export to the filesystem kind's, through the binary
(#455). `/acquire` answers an http source's expired reference as `410 source_reference_expired`
(#463). verify-ts lists sessions and receipt files in the order of their names (#458), and a
failing verify-ts test is named in CI's summary (#457). A pre-release batch fixed the release
review's findings. The release tag is also the milestone. The implementation rows are
[#454](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/454),
[#455](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/455),

## Compatibility

| With | What holds |
|---|---|
| An engine configuration | No engine configuration version is added. A configuration that loaded under v0.28.0 loads as before; one with `storage` starts once its store is migrated (next row). |
| A PostgreSQL store of v0.28.0 (schema version 3) | Is refused by this release's start until `gateway store migrate` raises it to schema version 5 (item 1). The migration is one-way: a v0.28.0 binary refuses a schema-5 store as newer than its own. |
| The format | Receipt versions 2 and 3, the seal and the witness statement are unchanged, and no receipt member is added. SPEC.md §1.3a adds two removal records, `session-removal` and `scope-removal`, in the store's removal file; §4 step 4 adds the observation `session-removed`. SPEC.md §1.3, §1.3a, §4 (step 4 and the observations), §4.1, §5, §5a.1, §6 and §7 changed. |
| The corpus | Fourteen `v3-session-removed*` store vectors are added, signed by hand by a signer that shares no code with the gateway. Frozen vectors are unchanged. |
| A verifier of v0.28.0 or earlier (Go, TypeScript, or any downstream reader) | Loads no `session-removal` record, and reports a removed sealed session as `sealed-session-missing`, which fails the store-wide verdict. Upgrade every verifier before removing anything (item 4). |
| verify-ts | Lists sessions, and each session's receipt files, in the byte order of their names, as the Go verifier does. The order of its findings can differ from v0.28.0's; the verdict does not (#458). |
| Receipts and stores written before this release | Keep their bytes and verify as before. |
| Judgment Pack Runner and other `/acquire` clients | `/acquire` gains one answer: `410` with `{"code":"source_reference_expired","error":…}`, where v0.28.0 answered `400` (item 5). |
| The runtime in the engine image | Unchanged: the `Dockerfile` pins `0.46.0`, as in v0.28.0. |
| PostgreSQL | 16 is the version tested: CI runs PostgreSQL 16.15 pinned by digest. |

## Changes for operators upgrading from v0.28.0

1. **The PostgreSQL kind: migrate before the first start.** In this order:
   - stop every instance and wait for each to exit;
   - back the database up;
   - run `gateway store migrate` as the migration login. It applies migrations 4 and 5 in one
     transaction: `{"applied":[4,5],…,"schemaVersion":5}`. Migration 4 rewrites
     `gateway.log_records` under a lock no reader or writer passes, and refuses a log that is
     not one chain, with nothing changed (`docs/postgresql-store.md` gives two queries that name
     where it breaks);
   - start the new binary.

   The migration is one-way. A v0.28.0 binary refuses a schema-5 store, and a v0.29.0 binary
   refuses a store below 5. Before it commits, the migration compares the schema's definitions
   as the start does (item 2), and rolls back on a mismatch, so the store stays at the version
   it was. A deployment on the filesystem kind runs no migration.
2. **The PostgreSQL kind's start holds more of the schema** (#459).
   - It reads every column (type, collation, NOT NULL, default or generation), constraint and
     index of the store's tables as the server prints it, and refuses a database where one
     differs from the list the binary carries, is missing, or has one beside it. The refusal
     names the table, the kind and the name.
   - It refuses an unlogged table, a table inheriting from one of the store's or inherited by
     one, and an index that is not valid.
   - Schema version 4 holds the registry's records to one chain from offset 0 (a unique end
     offset and a foreign key from each record's start to another's end), whoever writes them.
   - The list was read from PostgreSQL 16 and is tested there alone. A server that prints a
     definition otherwise has its start refused, and its migration rolled back.
3. **The PostgreSQL kind's connection and server** (#454).
   - A password of only spaces is refused, with the sentence a missing password gets.
   - The server's version is read by query on each connection, and a server whose queried
     version disagrees with the `server_version` it reported at the login is refused, naming
     both. The PostgreSQL 17 checks use the queried version.
   - `gateway export --config` holds the connection file as `serve` and `gateway store migrate`
     do, links in its path included, and reads the resolved path.
4. **Removing one scope identifier's records** (#462; ADR-0034).
   - The filesystem kind: `gateway remove-scope --store <dir> --seed <file> --registry <file>
     --authority <authority> --scope <identifier> --by <label>`, with the gateway stopped (it
     takes the registry's lock). It removes each session all of whose receipts carry the scope
     identifier, and each payload only those receipts name. It appends a signed
     `session-removal` record for each sealed session and one `scope-removal` record for the
     call, then removes the files, and prints the records. A session of mixed scopes, a receipt
     left that cites one it would remove, a linked `artifacts/`, `receipts/` or session
     directory, and a session holding anything but receipt files refuse the whole call by
     name, before anything is written. A run cut off is completed by running it again.
   - The PostgreSQL kind: `gateway store remove-scope (--connection-file <path> |
     --connection-env <NAME>) --owner <role> --runtime <role> --seed <file> --scope
     <identifier> --by <label> [--timeout <seconds>]`, as the migration login acting as the
     owner, under the migration's advisory lock and the start lease (refused while an instance
     serves). The scope's rows, its row of `gateway.scope_identifiers` and the records, rows of
     `gateway.removal_records` (schema version 5), commit together or not at all.
   - The run-time role gets SELECT alone on `gateway.removal_records`, and its privileges are
     otherwise unchanged: no DELETE on any table but `gateway.documents`.
   - Both verifiers of this release, Go and verify-ts, read the records: a removed sealed session
     that a record names is observed `session-removed`, `{sessionId, observation}`, and is no
     finding. **A verifier from v0.28.0
     or earlier (Go, TypeScript, or any downstream reader) reports a removed session as
     `sealed-session-missing`.** Upgrade every verifier that reads the store or its exports
     before removing anything.
   - Do not export during a removal. On the PostgreSQL kind an export that a removal overlaps
     stops with exit status 1, before its manifest, and is run again once the removal is done.
     On the filesystem kind the export does not take the registry's lock, so nothing stops it:
     an export cut across a removal can hold a removed session's receipts without their
     payloads, which verifies as damage. Export before or after the removal.
   - What a removal leaves, on each kind, is stated in README.md, "What a removal of a scope
     identifier leaves": among it the seals in the registry, the records, decision records
     outside the store, and copies made before the call.
5. **An http source's expired reference** (#463; closes #461).
   - Where an http source's endpoint answers 410, `/acquire` answers `410` with
     `{"code":"source_reference_expired","error":"source failed: the source's endpoint answered
     410 Gone: the reference the request sent has expired; nothing was retained or minted"}`.
     v0.28.0 answered `400` with the adapter's text. A client that accepts only an `error`
     member must accept `code` beside it.
   - The endpoint's text no longer appears in the answer; the source's check still shows it.
     Nothing is minted, no call index is taken, and no receipt is written.
   - `adapter-http` exits with the new status 8 for it. With an adapter and a gateway of
     different versions the answer stays the old `400`.
   - A token endpoint's 410 is unchanged: a refused token request, `400`.
   - A 410 on a read that started from the first value means stop, not read again.
6. **verify-ts output order** (#458). Sessions and receipt files are listed in name order, so a
   report's findings can come in another order than v0.28.0's.

## Decisions

- ADR-0034: removing one scope identifier's records, by a signed `session-removal` record per
  sealed session and a `scope-removal` record per call, made with the gateway stopped, and on
  the PostgreSQL kind by the migration login as the owner. Its option 1 was amended on
  2026-11-15 (the run-time role holds SELECT alone on the records' table, and an identifier
  with no rows gets no record); the amendment awaits the maintainer's confirmation.
- ADR-0029 gains one sentence for the expired reference (#463).

## What this release does not establish

- The definitions the start and the migration compare are tested on PostgreSQL 16 alone. A
  server of another major version that prints one definition otherwise is refused at the start
  and rolls its migration back; the list would then need that version's text.
- On the filesystem kind, nothing keeps an export and `gateway remove-scope` apart (item 4).
- A removal does not reach what lies outside the store, or copies made before it, or, on the
  PostgreSQL kind, the removed rows' bytes in the database's files until vacuum reuses their
  space, its write-ahead log and base backups.
- Sessions, seals and registry lines carry no scope identifier (#442).
- Open review items on the PostgreSQL kind remain in #440, #444 and #447: among them the
  run-time login writing a start lease whose renewal time is in the future, `serve --config`
  not run through the binary in CI, and rows written outside the gateway under a scope never
  recorded, which the export does not reach.
- Whether the launcher should keep a mount-namespace boundary without a fresh `/proc` is still
  open (#450).
