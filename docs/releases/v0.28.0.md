# v0.28.0

This release publishes the engine image, with the source sandbox's launcher in it (#436, #449;
closes #378, #385, #437). An engine configuration of version 23 can make the start measure each
source's sandbox and refuse to start where a launch would be refused. It adds a second storage
kind, PostgreSQL, behind the store contract (#439). An engine configuration of version 24 selects
it, `gateway store migrate` makes its schema, and one instance serves a database at a time, held
by a start lease (#443). A platform fixed to a scope identifier is served on that kind, each
scope's rows held apart in the database by row-level security, enabled and forced (#445). A
pre-release batch fixed review findings on the kind (#448; closes #446). The filesystem kind stays
the default and is unchanged. The release tag is also the milestone. The implementation rows are
[#436](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/436),
[#439](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/439),
[#443](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/443),
[#445](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/445),
[#448](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/448),
[#449](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/449) and
[#451](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/451), which moves the runtime
the image carries to `0.46.0`.

## Compatibility

| With | What holds |
|---|---|
| An engine configuration of version 22 or earlier | Loads and behaves as before. `connect` raises no file to 23 or 24: edit `engineVersion` by hand. |
| A gateway of v0.27.0 or earlier | Refuses a configuration of version 23 or 24 by its version. |
| The format | SPEC.md and the corpus are unchanged. Receipt versions 2 and 3, the seal and the witness statement are as v0.27.0 stated them, and no receipt member is added. |
| Receipts and stores written before this release | Keep their bytes and verify as before. Nothing moves a store from one kind to the other. |
| A verifier, Go or verify-ts | Reads an export of the PostgreSQL kind as it reads a filesystem store: the export is the layout of SPEC.md §1.3, byte for byte what the filesystem kind writes for the same work (a test, for one scenario and for every corpus store). A verifier never reads the database. |
| Judgment Pack Runner | No route, request or answer changes on the filesystem kind. On the PostgreSQL kind a session's receipts are of one scope: an acquisition into a session that holds another scope's receipts, or receipts of no scope, is refused `400` (item 4). |

That release reads Core `0.1.0-draft`, `0.2.0-draft`, `0.3.0` and `0.5.0`; a Core `0.5.0` pack from the runtime's own evaluation suite was evaluated in the image and reached the disposition that suite expects. |
| PostgreSQL | 16 is the version tested: CI runs PostgreSQL 16.15 pinned by digest. The kind refuses a server older than 16. |
| Posture consumers | No posture line is added or changed for a configuration without `storage`. What posture says of a configuration with `storage` was not reviewed (#444). |

## Changes for operators upgrading from v0.27.0

1. **A deployment that stays on the filesystem kind changes nothing.** A configuration without
   `storage` loads, starts, writes and answers as before. Its store, registry, receipts and
   posture keep their bytes. The one visible difference is the usage line of `gateway` with no
   command, which now names `store`.
2. engineVersion 23 adds `measureSandboxAtStart` (#436), refused by name under 22 and below. It
   is `true` or `false`; without it nothing is probed at the start.
   - With it on, the start probes each source's sandbox as the source's user, one source at a
     time, each probe under a launch's own bound, before anything is made.
   - The engine does not start, and exits 1, where a probe gives no report or measures a
     restricted mode as `not-enforced`. The error names every such source with the probe's
     reason. A source whose policy selects `danger-full-access` is not refused.
   - `partial` starts. The start prints one line, `start: measureSandboxAtStart: measured`
     followed by each source's mode, backend and state.
   - Each launch after the start is bound to the posture the start measured.
3. engineVersion 24 adds `storage` (#443), refused by name under 23 and below. It names the
   PostgreSQL kind in place of `store` and `registry`, which are then refused by name.
   - Members: `kind` (`postgresql`, nothing else); `connection`, exactly one of `file` (an
     absolute path, held as the seed's file is, at most 4096 bytes) or `environment` (a
     variable's name, which the start reads and then removes from its own environment);
     `connections`, 1 to 64, 4 without it; `operationSeconds`, 1 to 600, 30 without it.
   - The connection string is never in the configuration and never printed. The start says only
     which reference it was read from.
   - An instance holds `connections` + 1 connections: one more for its start lease.
   - `gateway mcp` under such a configuration is denied the connection file, and refuses to start
     when its environment holds the connection variable.
   - A platform's `scope` is taken with `storage` (#445).
4. On the PostgreSQL kind a session's receipts are of one scope (#445). An acquisition into a
   session that holds the receipts of another scope, or of none, is refused `400` before its
   source runs: `session <id> holds the receipts of a scope other than this source's (another
   scope identifier, or none): with the PostgreSQL storage kind a session's receipts are of one
   scope, so acquire into a new session`. The refusal names neither scope. The filesystem kind
   takes such an acquisition, as before.
5. New command: `gateway store migrate (--connection-file <path> | --connection-env <NAME>)
   --owner <role> --runtime <role> [--timeout <seconds>]` (#443).
   - It takes the migration login's connection string, by one reference, and creates or raises
     the schema. It is the only way the schema changes: the start checks the schema and changes
     nothing.
   - It refuses the run-time login, and any login that is the owner or the run-time role, before
     anything is applied. It refuses a schema newer than the binary and a migration changed since
     it was applied. A second run applies nothing.
   - It prints canonical JSON: `{"applied":[1,2,3],"migrations":"sha256:…","schemaVersion":3}`.
     `--timeout` is 1 to 3600 seconds, 300 without it. Exit 0 on success, 1 on a refusal or
     failure, 2 on a usage error.
   - This release's schema is version 3. Run the command before the first start. The start
     changes no schema: it refuses a database whose schema is older or newer than its own.
6. The PostgreSQL kind's start and `gateway store migrate` both refuse (#439, #443, #448):
   - a connection string without a password, or with an empty one, with one fixed sentence that
     quotes no part of it;
   - an `sslmode` other than `verify-full` (the default) or `disable`, and `disable` unless the
     host is a loopback address or `localhost` and the address reached is loopback; any parameter
     other than `sslmode`, `sslrootcert` and `connect_timeout`;
   - a server that asks for a password in the clear or by MD5, or admits the login without the
     SCRAM-SHA-256 exchange;
   - a server older than PostgreSQL 16, and a database whose encoding is not UTF-8;
   - roles outside the conditions `docs/postgresql-store.md` lists.

   The start also refuses a database whose privileges, tables, policies or row security differ
   from what the page lists. On PostgreSQL 17 and later that includes a run-time login holding
   `MAINTAIN`, and the start also checks the `transaction_timeout` bound.
7. One instance per database (#443). A start takes the start lease before it writes anything.
   - A second start is refused, exit 1, with `start-lease-held`, while another instance's lease
     is live. An instance that loses its lease stops serving and exits 1 with
     `start-lease-lost`. Every write is fenced by the lease.
   - The lease runs 30 seconds from each renewal by the database's clock and is renewed every 10
     seconds. A clean stop (SIGINT or SIGTERM) releases it. After an unclean stop a new start is
     refused until the old lease has expired and its sessions are ended, within 45 seconds of the
     old instance's last renewal; start it again then.
   - Replace an instance in this order: stop the old one and wait for it to exit; run
     `gateway store migrate` if the new version carries a migration; start the new one.
8. The release publishes the engine image (#436, #449): "The engine image", below.

## The engine image

The image is pushed to `ghcr.io/judgment-pack/judgment-pack-gateway` under the version without its
`v`, `0.28.0`, for `linux/amd64` and `linux/arm64`, past the `production` gate. No `latest` is
pushed. The version's tag is a name the registry can move: pin the digest. The "Engine image"
section the release workflow writes below these notes gives the tag and the digest. The digest is
the SHA-256 of the asset `judgment-pack-gateway_0.28.0_engine-image.index.json`, which
`checksums.txt` names and the release attests.

The image carries the gateway, the adapters, the runtime (`jpack`, the release Compatibility
names), the catalog and the corpus. It carries bubblewrap 0.13.1, the source sandbox's launcher,
built statically from its release source at `/usr/bin/bwrap`, with a static `/bin/true` for its
start check; both are root's, with no set-user-id bit and no capability. It carries no
seed, store, registry or configuration: they are on volumes the operator mounts.
`docs/engine-quickstart.md` takes the image to a running engine. Run it with an init
(`docker run --init`).

What the sandbox needs of the container, as measured:

- Docker's default seccomp profile refuses the source's user a user namespace, and on some Docker
  versions refuses Landlock's calls too. With neither backend, posture reports the source
  `not-enforced`, each restricted launch refuses, and with `measureSandboxAtStart` on the engine
  does not start.
- `bubblewrap enforced` needs `--security-opt seccomp=unconfined`, or a profile of the operator's
  own that lets the source's user make a user namespace (not tested), and
  `--security-opt systempaths=unconfined`: bubblewrap mounts a fresh `/proc`, which the kernel
  refuses in a container whose `/proc` has masked or read-only paths. On a host whose Docker lists
  AppArmor, also `--security-opt apparmor=unconfined`. All three were needed on CI's runner.
- `systempaths=unconfined` lifts Docker's masks and read-only mounts over some `/proc` and `/sys`
  entries for the whole container. The quickstart lists what that gives up.
- Without the system paths unconfined, where the kernel refuses the mount, the engine starts with
  the Landlock posture, `partial`. File-content writes, truncation and directory changes are
  restricted; metadata changes such as `chmod`, and connections to local sockets, are not.
- CI starts the image under `seccomp=unconfined` and `systempaths=unconfined`, with the
  container's profile relaxed where its runner lists one, and fails unless posture and the start
  say `workspace-write bubblewrap enforced`.

Whether the launcher should keep a mount-namespace boundary without a fresh `/proc` instead of
falling back is the open question #450.

## The PostgreSQL storage kind (#439, #443, #445, #448)

A client of the standard library alone: protocol 3.0, SCRAM-SHA-256 only, TLS `verify-full` or,
to loopback, none. The schema is plain SQL the binary carries, applied by a migration login that
reaches a NOLOGIN owner only by `SET ROLE`. The run-time login holds table privileges alone and
is append-only but for documents and the start lease. The kind passes the same store conformance
suite and the 184 corpus store exports as the filesystem kind. `docs/postgresql-store.md` is the
operator page: the roles to make, the grants, the connection string, TLS, the lease and backup.

**Scope identifiers.** Each scoped table has row security enabled and forced, the owner included,
with one policy: `scope = current_setting('gateway.scope', true)`. Every transaction sets the
scope for itself alone, so a pooled connection carries none from one transaction to the next, and
a transaction that sets none sees no row. Schema version 3 records each scope identifier a start
opens a view for. The export reads every recorded scope, one at a time. ADR-0033.

## Decisions

- ADR-0030: the engine image carries a static bubblewrap; the release publishes the image by
  digest past its gate; engine configuration version 23 adds `measureSandboxAtStart`.
- ADR-0031: a second storage kind on PostgreSQL, behind the store contract.
- ADR-0032: engine configuration version 24 names the storage kind; `gateway store migrate`; one
  instance per database by a start lease.
- ADR-0033: a platform fixed to a scope identifier on the PostgreSQL kind, each scope's rows kept
  apart by the database.

## What this release does not establish

### The PostgreSQL storage kind

- **Not available with this kind yet**, each refused with `storage-kind-unsupported` and never
  answered from an empty directory:
  - `witness`, refused at the configuration's load;
  - `sealOpenAtStart`, refused at the load;
  - a platform's `write: true`, refused at the load, and `/act`, which answers `501`;
  - a platform's `descriptorStatements`, descriptor provenance, and a descriptor capture by
    `gateway connect` (`--no-descriptors` connects a platform without one);
  - `/verify`, which answers `501`: export the store with `gateway export --config` and verify
    the export;
  - `gateway seal-open --config` and `gateway remove-artifact --config`;
  - key rotation: `gateway rotate-key` takes a registry file, and the start refuses a rotation
    under way beside the seed.
- One instance serves a database at a time. The lease decides which; several instances on one
  database are not supported. Moving a store from one kind to the other is not supported.
- CI tests PostgreSQL 16 only. The kind's tests were run once against PostgreSQL 17, outside CI
  (#448). No connection pooler was tested. A password outside printable ASCII may fail to log
  in.
- Row security keeps apart what the gateway does. It is not a boundary against the run-time login
  itself, which may set any scope in a transaction of its own. Keep its password to the gateway.
  It may also do what every role may in a database it connects to: create large objects, use
  `LISTEN` and `NOTIFY`, and hold a session advisory lock on the registry's key, which makes every
  append wait and fail at the lock timeout.
- The registry is one chain across scopes. A gateway of one scope reads the ids and receipt counts
  of every scope's sealed sessions. Sessions, seals and registry lines carry no scope (#442).
- A new session's admission looks for its name in every recorded scope, under the service's lock:
  2N + 5 statements for N identifiers recorded. On a test server on loopback the median was about
  100 ms with 100 identifiers and about 1 s with 1,000.
- Open review items (#440, #444, #447):
  - the run-time login can insert a registry record overlapping committed bytes without the lock;
    committed bytes are never returned altered, but the log can then no longer be read in full
    (#440, item 4);
  - the start does not check indexes, constraints or columns: a key or check the owner dropped is
    not found at the start (#440, item 5; #447);
  - a server whose reported version cannot be read is taken as older than 17, so on such a
    PostgreSQL 17 server the `MAINTAIN` and `transaction_timeout` checks are not made (#440,
    item 11);
  - `gateway export --config` holds the connection file's owner and mode but follows a link in
    its path, which the start and `gateway store migrate` refuse (#444, item 1);
  - the run-time login can write a start lease whose renewal time is in the future and so hold
    the lease up to ten minutes past it (#444);
  - `serve --config` has not been run through the binary on this kind in CI: CI serves in-process,
    and the binary migrates, exports, checks and verifies (#444, item 3);
  - rows written outside the gateway under a scope that was never recorded are not exported, and
    nothing reports them (#447).

### The engine image

- The `arm64` image is built, its index entry checked and its filesystem judged, but it is not
  run in CI.
- `bubblewrap enforced` was measured on CI's runner and on one other host. An SELinux label, a
  seccomp profile of the operator's own, and an orchestrator's setting for an unmasked `/proc`
  were not tested.
- The launcher's compiler and the two libraries it links are installed from the pinned base
  release's signed repository at build time, not pinned by content. A rebuild may link a newer
  package revision of the same versions. No software bill of materials is published.
- For a source run through a container helper, the start line prints the probe's state, while
  posture reports the same source `partial`. The probes at the start are bounded each, not in all
  (#438).
- The witness scenario was not run against the runtime the image carries, `0.46.0`; it keeps its own runtime pin.
