# v0.30.0

This release lets several gateway instances serve one PostgreSQL database, in the three steps
ADR-0035 records (#464). A start may wait for the instance it replaces, and a stop drains before
it releases the start lease, so a roll-out can start the new instance before it stops the old one
(#469). `gateway seal-open --config` and `sealOpenAtStart` seal, on the PostgreSQL kind, the
sessions a stopped instance left open (#470). With `storage.instances` `"several"`, instances
serve one database at once, each session held by the instance that admitted its first call
(#471); one instance per database stays the default. No verification step, record, finding or
vector changes: a store written by several instances reads like one written by one. CI checks
the merge queue's groups, and DCO runs as a workflow of the repository (#472). The release
review's fixes are in #473: among them, a seal now checks only the registry lines added since its
instance last read the registry. The release tag is also the milestone. The implementation rows
are [#464](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/464),
[#469](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/469),
[#470](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/470),
[#471](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/471),
[#472](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/472) and
[#473](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/473).

## Changes for operators upgrading from v0.29.0

1. **The PostgreSQL kind: migrate before the first start, with every instance stopped.** The
   steps, what migration 6 changes and how to go back are in
   [`docs/postgresql-store.md`, "Upgrading from v0.29.0"](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/v0.30.0/docs/postgresql-store.md#upgrading-from-v0290).
   In this order:
   - stop every instance and wait for each to exit. The orderly hand-over (item 2) does not carry
     this step: `gateway store migrate` is refused while any instance's lease is live, and a
     v0.30.0 instance refuses a schema-5 database;
   - back the database up;
   - run `gateway store migrate` as the migration login: `{"applied":[6],…,"schemaVersion":6}`;
   - start the v0.30.0 instances.

   Migration 6 is one-way. It makes the start lease one row per instance, and records from then
   on the instance that holds each session. A v0.29.0 binary refuses a schema-6 database, by its
   start and by its `gateway store migrate` alike; going back to v0.29.0 means restoring the
   backup. A deployment on the filesystem kind runs no migration.
2. **An orderly hand-over between instances** (#469; ADR-0035, step D; engine configuration
   version 25).
   - `storage.startWaitSeconds`, 1 to 3600, has a start that finds another instance's lease live
     wait for it, where it was refused at once. It binds its listener at once and answers every
     route `503`, with `Retry-After`, until it holds the lease; where the old instance on the same
     host holds the address, it waits without listening and binds once it holds the lease. It
     then makes the start's checks again. When the wait runs out it exits 1, `start-lease-held`.
     Within the wait it reads the lease again past a failure that is the database's for the
     moment: a connection reset or refused, a server shutting down, not yet up or at its
     connection limit, a serialization failure or a deadlock (#473).
   - **The stop drains, on the PostgreSQL kind.** SIGTERM or SIGINT closes admission (each
     acquisition is answered `503` with `Retry-After`, and SIGUSR2 does not reopen it), lets what
     was admitted finish within `storage.operationSeconds`, then releases the lease. v0.29.0
     cancelled sources in flight at once. A second signal ends the process at once, undrained.
     The filesystem kind's stop is unchanged.
   - Start the new instance, then stop the old one. A hand-over leaves open sessions open
     (item 3), compares no key or authority between the two, and does not carry a migration
     (item 1). `docs/postgresql-store.md`, "Handing over to a new instance", gives the procedure
     and the connection budget it needs.
3. **Sealing the sessions a stopped instance left open** (#470; ADR-0035, the third step).
   - `gateway seal-open --config <engine.json> (--session <id> | --all)` and
     `sealOpenAtStart: true` now work on the PostgreSQL kind, with the seal made after an
     interruption (SPEC.md §3c): `sealedVia` `"command"` or `"start"`, its count the receipts the
     store holds in the session. A verifier observes such a session `sealed-after-interruption`,
     or, with `--ordinary-seals-only`, finds it.
   - The command takes the start lease as a start does. While an instance of the one-instance
     mode serves, it is refused at once, `start-lease-held`, whatever `startWaitSeconds` says. The
     start seals once it holds the lease and has walked the registry, before it serves.
   - Where instances serve beside one another, both seal only a session whose holder's lease has
     expired, and pass over (`--all`) or refuse (a named session) one that a live instance holds.
   - On this kind the run-time login may only read and insert receipts and registry lines, so
     taking a receipt or a seal line away takes the owner role (SECURITY.md).
4. **Several instances on one database** (#471; ADR-0035, option C; engine configuration
   version 26).
   - Opt in on each instance: `engineVersion` `"26"` and `"instances": "several"` in `storage`.
     `"one"`, the default, keeps one instance per database. Each instance takes its own row of
     the start lease, and every write of it stays fenced on that row.
   - **Send each session to one instance.** The instance that admitted a session's first call
     holds it. Another instance answers a call into it, or its seal, `409` before the source
     runs, with one fixed sentence that names no instance; it does not forward the call. A router,
     or the caller, sends every call of a session and its seal to the instance that answered the
     first.
   - **One seed and one authority on every instance.** A start is refused, `instance-mismatch`,
     where a live instance signs under another key id or names another authority. The comparison
     is with live instances alone: once every instance has stopped, a changed key is still refused
     by the start's walk of the registry, but a changed authority is not, so keep one authority for
     the database's life (#473). Sources are not compared: give every instance the same ones.
   - **The two modes refuse each other** on one database, `start-lease-held`. Stop the instance
     of the one-instance mode before the first instance of the several-instances mode serves, and
     stop every instance of that mode before going back to one.
   - **An instance that stops or dies.** While its lease is live, other instances answer its
     sessions `409`. Once it has expired, a session that holds no receipt is taken up by the next
     instance a call reaches, and one that holds receipts is refused `400` until it is sealed
     (item 3). A stopping instance's `503` says that another instance serves the call sent again,
     unless the call's session holds receipts already (#473).
   - **The registry stays one chain.** A seal is judged against the registry in the append's own
     transaction, under its lock, so no session is sealed twice. Each instance keeps its walk of
     the registry from its start on, and a seal reads and walks only the lines appended since its
     instance last read the registry, after finding that instance's last line again in its place.
     A registry that is not the one the instance read (a restore, or commits lost to a failover)
     is read and walked whole again (#473). As first built, a seal walked the whole registry under
     the lock, and past about 70,000 seals every seal failed; no release carried that.
   - **Connections and delegated runs.** Budget `connections` + 1 for each instance on the
     server. A delegation's credential is bound, and revoked, at the instance that bound it: keep a
     delegated run's calls to that instance. Every instance still refuses a revoked delegation.
   - **Operations that need every instance stopped.** `gateway store migrate` and
     `gateway store remove-scope` hold every row of the start lease, and are refused while any
     instance's lease is live.
   - **The database host's clock** must not step backward: keep it synchronized and slewed, not
     stepped (#473; `docs/postgresql-store.md`, "Time").
5. **Two more fixes from the release review** (#473).
   - A claim of a session's series that no recorded scope identifier answers is refused as
     unreadable, where it was admitted.
   - A start that found no registry, and then finds a session in the store, reads the registry
     again before refusing, and goes on with the registry another instance made meanwhile.

## Decisions

- ADR-0035: several gateway instances on one PostgreSQL database, accepted on 2026-11-15 in the
  order D (an orderly hand-over), then a seal after an interruption for a stopped instance's
  sessions, then C (each session held by the instance that admitted it, beside one registry
  chain); questions 2 to 12 at their recommended answers. Its implementation notes record why a
  seal walks only what was appended since (over a keyed table of sealed sessions, which would be a
  second record of what is sealed), that key and authority are compared with live instances alone,
  and the start lease's assumption about the database's clock. The filesystem kind stays one
  instance per store and registry.
- ADR-0031, decision 10, points at ADR-0035.

## What this release does not establish

- Instances on separate hosts, a router in front of the instances, and throughput under the
  registry's append lock are not tested.
- A call that reaches an instance other than its session's holder is refused, not forwarded.
- An authority changed once every instance has stopped is not refused (item 4).
- The start lease assumes the database host's clock does not step backward. Were it to step back
  past an expired row's expiry, a paused instance could append receipts to a session sealed after
  the interruption; a verifier reports those receipts, and that instance's own seal is refused.
- A seal made after an interruption seals the count the store holds, not what the minting process
  wrote (SPEC.md §3c); `--ordinary-seals-only` finds such a session.
- `gateway rotate-key` is not available on the PostgreSQL kind.
- The filesystem kind stays one instance per store and registry.
- Sessions, seals and registry lines carry no scope identifier (#442).
- Open review items on the PostgreSQL kind remain in #440, #444 and #447.
- Whether the launcher should keep a mount-namespace boundary without a fresh `/proc` is still
  open (#450).
