# v0.37.0

This release builds ADR-0051: from engine configuration version 39 the session a caller names is a label in its scope, mapped to a session id the gateway mints. It also adds `gateway store rotate-key`, a stopped-gateway key rotation on the PostgreSQL kind. It takes one engine configuration version, 39, and one PostgreSQL migration, 9.

**On the PostgreSQL kind, run `gateway store migrate` before starting this release.** A database at schema version 8 is refused at start until it is migrated, whatever the configuration's version (item 1).

A configuration of version 38 or earlier reads the session a request names as its id, as before. Two things change for every configuration all the same:
- Every writer of a key rotation or a store continuation refuses a time before the key history's last rotation (item 6).
- `gateway store rotate-key` is new, and the PostgreSQL kind's refusals of a SIGHUP rotation and of an instance under another key name it (item 5).

- **Session labels** (engine version 39; #550, #565, #567; ADR-0051, accepted): `/acquire`, `/seal` and `/act` read `session` as a label in its scope's namespace. The receipt carries the minted `sessionId` (items 2 to 4).
- **`gateway store rotate-key`** (#563, #566; ADR-0050): moves a store on the PostgreSQL kind from the seed to a key service's key version, or from one key version to the next, every instance stopped (item 5).
- **Batch fixes** (this release's reviews): `/act` records a minted label only once it is admitted (a keyed read-back excepted), on the PostgreSQL kind a minted id is never one a label names already, and every key history writer holds its time to the history (item 6).

## Compatibility

| With | What holds |
|---|---|
| An engine configuration | A file of version 38 or earlier serves as before. Version 39 adds no member: it changes how `session` is read in `/acquire`, `/seal` and `/act` (item 2). |
| A PostgreSQL store of v0.36.0 (schema version 8) | **Refused at start until `gateway store migrate` applies migration 9.** Migration 9 adds `gateway.session_labels`, one row for each label, under the row security of every scoped table, and the column `labels` of `gateway.start_lease`. It is additive, and no existing row changes. The migration applies `grants.sql` as well: the run-time role gets SELECT and INSERT on `gateway.session_labels`, and nothing else on it. |
| A filesystem store of v0.36.0 | Is served as it is. At version 39 the store gains `labels/`, one file for each label. |
| The format | Receipts, seals and the registry are unchanged, and carry the session id as before. `labels/` is a store member a verifier passes over (SPEC.md §3a): a store holding it verifies exactly as the same store without it. |
| Older verifiers and the corpus | An older verifier reads a store of this release as before: it never read `labels/`. Every earlier vector stands. |
| Receipts and stores written before this release | Keep their bytes and verify as before. |
| Judgment Pack Runner and other `/acquire` clients | Unchanged below version 39. At version 39 a client reads the session id from the receipt and does not assume it is the label it sent (item 4). |
| The runtime in the engine image | Unchanged: the `Dockerfile` pins `0.46.0`. |
| PostgreSQL | 16 is the version tested, in CI's two `postgresql` legs. |

## Changes for operators upgrading from v0.36.0

1. **PostgreSQL: migrate first** (#567).
   - Stop every instance. Run `gateway store migrate` with the migration login (docs/postgresql-store.md), naming the run-time role, as at every migration. It applies `0009_session_labels.sql` and the grants in one transaction, and moves the schema to version 9. Then start.
   - Until then, a start refuses a database at schema version 8 by name (`apply the store's migrations`). So does every command that opens it.
   - An instance of v0.36.0 on a database at schema version 9 passes `gateway.session_labels` over.
   - The filesystem kind needs nothing.
2. **Session labels** (engine version 39; #550, #565, #567; ADR-0051, accepted; SPEC.md §3a and §6).
   - **What it adds.** At version 39 the `session` of `/acquire` is a label in the namespace of the source's scope identifier, the `session` of `/act` a label in the namespace of none, and the `session` of `/seal` a label in the namespace of the `scope` it names, or of none where it names none. On a label's first use in its namespace the gateway mints a session id of 32 lowercase hexadecimal characters from 128 random bits, and records the mapping in the store before the session's first receipt. One label in two scopes is two sessions, and what a caller of one scope is answered never depends on whether another scope uses the label.
   - **Where the labels are kept.** On the filesystem kind, `labels/<hex>.json` in the store. On the PostgreSQL kind, a row of `gateway.session_labels`, written `ON CONFLICT DO NOTHING`, so every instance on one database agrees on one id for a label.
   - **`/seal`.** A label the named namespace does not hold, or a namespace the caller does not reach, is answered `400` `no such session: <label>`, with nothing else read. In the caller form, the MCP seal tool takes an optional `scope`, held to the token's reach.
   - **A label names one session for its life.** A label whose session is sealed is refused as that sealed session is. A job that runs again after a seal uses a new label.
   - **`gateway sessions --config <engine.json> (--scope <identifier> | --no-scope) [--label <label>]`** prints a `label sessionId` line for each label of one namespace, in label order, or the one label's line. It reads the store with the gateway running or stopped, and writes nothing. `--scope none` names the scope identifier `none`.
   - **Removal.** `remove-scope` and `store remove-scope` remove the scope's labels, also where the scope holds labels and no session. `retain` and `store retain` remove the label of each session they remove. Labels go once the removal's records are durable and before the receipts, so a removal cut off never leaves a label naming a session it removed.
   - **What is not carried.** `gateway export` carries no labels, and `gateway store rotate` starts the new store with none.
   - **What to do.** Nothing, unless you move to version 39. To move, follow item 3.
3. **Moving to version 39, and back.**
   - **The upgrade.**
     1. Stop every instance.
     2. Seal every session: `gateway seal-open --config <engine.json> --all`.
     3. On the PostgreSQL kind, run `gateway store migrate` (item 1).
     4. Raise `engineVersion` to `"39"` in every instance's configuration, and start them all.
   - **Why every session is sealed first.** A session open from before version 39 was named by its caller, and no label names it. A start at version 39 refuses while the store holds such a session, names up to five of them, and says to run `gateway seal-open --all`. A session a version-39 gateway left open at a crash is named by its label and does not refuse the start.
   - **Mixed versions.** On the PostgreSQL kind each instance records in its start-lease row whether it reads labels. An instance at version 39 beside a live one at 38 or earlier, either way round, is refused at start with `instance-mismatch` and a sentence naming the upgrade. The move is not made one instance at a time.
   - **Going back to version 38.** It is not enforced: a start below version 39 does not look at labels. A session a label names and that is left open is then no longer reached by its label. So go back the same way: stop every instance, seal every session with `gateway seal-open --config <the version-39 configuration> --all`, then start every instance at the earlier version.
4. **Callers at version 39** (ADR-0051).
   - Read the minted `sessionId` from the receipt, or from the seal `/seal` answers. Do not assume it is the label sent.
   - To verify, export or cite, use that id. `cites[].sessionId` in `/act` stays a session id.
   - Callers of one scope share its namespace. One of them can learn, by a refusal, that a label is in use within its own scope. This is by design.
5. **`gateway store rotate-key`** (#563, #566; ADR-0050; SPEC.md §3b; docs/postgresql-store.md, "Rotating the signing key").
   - **The command.** `gateway store rotate-key --config <engine.json> (--connection-file <path> | --connection-env <NAME>) --owner <role> --runtime <role> [--from-key-version <name> --from-public-key <hex>] [--timeout <seconds>]`.
   - **What it does.** It rotates the PostgreSQL kind's signing key with every instance stopped. The next key is the configuration's `signingKeyVersion`, held to `signingPublicKey`. The key rotated from is the seed's key, or the key version `--from-key-version` names, held to `--from-public-key`. As the migration login acting as the owner, in one transaction under the migration's lock and every row of the start lease, it appends SPEC.md §3b's two rotation statements and reads the registry back as a walk to the next key before the COMMIT.
   - **What it refuses.** Among others: a live instance; a session that holds a receipt and is not sealed; a next key that is the key in force; and a `rotatedAt`, this host's clock, before the key history's last rotation. Nothing is written by a refused run.
   - **A COMMIT whose answer did not arrive** is settled by a rerun. It finds the rotation made and changes nothing, or rotates.
   - **The refusals that now name it.** SIGHUP on the PostgreSQL kind, and the start of an instance under another key id than a live instance's.
   - **This lifts v0.36.0's limit.** A PostgreSQL database that already holds a store can now move from the seed to a key service, or from one key version to the next. v0.36.0 allowed a key service on that kind on a fresh database only.
   - **What to do.** To rotate: stop every instance; seal every session left open with `gateway seal-open --config <the configuration naming the key in force> --all`; write the next key version and its public key into the configuration; run the command with it; start every instance under it.
6. **Batch fixes** (this release's reviews of #561, #565, #566 and #567).
   - **`/act` leaves no label when it is refused before admission.** `/act` recorded a minted label at its session step, before its platform, tool and `writeRequesters` checks. A requester the tool's list refused therefore added a label to the namespace of none, where nothing removes it. `/act` now looks the label up without writing and records it once the action is admitted, before the dispatch is claimed, as `/acquire` records one once its acquisition is admitted. Where another request recorded the label first, the action is admitted into the session the label names. A keyed read-back is the exception. It records its label once admitted and before `reconcileAction`, which can still refuse it: an unauthenticated key, a scope that does not hold the read-back source, or a refused grant or read-back. Such a refusal keeps its label (#570).
   - **A minted id that a label names already, on the PostgreSQL kind.** Minting also refuses an id that a label of the label's namespace already names, and the table's unique `series` refuses any other at the record. On the filesystem kind a minted id is checked against the sessions held and `receipts/<id>` only; an id only another label names stands at 2⁻¹²⁸ per pair (ADR-0051, decision 1).
   - **No writer leaves a key history its own check refuses.** SIGHUP's rotation, `gateway rotate-key` and `gateway store rotate`'s `continuedAt`, on the file kind, wrote whatever the host's clock said. `store rotate` on the PostgreSQL kind did the same. The registry is append-only, so a record stamped before the key history's last rotation left `GET /publickey/history` answering `500` for good. Each writer now builds the history as the route does, with what a store rotation carried, and refuses a time before the last rotation. A time before the last rotation is refused with a sentence naming both times and the host's clock. Two rotations in one second still hold.
     - `rotate-key` refuses before the next seed is made.
     - `store rotate`, on both kinds, checks the time first before anything is sealed, and stamps the continuation again after the seals. A refusal that leaves seals behind happens only where the clock steps back during the seals. Those seals are legitimate, delivered under the receipt sink's rules, and a rerun once the clock is corrected proceeds. Nothing is written to the new store or database.
   - **`store rotate-key`'s refusals name their cause.** It reported the clock sentence for any finding of the history with its record. It now reports that sentence only for a `rotatedAt` before the last rotation, and `the rotation's record would not hold in the key history: <finding>` otherwise. Nothing is written either way.
   - **SPEC.md §6a** says which seal after an interruption delivers the receipts the store holds: `seal-open --config`, or the start's own seal (`sealOpenAtStart`). A start without it delivers no stored receipt, and the sessions it finds open stay open.

## Decisions

- **ADR-0051** (#551), accepted, with its amendment settled at the build (#550): the start refuses only a session open that no label names; a removal takes the labels before the receipts; `gateway sessions` names none by `--no-scope`.
- **ADR-0050** (#536), proposed: `gateway store rotate-key` is recorded against decision 3(a).

## What this release does not establish

- That a live key service answers as the in-process stand-in does. Every key-service test of `store rotate-key` runs against a stand-in for the metadata server and the service.
- A coordinated live rotation across PostgreSQL instances (#537). Stop every instance to rotate.
- A move to version 39 one instance at a time. Every instance stops, and every session is sealed first.
- That a host's clock is right. The writers refuse a time before the key history's last rotation, not a time that is wrong but later.
- `/act` receipts and seals at the sink (#539).
- Of what v0.36.0 did not establish, these stand:
  - that a live sink acknowledges seals as the stand-in does;
  - the live directory service's error codes;
  - that anything of version 33 meets the live services as the stand-ins do;
  - that PS256 is taken by the live identity platform;
  - that a `read-external` tool only reads.
