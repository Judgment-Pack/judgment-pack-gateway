# Gateway v0.22.0

Gateway v0.22.0 completes the v0.22.0 milestone. Every current MCP tool, acquisition capability and connection operation carries an owner-declared operation family and effect, and the MCP annotations the gateway serves are derived from them. The gateway's durable state sits behind one store contract, with an audit export that `gateway verify` reads. The signing key can be rotated with a continuity statement that `gateway verify`, verify-ts and the witness follow. `gateway posture` reports which isolation protections a host enforces. An adapter can be held to a versioned envelope schema with `gateway adapter-conform`. A release now takes main's CI evidence at the tagged commit.

The release includes everything `v0.22.0-alpha.1` carried: the owner taxonomy for current MCP tools (#326), shared receipt construction and the receipt refusal tests (#319, #320, #322), the recurring Drive status correction (#321), and the development-kit adoption and public-text changes merged before it (#302, #304, #305, #306, #307, #309, #325). That alpha was a scoped cut for Agent v0.11.0. It does not graduate; this release supersedes it.

Closes #88, #89, #163, #164, #303, #311, #312, #315, #317, #318, #323, #324, #330, #332 and #334. #314 stays open for its sandbox modes and permission presets (v0.23.0).

## What an operator must do

- **Migrate current MCP bindings to the owner taxonomy** (required since `v0.22.0-alpha.1`). Current MCP admission requires binding version `2`, snapshot version `2` and engine configuration version `11`. Version 1 bindings and snapshots stay readable for historical inspection, but they cannot authorize current registration, configured startup or an unclassified tool offer. For each enabled operation:
  - declare `toolTaxonomies` for every exact allowed server tool;
  - update the pinned catalog explicitly;
  - recapture with `connect --replace`.

  Live and write operations have separate descriptor pins. When both are enabled, both captures must succeed before the configuration is replaced. A changed owner, endpoint, constraint or approved server metadata needs a new whole-byte approval and a restart of the configured processes. A failed replacement can leave unused immutable evidence, which is retained and not deleted automatically. Request `gateway-connections --catalog-v5` for the owner declarations and complete derived profiles. The default and older catalog outputs are unchanged and do not carry this contract. See the [taxonomy migration guide](taxonomy-v2-migration.md) and [ADR-0021](../adr/0021-owner-taxonomy-binds-current-tool-approval.md).
- **A write-back tool must declare `act`/`act`** (new since the alpha). A version 2 binding is now refused when it loads if its `write` operation allows a tool declared with any other operation or effect, such as `read`/`read-external` or `run`/`act`. The refusal names the binding. If you wrote a binding against the alpha with a weaker write declaration, correct it. The write tools in the shipped catalog (Azure DevOps and Databricks) already declare `act`/`act`. Version 1 bindings never reach this rule. The migration guide does not state it yet (#346).
- **Rotate the signing key only with the gateway stopped, and keep the first key pinned.** `gateway rotate-key --seed <file> --registry <file>` appends the continuity statement to the registry and then switches the seed. It keeps the seed rotated from as `<seed>.rotated-<n>`, which is yours to destroy.
  - On Unix, a running gateway holds a lock on its registry and `rotate-key` refuses while that lock is held. On other platforms no lock is taken, so stop the gateway yourself first.
  - If a rotation stops part way (a torn append or a switch not made), the gateway refuses to start under either key until `gateway rotate-key --resume --seed <file> --registry <file>` finishes it. Do not move the seeds by hand.
  - Verifiers keep the key they pinned from `keygen` and follow the rotations from it. After a rotation, the audit export's manifest names `firstKeyId`, the key to pin, beside `keyId`.
  - A verifier that follows no rotation gets every rotation vector wrong (#331), so verify a rotated store with this release's `gateway verify` or verify-ts. A store whose registry holds no rotation statement verifies exactly as it did before.
- **Run the engine image with an init** (`docker run --init`, or the orchestrator's equivalent). The image's entrypoint is the gateway itself, with no init. When the gateway is PID 1 it now reaps its own posture probe, but it does not wait for a source's orphaned descendants (#340).
- **`GET /posture` is a new endpoint on `serve`.** Where `identity` is configured it requires a bearer token, as `/verify` does. Otherwise it is open. Its reasons give no path and no account name. On Linux, the `descendant-reaping` reason ends with `; checked at <time>`. Read a line's name and state, not its reason.
- **Nothing is required for the store contract.** The filesystem store is the code that kept the files before, moved and not changed. Receipt formats are unchanged, and no existing receipt, seal, registry line or witness statement changes a byte. The conformance corpus gains twelve rotation store vectors (97 store vectors in all), and no earlier vector was edited. `gateway export` and `gateway-connections --export-observations` are new and optional.

## Owner-declared operation family and effect (#326 in the alpha, #346; closes #324)

- The families and effects are the ones agent ADR-0027 defines. Gateway [ADR-0021](../adr/0021-owner-taxonomy-binds-current-tool-approval.md) was accepted after the review of #326.
- #326 adds binding v2, snapshot v2, engine configuration v11 and the opt-in catalog v5. The owner's declarations are carried through catalog and `connect`, immutable publication, preview, the MCP listing and the drift checks before each call.
  - Every invocation checks its operation's approval and the whole approved tool projection before the selected call. That includes approved sibling tools left out of a narrowed execution allowlist.
  - Server annotations that contradict the declared effect are refused at admission. A missing declaration is never filled from tool names, hints or model text.
  - Catalog v5 keeps intrinsic operation families and the strongest effect of all constituents. Arbitrary SQL and seal operations are `act`.
  - On Windows, the file-mode bits of pinned evidence are read according to the platform. Windows ACL trust is not verified; it is a deployment assumption.
- #346 builds the rest of #324 that stays in v0.22.0:
  - `CheckCapabilities` refuses any capability (`answer`, `search` or `page`) without a valid declaration, so neither a catalog nor a connection's `research` can name an undeclared one. The `web` and `web-search` dispatch selectors take the capability's declaration, which leaves one table.
  - `gateway mcp` refuses to list a tool without a valid operation and effect ("a tool without both is not served"). Its annotations are derived from the effect in that one place.
  - A version 2 binding's write-back tools must declare `act`/`act` (see above).
  - Tests in both Go modules walk every capability, every broker method per provider (`document-processing` included), every dispatch selector per source and every binding operation, and name the first item without both fields. `testdata/tool-taxonomy/served-listing.json` is a handwritten vector of the served listing. Catalog encodings V2 to V5 and the default are byte-identical to the previous main.
- Metadata grants no execution authority. `/act` keeps its decision, citation and argument checks. A `read-external` label is not proof that a receipt signature was verified.
- No receipt carries an operation or an effect. The classification is bound by the digests of the approved snapshot and the owner declaration.
- Not in this release: classification for customer MCP registration, which moved to #310 (v0.23.0); signed descriptor provenance (#313); sandbox modes and presets (#314).

## Receipts held to one builder and to their refusals (#319, #320, #322; closes #311, #163, #164, #88, #89; all in the alpha)

- #319: acquisition and action receipts are built by one pure constructor, each path supplying its own inputs. Clock and salt draws, admission, signing and storage keep their order. A test reads the common required members from SPEC §1.2a and checks real acquisition and action receipts against them, with both LF and CRLF line endings. Independent byte expectations cover v2 and v3 command receipts, adapter material and chained action receipts.
- #320 (test-only): a 16-row parser table, a 25-row receipt-shape table and a 3-row statement-number probe hold each canonicalization and receipt-shape refusal to its exact message.
- #322 (test-only):
  - A directory named like a receipt is never counted as one, including when it takes the place of a missing tail receipt, which still reads `tail-rollback`.
  - The session ids `.` and `..` fail at the token rule and cannot be sealed, and the registry is left byte for byte unchanged.

## A store contract and a consistent audit export (#327, closes #315; #339, closes #330)

- The contract (`go/store_contract.go`) provides:
  - immutable content-addressed blobs;
  - exclusive indexed creation;
  - versioned documents replaced by compare-and-set;
  - durable append-only logs;
  - secret values made once;
  - leases with fencing tokens;
  - an atomic snapshot.

  Faults are typed. A write that was not made durable is an error, never a success. Error text stays its cause's own, so existing messages read as before.
- The filesystem store moved behind the contract unchanged, together with its path, link and owner checks. Artifacts, receipts, the seal registry, the witness's appends, the descriptor snapshots `connect` publishes and the seed all go through it. The connection custody uses the same document primitives in `adapters/internal/storecontract`.
- A conformance suite runs against the filesystem store and an in-memory one kept for tests. It covers create-once, concurrent compare-and-set, append order, lease expiry, stale fencing tokens, snapshot consistency and durability failures.
- `gateway export --config <engine.json> --out <dir> [--observations <file>]...` writes one consistent cut in the SPEC §1.3 layout. That cut holds the registry first, then the receipts, then the artifacts, followed by the decision records, the pinned descriptor snapshots, any observation journals given, and a `manifest.json` that names the authority, the key by its id and every file by digest and size.
  - Neither the seed nor the public key is in any file of the export.
  - A link among the store's receipts or artifacts refuses the export, and no file is read through one.
  - `gateway export --check <dir>` checks an export or a restore against its manifest, byte for byte.
  - `gateway-connections --export-observations` writes the custody's observation journal without credentials.
  - Every corpus store exports, restores and verifies byte for byte against the store's own verdict.
- Unchanged:
  - Verification reads the §1.3 layout directly. A store of another kind is verified through its export.
  - Locks stay locks, and no caller uses leases yet.
  - The directory sync for receipts and artifacts stays best effort. Windows cannot sync a directory.
- #339: fencing tokens never restart. A put or delete of a `lease-` document through `documents()` is refused, in any letter case. A grant after an attempted delete still counts up from the last token. Four safeguards that #327 moved unchanged now have tests: the staging file's sync, the series escape check, the storage intent's directory sync, and the owner and mode check on a pinned snapshot.

## Signing-key rotation with a continuity statement (#331, closes #317; #338, closes #332)

- SPEC.md §3b specifies a rotation as two registry lines appended together:
  - a `key-rotation` statement, signed by the key rotated from, that names the next key;
  - a `key-continuation` statement, signed by the next key, that names the key it continues.

  Both are signed under the prefix `judgment-pack-gateway/rotation/1:`, which no receipt, seal or witness statement uses. §1.2a, §1.4, §3, §4, §5, §5a.1, §6, §7 and §8.3 to §8.5 are amended to match.
- A verifier walks the registry from the key it pinned. A seal loads only under the key current at its line. A receipt is accepted under any key reached, but a session never goes back to an earlier key (`chain-broken`). The walk stops at the first of four findings:
  - `rotation-break`: a rotation statement out of form, or without its matching continuation on the next line;
  - `rotation-forged`: a continuation the current key did not name, or a rotation the current key did not sign;
  - `rotation-order`: an ordinal skipped or repeated;
  - `rotation-key-refused`: a next key that §8.4's key rule refuses, or a key already reached.

  `gateway verify` and `GET /verify` report `rotations: {count, keyId}` when they follow a rotation.
- `gateway rotate-key`:
  - Before it appends, it durably keeps the exact record in `<seed>.rotation`, with the registry's length and digest at the place the record goes.
  - It refuses while a rotation is already under way, and refuses a registry that changes under it. Each refusal writes nothing.
  - `--resume` rebuilds the record from the two keys and holds the kept record to it. It cuts only the record's own bytes, then appends the record whole and makes the switch.
- The gateway reads its own registry from the key its first rotation rotated from. It refuses to start, to seal, to admit into a session it does not hold, or to answer `/verify` when that walk does not hold or ends at a key other than its seed's. A session sealed under the old key stays sealed.
- `/act` resolves citations under every key the gateway's own walk reached, so a receipt minted before a rotation can still be cited.
- The witness holds its log to the walk's keys in order, and its chain continues across a rotation. `gateway witness verify --registry <file>` answers `{"refused": <status>}` when the walk does not hold.
- verify-ts implements the walk. Twelve store vectors were added, signed with published test seeds and given expectations written by hand from the specification. `gateway conform` and `gateway conform --impl` report 0 disagreements over all 97 store vectors.
- #338: once the gateway holds the registry lock, it looks again for a rotation under way and reads its registry again. Either refusal releases the lock, and the gateway exits naming `rotate-key --resume`. One sentence of §3b says so. An engine whose seed is configured as a link now looks beside both the configured name and the resolved one. Tests now drive `serve` and `serve --config` through the start-up refusal and the lock, and hold `--resume`'s digest and ordinal checks.

## Isolation posture (#333, toward #314; #340, closes #334)

- `gateway posture [--json] [--config <engine.json> | <serve command line>]` and `GET /posture` on `serve` report five lines, in a fixed order. Each line is `enforced`, `not-enforced` or `not-applicable`, with a one-sentence reason:
  - `source-user-switch`;
  - `descendant-reaping` (on Linux, a probe that starts a grandchild and kills the group);
  - `container-custody` (the engine image's markers, with the signer's capabilities held to `capabilityRefusal`);
  - `seed-file-protection` (on Unix, the seed checked without opening it);
  - `operator-program-confinement`, which is always `not-enforced`.

  The values for other platforms are stated, not probed.
- `--json` writes canonical JSON. The command exits 0 whatever it reports, 2 on a usage error and 1 when `--config` cannot be read. On the endpoint, reasons carry no path and no account name; the command keeps the full text.
- #340:
  - As PID 1, the gateway reaps the probe's grandchild.
  - The fallback that ends the grandchild by its pid is now tested.
  - The probe's verdict is kept per process, and concurrent calls share one probe. A probe that reached no verdict is not kept, so a transient failure is retried on the next call.
- What #314 still asks for, and this release does not ship: a sandbox policy with `read-only`, `workspace-write` and `danger-full-access` modes and OS-level backends, reported per spawned program class; and named permission presets reported in `gateway posture`. No sandbox backend exists yet for the report to name.

## A versioned adapter envelope and `gateway adapter-conform` (#335, closes #312)

- `schema/adapter-envelope.v1.json` (JSON Schema 2020-12) states the SPEC §6 envelope as the signer's `parseEnvelope` reads it. Its 15 valid and 83 invalid vectors were written by hand. A Go test holds the signer to every vector and each refusal to its reason. A pinned validator holds the schema to the same vectors and to the remote-endpoint table. The schema names the four things a schema cannot state, which the gateway applies itself.
- `gateway adapter-conform --shape airbyte|mcp|http [--vectors DIR] ...` runs an adapter as `serve` runs a source and reads its answer as an acquisition does. It mints and retains nothing.
  - A case expects `accepted` or `refused: CLASS`, where the class is one of `source-failed`, `timeout`, `output-bound`, `not-started`, `not-json`, `not-an-envelope` or `not-returnable`. A refusal of another class is unexpected.
  - The command exits 1 on any unexpected case and 2 on a case file it cannot read.
- `serve` and the command share `readEnvelope` and `returnableResult`, and the refusal messages are unchanged. `parseEnvelope` is not edited.
- New `dev.json` steps, `adapter-envelope-schema` and `adapter-conform`, hold every adapter program to the command.

## Release engineering (#343, closes #323; #302, #304, #306, #307, #336, #337, #341, #342)

- The release's `CI at the tag` job no longer runs `ci.yml` again. It runs the development kit's release evidence gate (`scripts/dev/release_evidence.py`, vendored at devkit v0.11.0) on the tagged commit.
  - The gate takes the evidence that a push to `main` recorded there for the four jobs its configuration requires: `check`, and the Linux, macOS and Windows Go legs. Otherwise it refuses by name and stops the release.
  - `.github/ci-evidence.json` sets the evidence's maximum age to 48 hours and admits prerelease tags.
  - Every release-specific job is unchanged and in the same order: admission, packaging, the native archive smoke tests, attestation and the draft, and publication behind the `production` approval.
  - [ADR-0022](../adr/0022-a-release-takes-mains-ci-evidence-at-the-tagged-commit.md) supersedes part of ADR-0008's determination 2. This is the first release through the gate.
- The native Go legs now run exactly Go 1.26.5, the toolchain `release.yml` names, instead of the newest cached 1.26 patch. A test holds the two equal. The required status names are unchanged.
- One stated bound: the dependencies pip resolves for the pinned `jsonschema` are not pinned themselves (`docs/releasing.md`, ADR-0022).
- The development kit is adopted (#302). CI's seven non-matrix jobs became one `check` job that runs every step of `dev.json`, while the three native Go legs and the required statuses stay as they were. The kit's scripts were re-vendored at v0.2.0 (#304), v0.4.0 (#306), v0.5.0 with the update-branches workflow (#307), v0.8.0 (#336), v0.9.0 (#341), v0.10.0 (#342) and v0.11.0 (#343).
- Pull requests run the checks their changed paths map to in `jpdev.json` (#337). A push to `main` and the release still run the whole list.
- `docs/releasing.md` describes the two prerelease forms: `vX.Y.Z-rc.N` is a candidate of the complete milestone, and `vX.Y.Z-alpha.N` is a scoped cut for a named consumer that never graduates (#346).
