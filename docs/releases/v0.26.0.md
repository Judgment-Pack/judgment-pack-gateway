# v0.26.0

This release refuses, before its source runs, a read or a seal into a session an earlier process
left open (#381), and lets the operator close such a session with a seal of its own kind, made
after an interruption, by `gateway seal-open` or at the start (#395). `serve` from the command
line can listen off loopback once told that it authenticates no caller (#387), a platform can name
who may ask for a write (#383), and a binding's `live` operation can read a plain HTTP API through
`adapter-http` (#384). A closed decision policy can carry a tool whose idempotency argument the
gateway sets (#380). Posture tells a wrapped source whose sandbox helper gave no report from an
unwrapped one (#405), and names the platforms a delegation cannot serve (#376). Conformance
compares observations, runs vectors under `--ordinary-seals-only` (#398) and reads member names
exactly (#410). The documentation now says that one gateway runs per store and registry, and what
the source sandbox needs of the kernel (#385, #386). The release tag is also the milestone. The
implementation rows are

## Upgrade

1. A session the gateway does not hold, in which the store holds a receipt, is refused before its
   source runs, at every `engineVersion` (#394). Stopping a v0.25.0 gateway to upgrade leaves
   every session it had not sealed in that state.
   - `/acquire` and a delegated `/acquire` into such a session answer `400` with the left-open
     refusal (quoted under #394, below). v0.25.0 ran the source and failed at the stamp, or, in a
     session that had lost receipt 0, minted a new one beside the old chain. An action's
     read-back goes through the same admission, and `/act` already refused a session it did not
     mint. A client acquires into a new session after a restart.
   - A session the store holds as a file or a link, or cannot read, is refused with a text of its
     own. An empty session directory, or one holding only a staging file, is taken up.
   - `/seal` of a session the gateway does not hold answers `session is sealed in the registry:
     <id>` where an earlier process sealed it, then the refusals above, and `no such session:
     <id>` otherwise. v0.25.0 answered `no such session: <id>` to all of them.
   - The left-open text as released ends with a clause #397 added. Text matched against the form
     quoted on #394 needs these bytes.
   - Roll out by stopping the old gateway, waiting for it to exit, then starting the new one: on
     Unix a second gateway on the same registry is refused at its start, exit 1 (documented by
     #404).
2. A decision policy, open or closed, whose `bind`, `fix` or `shape` names the tool's
   `idempotencyArgument`, or a pointer under it, no longer loads (#396). The start and `connect`
   refuse it (`decisionPolicy.<tool>: bind[<i>] names "<pointer>", the tool's idempotency argument
   "<name>", which the gateway sets to the action key (actionRecovery); ...`), and `connect
   --replace` refuses to keep it. Remove that entry: the gateway sets the member itself. A closed
   policy on such a tool now admits a keyed request that omits the argument or sends it equal to
   the key, where v0.25.0 refused all of them. No configuration that loaded and admitted a
   request before is refused at `/act` now.
3. Upgrade every verifier of a registry, Go and verify-ts alike, before anything seals a session
   after an interruption (#397).
   - A v0.25.0 or older verifier drops a `seal-after-interruption` line, so the session reads
     `unregistered-session` and `ok` is false: it fails closed.
   - One exception: a line of the new kind carrying the signature an ordinary seal would carry
     (the vector `interruption-seal-is-not-an-ordinary-seal`) is graded `ok` by an older reader,
     which takes it for an ordinary seal.
   - Downgrade: a v0.25.0 gateway does not see such a session as sealed and has no #394 check, so
     a read into it runs its source and then fails at the stamp. It refuses an engine
     configuration of version 17 or 18 as an unsupported version, and one that pins an `http`
     binding by the shape's name.
4. A verifier implementation answers more of the corpus (#397, #409). It holds 131 store vectors
   (51 in `stores/`, 80 in `v3/stores/`), 18 of them new: 13 `interruption-seal*` vectors, and 5
   that state observations or run under `--ordinary-seals-only`. The 54 witness, 25 witness
   recovery and 30 canon vectors are unchanged, and so is every earlier vector.
   - The contract's verify is `CMD verify [--ordinary-seals-only] <store-root> <registry-path>
     <authority> [<decision-records-dir>]`. The runner passes the option first, exactly for a
     vector giving `"ordinarySealsOnly": true`. No verdict there disagrees with that vector
     (`store <name>: no verdict under --ordinary-seals-only:` and at most 256 bytes of its
     standard error), and the run goes on and exits 1. No verdict for a vector run without the
     option still stops the run, exit 2.
   - Observations are compared as a multiset, and only for a vector that states them. An
     implementation's `"observations": null` counts as none, and a member that is no array of
     objects disagrees. A vector stating `null`, or an element that is `null` or no object,
     refuses the run.
   - An implementation that reports no observations disagrees with two of the five new vectors,
     one that takes the option and ignores it with two others, and one that refuses it with the
     four run under it.
5. `gateway conform` reads an answer, and every vector file, by its members' exact names (#412).
   - An answer's member spelled another way, case included, is not read. The vectors it would
     have answered disagree, and an object compared whole (a finding, an observation, a witness,
     the rotations, a witness answer's refusal and its `latestCheckpoint`) holding it disagrees.
   - A member given twice in one object, at any depth, disagrees with that vector (`store <name>:
     the verdict gives a member twice in one object:` or `witness <name>: the answer gives a
     member twice in one object:` and the name, quoted), and the run goes on and exits 1. It is
     looked for once the answer is read as one JSON value and before any member is read, so it
     wins over a member of the wrong type.
   - An answer that is not one JSON value, is not an object, or gives a member the runner reads
     with the wrong type still stops the run, exit 2.
   - A store vector with a member the runner does not read, at the top or in `expected`, now
     refuses the corpus (#409), as a witness or witness recovery vector already did. Another
     spelling is such a member in both readers: `gateway conform` refuses it as `<path>: json:
     unknown field "Authority"`, verify-ts's corpus reader as `<file>: unknown member
     "Authority"`. `canon.json` passes it over.
   - A `gateway adapter-conform` case gives each of its two members once, under its exact name:
     `{"Request": ...}` stops the run before the adapter starts.
   - Every vector file is UTF-8, and a name is compared as decoded: `"\u006fk"` is `ok`, so an
     object giving both gives one name twice.
   - A verifier that writes each member of its answer once, under its name, answers as before.
6. `--ordinary-seals-only` goes first in `gateway verify` and in verify-ts `verify` (#397). Given
   anywhere later it is a usage error, exit 2 in Go and 64 in verify-ts, where it was read as a
   path. A store root, registry or decision-record directory of that name is given as
   `./--ordinary-seals-only`, and an authority label so spelled can no longer be passed. `/verify`
   has no such option.
7. New values in a verdict (`gateway verify`, `/verify`, verify-ts):
   - the observation `session-open` on the last receipt of every whole session no seal closes,
     beside its `unregistered-session` finding, which stands (#394). A running gateway's own
     unsealed sessions are observed so on `/verify`. `ok` does not change.
   - for a session a seal made after an interruption anchors (#397): the observation
     `sealed-after-interruption` on its receipt at `finalCount - 1`, beside `ok`; the findings
     `seal-head-mismatch` and `seal-conflict`; and, under `--ordinary-seals-only`, the finding
     `sealed-after-interruption` in the observation's place.
8. New offline command, run with the gateway stopped (#397): `gateway seal-open (--config
   <engine.json> | --store <dir> --seed <file> --registry <file> --authority <authority>)
   (--session <id> | --all)`.
   - It writes each line it appends on stdout and each refusal on stderr.
   - It exits 0 when it sealed or found nothing to seal (`seal-open: no session in the store is
     left open; nothing was sealed`), 1 on any refusal or failure, and 2 on a usage error.
   - On Unix it refuses while a gateway holds the registry (`...; stop the gateway, then seal`).
     Elsewhere it seals and writes `seal-open: this platform locks no registry, so a gateway still
     running was not looked for; the gateway was to be stopped`.
   - It refuses a rotation under way, and a registry whose walk ends at another key.
9. engineVersion 17 adds `sealOpenAtStart` (`true` or `false`), refused by name under 16 and
   below. `serve --seal-open-at-start` is its command-line form. Neither is on unless given
   (#397).
   - On, the start seals each session left open whose receipts are whole, under the registry hold
     and before anything is served. It writes `start: sealed after an interruption: <line>` for
     each, and `start: <refusal>` for each session it leaves open, on stderr before the readiness
     line.
   - A session it cannot read, or a seal it cannot append, stops the start (`start: sealing the
     sessions left open: ...; the gateway does not start`), exit 1.
   - `connect` raises no file to 17 or 18, so edit `engineVersion` by hand.
10. engineVersion 18 adds a platform's `writeRequesters` (#402), refused by name under 17 and
    below. It needs an `identity` and `write: true`, and without a `delegation` each entry's
    issuer must be `identity.issuer`.
    - A requester the tool's list does not name is refused `403` with exactly the body below. A
      client that expects only `400` or `401` from `/act` handles it.

      ```json
      {"error":"the requester is not one the configuration's writeRequesters names for this tool","refusedAt":"write-requesters"}
      ```

    - `connect --replace` keeps the member. It refuses a replacement without `--write`, or one
      whose binding's write operation no longer names a tool the member lists. To drop the
      member, remove it from the file first.
11. `serve --listen ADDRESS [--accept-unauthenticated-callers]` (#399). Without `--listen` nothing
    changes.
    - ADDRESS is an IP literal in its canonical form. A name (`localhost` included), a zone, a
      port, an empty value and an IPv4-mapped form are refused, and an address written another
      way is refused naming the form to give.
    - An address that is not loopback (loopback is `127.0.0.0/8` and `::1`) needs the
      acknowledgement, and the acknowledgement without such an address is refused. Each refusal
      is a usage error, exit 2.
    - Each address is bound in its own family: `0.0.0.0` binds IPv4 alone, `::` IPv6 alone.
    - Off loopback the start writes `start: listening on <address>, which is not a loopback
      address: ...` on stderr, after any line of item 9 and before the readiness line, which is
      unchanged.
    - `gateway posture` takes serve's options through the same parser, so it accepts these two and
      refuses the same combinations. `serve --config` is unchanged: its `listen` stays loopback.
12. A binding's `live` operation may be of shape `http` (#406), in bindingVersion 1 only and as the
    binding's only operation.
    - A platform on such a binding is refused a `grant` or an `endpoint`, and the operation an
      owner taxonomy.
    - Changed texts: `operation live is served by the mcp or the http shape, not "<shape>"` (was
      `operation live is served by the mcp shape, not "<shape>"`), and `platform <name> has no

    - `connect` writes a check line for the source. A delegated acquisition on such a platform is
      refused `grant-unknown`.
    - No configuration member, engine version or binding version is added. `adapter-http` ships
      in the image and in the archives.
13. Posture bytes change; posture is information, never a gate.
    - Every gateway with a `delegation` reports a third delegation line, `delegation-grants`, after
      `delegation-sender-constraint`, so its canonical `/posture` and `gateway posture` bytes
      change (#411). The line is `enforced` when a platform a delegated call can reach names a

    - `write-requesters` comes last, where some platform gives the member (#402).
    - `/posture` gives a sentence of its own for a wrapped source whose backend check gave no

    - `/posture` names no uid and no mode: its `seed-file-protection` and container-custody lines

## A session an earlier process left open (#394; refs #381)

A gateway holds each session's next call index and chain head in memory, and seals a session only
when asked, so a gateway that stops leaves every session it had not sealed in the store with
receipts and no seal. Neither the chain nor the count can be had from the store, which is outside
the trust boundary: a chain continued from the disk, or a seal of the count found there, would sign
over a rollback made between the stop and the start. A gateway now takes up a session it does not
hold only where the store holds no receipt in it. This is judged under the admission lock, before
the custody, the issuing host, the budget or the source:

- a session directory holding any `*.json` entry is refused as left open;
- an entry of another kind where the directory would be (a file, a link, one that leads nowhere)
  is refused as no session directory;
- a look that fails for any reason but absence is refused as unread, never taken for empty;
- an empty directory, or one holding only a staging file, is taken up.

Each refusal answers `400`, with its text as the `error`, `<id>` being the session:

```text
session <id> was left open by an earlier process: the store holds receipts in it that this process did not mint, and no seal closes it; its chain is not continued from an empty memory, nor is it sealed here from a count on disk, so acquire into a new session (gateway verify reports this one unregistered-session, and observes it session-open while its receipts are whole; gateway seal-open, with the gateway stopped, seals it as sealed after an interruption)
session <id> is in the store as something other than a session directory, which this process did not make; nothing is taken up there
session <id> could not be read in the store, so whether an earlier process left receipts in it is not known; it is refused rather than taken for empty
```

`/seal` reads the registry before the store, so a session an earlier process sealed is said to be
sealed, never left open. The verifiers observe `session-open` on the last receipt of a whole session
no seal closes. The observation says what the store shows: a whole session copied from another
store reads the same.

## A seal made after an interruption (#397; closes #395)

A seal of the ordinary form says the minting process sealed its own count. A seal made after an
interruption is a registry line of its own kind, saying that the key holder sealed what the store
held then (SPEC.md §3c):

```json
{"finalCount":3,"headSignature":"<128 hex>","keyId":"<32 hex>","kind":"seal-after-interruption","sealedAt":"2026-11-10T00:00:01Z","sealedVia":"command","sessionId":"s1","signature":"<128 hex>"}
```

`sealedVia` is `command` or `start`. The signature is over
`judgment-pack-gateway/seal-after-interruption/1:` and the canonical form of the record without
`signature`. `headSignature` is the signature of the receipt at `finalCount - 1`, as the receipt
file gives it, so a session whose receipts were replaced after the seal is not the one it sealed
(`seal-head-mismatch`). A line of this kind is read as that seal and as nothing else, so one
carrying an ordinary seal's signature loads nothing. More than one seal for a session, at least one
of them of this kind, is `seal-conflict`, once, and the first still anchors it.

`/seal` never makes one. `gateway seal-open` makes it with the gateway stopped (Upgrade, item 8),
and the start with the switch on (item 9), each over a session whose receipts are whole. The
registry gains a line shape and no version step. The corpus adds 13 store vectors for it, and
`testdata/interruption-seal/cases.json` adds 26 rows that both implementations run, which are not
conformance.

## A closed policy and the idempotency argument (#396; closes #380)

The gateway sets a tool's `idempotencyArgument` to the action key (`actionRecovery`). A policy that
bound, fixed or shaped it would admit one key, or none, or only a record that states the key, so a
configuration that does so no longer loads (Upgrade, item 2). A closed policy reaches that one
top-level member as the gateway's while the request holds an action key. A request with no key is
given no member, and one it sends is refused `argument "<pointer>" is reached by no binding`
(`policy-bind`).

## Listening off loopback from the command line (#399; closes #387)

`serve` from the command line has no `identity`, so every request it takes is admitted. With
`--listen` it binds the address named, in that address's own family, beside `--port`. Off loopback
it requires `--accept-unauthenticated-callers`, and writes this before the readiness line:

```text
start: listening on <address>, which is not a loopback address: other hosts can reach this gateway, and it authenticates no caller, so whoever reaches it can run its sources and have receipts and seals signed under its key
```

An authenticating proxy that terminates TLS, or a private network that admits only the intended
callers, belongs in front (README, "Listening off loopback"). ADR-0023 records the rule, and narrows
one sentence of ADR-0013 to the engine form, whose `listen` stays loopback.

## Who may ask for a write (#402; closes #383)

A platform's `writeRequesters` names, for each write tool, the requesters `/act` takes a write
from:

```json
"writeRequesters": {
  "platform": [{"issuer": "https://issuer.example", "subject": "user-17"}],
  "tools": {"update_ticket": [{"issuer": "https://issuer.example", "subject": "user-42"}]}
}
```

A tool under `tools` is held to its own list, every other write tool to `platform`'s, and a tool
with neither to none. An empty list names nobody, so the member only narrows. The requester is the
one the action receipt names: a bearer token's configured issuer and `sub`, a delegation chain's
`sub`, or a reservation's `sub`, each compared byte for byte. It is held once the session, platform
and tool steps pass, and before the arguments, the action key, the decision, the cites and the
policy are read. It covers a first dispatch, a replay, a reconciliation, a read-back, a delegated
call and a reservation's. Nothing is sent, journaled or minted for a requester it refuses, and
`/acquire` is not held. The posture line `write-requesters` is `enforced` when every write tool is
held to a list and `not-enforced` otherwise, and counts tools without naming a requester.

## A live operation over plain HTTP (#406; closes #384)

A binding's `live` operation of shape `http` (ADR-0024) derives `<platform>/live` as `adapter-http`,
started as every engine source is: as the platform's OS user, under the source sandbox from engine
version 13, with the platform's credentials file. The binding fixes the endpoint, the paths, the
methods among `GET` and `POST` (`POST` alone where it names none), the headers, and one credential
member, sent as `Authorization: Bearer` or under a named header. An acquisition chooses a path and a
method among them, and gives the query and, by `POST`, the body. The engine passes `--endpoint=`,
`--paths=`, `--methods=`, `--credentials=`, `--bearer=` or `--credential-header=`, `--header=`, and
for a check `--check-path=`. It passes no `--ca-file`, `--max-output` or `--timeout`: the adapter's
own bounds, 1 MiB and 20 s, sit inside the engine's 1 MiB and 30 s. The receipt is the plain form's.
Its acquisitions name no tool, so the MCP listing shows none, `/act` does not reach it, and a
delegated acquisition is refused `grant-unknown` before the scope check.

## Posture (#408 and #411; closes #405 and #376)

- `/posture` named a wrapped source whose sandbox helper gave no report as one that selects no
  wrapper. For that source it now answers "the source configuration selects the adapter sandbox
  wrapper, and its backend check gave no report, so nothing was measured for this source; a launch
  checks again before it starts and is refused, whatever its mode, unless that check completes;
  gateway posture, given the configuration, names the cause". The entry's `mode`, `backend` and
  `state` are unchanged, and so is the answer for a source with no wrapper. The operator's reason
  for that source is `sandbox-not-enforced: source-user backend check did not complete
  successfully:` and the cause, with paths removed.
- `delegation-grants` (SPEC.md §11.9) says whether every platform a delegated call can reach names
  the connection grant its delegated calls are admitted under. A platform is reached through a
  write source or an `mcp` source. Where some name one and some do not, the line is `enforced` and
  names the rest, at most five, sorted, with the others counted: a platform with no grant refuses
  every delegated call (`grant-unknown`), so it is not an open boundary.

## Conformance (#409 and #412; closes #398 and #410)

These are normative for an implementation answering the corpus. No receipt, registry,
verification result, engine version or earlier vector changes, and both verifiers answer as
before. #409 compares observations where a vector states them, runs four vectors under
`--ordinary-seals-only`, and holds store vectors to the members the runner reads (Upgrade, item 4).
#412 reads every answer and every vector by exact name, and makes a member given twice in an answer
a disagreement with that vector, where it was read by its last occurrence (item 5). `gateway
conform` checks the README's counts on every run, the image's and a release's included.

## One gateway per store and registry, and the source sandbox (#404; refs #385 and #386)

Documentation only.

- README, "One gateway per store and registry": on Unix a running gateway holds an exclusive
  `flock(2)` on its registry until it exits, and a second start prints `start: the registry is
  held by a running gateway, or by a rotation under way: <registry>` and exits 1. The store's lock
  is shared, and keeps out a journal compaction, not a second gateway on another registry. Nothing
  is locked elsewhere than Unix, and the start says nothing of it. The lock is advisory, so the
  store and the registry belong on a local filesystem.
- `docs/design/engine-image.md`: the image carries `adapter-sandbox` and no bubblewrap, so a
  restricted source there is confined by Landlock or not at all. With no backend the engine
  starts, and each restricted launch is refused `sandbox-not-enforced`.

## The pre-release batch (#414)

The LOW findings of the pre-release review, all in posture:

- **`/posture` names no account.** The seed line answers "serve refuses this seed: it is not a
  regular file", "... it is not owned by the gateway's own user", "... it is readable by group or
  other", or, for any other refusal, "serve refuses this seed; gateway posture, given the
  configuration, says why". The container-custody line answers "the gateway binary is not the
  signer's own at mode 0700". Both gave uids and a mode before, in every earlier release;
  `gateway posture` still does.
- **A budget for each source.** One source whose sandbox helper hangs no longer makes the sources
  after it read as unmeasured. Each check has 12 seconds, within 30 seconds for the report. A
  source whose check the report had no time left for answers "the source configuration selects
  the adapter sandbox wrapper, and this report's time for backend checks ran out before this
  source's check gave a report, so nothing was measured for this source in this report". A report
  waits on a source whose check a launch is running, so the 30 seconds can be exceeded by that
  launch's check.
- **The sentence for an unmeasured source**, as under Posture above, and the cause in the
  operator's report.
- `delegation-grants` reads a platform's sources in name order.

The remaining finding is filed: the left-open check and `seal-open` read receipts from the
filesystem and not through the store kind, which is the same place for the one kind that ships
(#413).

## What this release does not establish

- A seal made after an interruption does not establish that the session was never sealed
  (SECURITY.md). One who can write to the store and the registry, without the key, can shorten a
  sealed session, take its seal line away and have the shorter session sealed by a key holder;
  with `sealOpenAtStart` on, at the next start with no operator looking. A consumer that needs to
  rule this out verifies with `--ordinary-seals-only`, which `/verify` does not offer.
- `serve --listen` off loopback is plain HTTP, authenticates no caller and limits no rate. The
  engine form cannot listen off loopback (#400), and posture does not report the listener (#401).
- `writeRequesters` restricts who may ask. It is no approval and no decision, and the target
  system's own authorization is unchanged. Under a delegation nothing ties an issuing host to an
  issuer, so an entry admits a chain any configured issuing host signs naming that `sub`; and with
  only `tools` given, a write tool a replaced binding adds is held to no list (#403).
- The `http` shape serves no delegated call and no write. A private certificate authority reaches
  it only through the platform's `environment`, which the binding's pin does not cover. An
  endpoint that takes no credential cannot be named, and a path may hold characters the client
  escapes on sending (#407).
- The registry is locked only on Unix. Elsewhere neither `seal-open` nor a second start can tell
  that a gateway is running.
