# v0.24.0

This release adds stable action identity (#355), connection grants and publisher trust for customer
MCP servers (#357), delegated authority for an agent acting for a person or a service (#356), and
action keys held to their first scope that close before answering that nothing was sent (#352).
The release tag is also the milestone. The implementation rows are
[#358](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/358),
[#360](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/360),
[#361](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/361),
[#363](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/363),
[#365](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/365) and
[#367](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/367), and the pre-release batch
that carries these notes.

## What an operator must do

- **Settle pending agent keys before upgrading (#365).** Takeover protection starts at a key's first
  request that sends `keyScope`. A key reserved before this release, or by any request without
  `keyScope`, has no first scope: another subject sending `keyScope` on it is not refused, and sends
  the write. That is every agent job in flight across the upgrade. Settle the pending keys of agent
  jobs, and of any client that will start sending `keyScope`, before upgrading the gateway or
  switching the client to `keyScope`.
- **Narrow Databricks scopes before upgrading; grants (#360).** Narrow a Databricks service
  principal saved with a scope no operation declares:
  it is refused as `excess-scope` until it is narrowed, with no opt-out. A Google or Notion token
  that states more than the requested scope at connect is now refused as `excess-scope`, not
  `provider-unavailable`. Existing grants have no owner, and are used as before and reported as
  `owner-missing`; `gateway-connections --grants report` lists them. **Grants cover the connection
  custody only.** An engine platform takes its tokens from the operator's credentials files and uses
  no grant, so an action through `/act`, delegated or not, gets no owner read, idle expiry,
  quarantine or `excess-scope` check (gateway #368, planned for v0.25.0).
- **Keys and identity (#358).** Keys reserved from v0.24.0 on survive a later release that adds,
  renames or reorders a derived adapter flag. **Keys v0.23.0 reserved keep v0.23.0's identity for
  good.** They answer under v0.24.0 as before, but under a later release that changes a derived flag
  each of them answers `action-key-conflict`, pending or settled (a settled one no longer replays).
  Nothing is sent again, and settling a key first does not avoid this. A receipt an action record
  cites is now durable before the record.
- **Journal operations (#365).** Compaction has a new procedure, in
  [action reconciliation](../design/action-reconciliation.md#compaction): never remove
  `actions/index/`, a closed entry or a subject record, and for an indexed or delegated entry move
  only `action.json`. Retention must outlast the longest client retry window, and the whole job of
  any client that reconciles. Back up `actions/` whole, and reconcile at the store that took the
  first send. **The gateway enforces neither the retention period nor the journal's growth limits**:
  both are defined in the design notes only, and compaction is an offline operator procedure. A
  leftover `.staging-*` directory is inert. A key answering `action-key-outcome-unknown` has a
  documented operator path, and so does a damaged subject record.
- **Publishers (#361).** Keep `<engine.json>.publishers.json` beside the configuration when it is
  moved or restored: a record that cannot be read refuses every customer platform's acquisitions,
  and every action that would dispatch, as `publisher-record-unreadable`. Under
  `gateway publishers --policy refuse`, an unmaintained publisher refuses registration, acquisitions
  and every action that would dispatch now. **What a key already holds is still answered:** a
  completed key replays its retained answer under either policy and with an unreadable record. Its
  read-back runs the publisher's program with the platform's credential, so it stays refused, and an
  uncertain key answers `action-reconciliation-unavailable` with its uncertain record, naming the
  refusal. A first request the policy refuses has already reserved its key. **Declaring a publisher on an existing customer binding changes the
  binding's pin**, and with it each pending key's identity: drain its pending keys, re-pin, and
  `connect --replace`.
- **Delegation (#363).** A `delegation` member needs engine configuration version 15 and
  `identity`. A configuration without it, and every undelegated call, are unchanged. Version 15
  includes version 14's required `actionKey`, so **on Windows every `/act` under it refuses**, as
  under 14. Delegation credentials live in memory: a restart ends them, and the issuing host binds
  again. No issuing host ships with this release.
- **Readers.** Verify delegated stores with this release's readers, Go or TypeScript. v0.23.0's
  readers return `ok` for a malformed `delegation` or `reconciler` member: 8 of the corpus's new
  vectors that this release calls `malformed`.
- **Downgrade.** v0.23.0 refuses every key this release reserved, closed keys included
  (`unknown member "identityVersion"`), and sends nothing under them. It answers its own keys,
  including one this release has since dispatched, and it ignores first scopes. Do not downgrade
  while a client relies on a first scope or on a closed key.

## Stable action identity (#358; closes #355)

A keyed action's identity (version 2) binds the approved fields: binding, approval pins, server
definition, endpoint, descriptor provenance, and the sandbox and policy digests. It no longer binds
the adapter command line a release derives, so a later release that adds, renames or reorders a
derived flag no longer turns those keys into conflicts. A reservation records the version it was made
under; v0.23.0's version 1 is computed beside version 2 and held to its own computation. The receipt
an action record cites is now made durable before the record (#352 L4). The journal's retention,
offline compaction and damaged-entry procedure are documented in
[action reconciliation](../design/action-reconciliation.md) (#352 L5).

Known limits: a key v0.23.0 reserved stays version 1 for good, as above. The owner-declaration pin is
the digest of a document this release composes, so a release that changes how it is composed changes
version 2 for every key with owner declarations, and must say so.

## Connection grants (#360; #357, part a)

- Each Drive, Gmail, Notion, Databricks and Azure DevOps connection now has a grant record in its
  custody: its owner, its scopes required, granted and used, its last use, an optional idle expiry,
  and whether it is active, quarantined or revoked.
- A token or configuration that holds a scope no operation declares is refused as `excess-scope`,
  with the extra scopes named. This applies at connect, at a Google renewal that adds one, and at
  every use. A Databricks service principal's `all-apis` is admitted and reported as wider than
  needed.
- Every use of a grant's credential by the custody (an acquisition, an action, a search or a
  connection test; never an engine platform's `/act`, as above) is refused when the grant is
  quarantined or idle-expired. If the grant has an owner, every
  such use is also refused unless the owner's issuing host answers that the owner is current.
  Removing an owner revokes or quarantines every grant it owns.
- `gateway-connections --grants report` lists the grants, their unused scopes and findings. It names
  no path, no account and no token. No receipt, seal, registry line or corpus vector changes.

Known limits: grants cover the connection custody only, as above; carrying the owner in delegated
admission (spec #284 NC2) is open. Reassignment out of quarantine, and acceptance, are not built.

## Publisher trust for customer MCP servers (#361; #357, part b)

- A customer binding may declare its server's publisher: an npm package, a GitHub repository, or a
  registrable domain. A host, or a host on a shared platform such as `vercel.app`, is not a domain
  publisher; declare the repository or package instead.
- `gateway connect` reads the publisher's liveness before anything runs, shows it with the approval
  and records it beside the configuration. `gateway publishers --check` reads it again on the
  operator's schedule.
- A deprecated, archived, expired, redemption-period, pending-delete, or no-longer-registered
  publisher is reported as `publisher-unmaintained`. Under `gateway publishers --policy refuse`, it
  refuses the registration, each acquisition, and each action that would dispatch now (a first
  dispatch, a freed attempt, or an action with no key). A completed key still replays its retained
  answer; a read-back stays refused, so an uncertain key answers `action-reconciliation-unavailable`
  with its uncertain record.
- A publisher the public source cannot show (a private package or repository, or a top-level domain
  without RDAP) is reported as `publisher-unverifiable` and never refused.
- A reading that fails never lifts a conclusive one. An unmaintained publisher stays refused until a
  conclusive maintained reading, and `gateway publishers --check` warns and exits 3.
- A registration whose name closely matches an integration the gateway ships, under another
  publisher, is flagged `name-lookalike`.
- A binding without `publisher` is `undeclared` and is not refused, and the default policy is
  `report`. Declaring one changes the binding's pin (see above).

## Delegated authority (#363; #356, and the delegated half of #352 M6)

Spec RFC 0030, a Draft. With engine configuration version 15 and its `delegation` member, the
gateway admits an agent's calls made for a person or a service under a delegation from an issuing
host. The host binds a credential to the delegation's chain, living at most five minutes and bound
to the run's key (DPoP, RFC 9449). Each acquisition and action is admitted immediately before
dispatch: signatures and narrowing, validity, scope (source, tool, declared effect), and the host's
answer for registration, revocation, limits and the subject's standing, which refuses when it cannot
be read. Receipts carry a signed `delegation` member, and `caller` names the subject, so earlier
readers read the same caller. Read-backs of delegated actions record who sent them (`reconciler`).
Action keys under a delegation are scoped to the subject, the root actor and the issuing host, so a
takeover under a new lease reads back instead of writing again, and only the run's actor ever
dispatches. With #365, the actor's first reservation also records the key's first scope, so another
root actor or another subject holding the key is refused. No platform credential is narrowed: the
gateway enforces the scope, and posture says so. A configuration without the member, and every
undelegated call, are unchanged.

Known limits: SPEC.md §11.10 lists what the gateway defines where the RFC leaves it open, and what is
not built (offline `delegation-unresolved`, issuing-host key rotation, revocation statements). A
delegated write uses no grant (above).

## Action keys held to their first scope (#365, #367; closes #352 and #366)

`/act` gains `keyScope` and `reconcile`, with the refusals `action-key-scope-conflict`,
`action-key-not-dispatched`, `action-key-closed` and `action-key-outcome-unknown`. A request sending
`keyScope: "authority"` records the key's first scope before reserving, and any request on that key
under another scope, sending the members or not, is refused before anything new is reserved or sent.
A delegated run's actor records it with its first reservation. A first scope takes nothing a scope
already holds. A reconciling request never dispatches: where it would answer that nothing was sent, it
first closes the key on the name a dispatch of that attempt would take, so exactly one of the two
happens across processes, and only then answers `action-key-not-dispatched`. `action.json`, a
reservation, a subject record and a delegated dispatch marker now appear whole, so a crash leaves no
partial record that refuses its key for good. A leaf of a delegation that could never dispatch is
refused as its admission would be and leaves nothing behind (#367).

**On upgrade an operator changes no configuration.** The journal procedures and the upgrade order
above apply. A request that sends neither member behaves as before on a key no record names, and SPEC
§1.2b states exactly where it differs on a key another scope holds.

Known limits: a first scope proves the same subject, not the same owner, and is no authorization: a
key is no secret, and anyone who passes the action ladder holding a key no record names can take it,
which denies the key and sends nothing. The record is one store's: a second store under the same
authority, or a store restored without `actions/`, can answer `action-key-not-dispatched` over a key
dispatched elsewhere. A key answering `action-key-outcome-unknown` stays there until an operator acts.
A delegated request the issuing host refuses at admission still takes the key's records first.

## Corrections to the v0.23.0 notes

The v0.23.0 notes are not edited after publication; these lines correct them.

- "A later release that adds or reorders a derived flag does the same": that holds for keys v0.23.0
  reserved, for good. Keys reserved from v0.24.0 on survive such a release (#358).
- "(#352 settles this scope for the agent)": #352 settles it from a key's first request that sends
  `keyScope`. Keys reserved before that, v0.23.0's among them, are not covered (above).
- "The journal has no retention policy yet": its retention, compaction and damaged-entry procedures
  are now documented, and the gateway enforces neither the retention period nor the growth limits.
- "The receipt a journal entry cites is synced best-effort": from this release it is durable before
  the entry cites it (#358).

## What this release does not establish

- RFC 0030 is a Draft, and no issuing host exists yet: the Desk side is not built.
- The delegation vectors were signed by a same-vendor scratch signer.
- Clock skew across hosts was not exercised.
- Retention and the journal's growth limits are defined, not enforced. `actions/index/` at millions
  of files was not measured.
- Mixed-version processes on one store were driven only by the pre-release review's probes.
- A real power loss: crash points were process kills and truncated files, and durability is the
  system-call order on Linux.
- An agent host end to end: the agent's members and refusal readers ran against this gateway's
  answers, and its store and writer did not.
- A delegated write's grant checks (gateway #368).

whole `dev.json` list in `check`. The tagged commit's main-push CI is what the release takes. Each
review is recorded on its pull request. Every pull request in this release was built and reviewed by
Claude Opus (Anthropic), same vendor, under the maintainer's approved same-vendor exception, and none
is a cross-vendor claim.

  fixed in the PR with tests and mutants: the decision policy and recovery contract unpinned in the
