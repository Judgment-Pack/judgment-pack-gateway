# v0.34.0

This release adds two engine configuration versions and extends one rule. **It has one breaking
change:** each live tool of a platform fixed to a scope identifier must now be declared effect
`read-external`, whether or not an MCP front serves it (item 1; ADR-0046). v0.33.0 held only a
scoped MCP front to that, which left a direct `/acquire` of such a platform's `act` tool open.
- Version 33 lets a token step's assertion be signed by the service account credentials API, for a
  fixed delegated subject. The catalog ships two read-only bindings for it,
  `google-workspace-directory` and `google-workspace-reports` (item 2; ADR-0045).
- Version 34 lets the certificate form's client assertion be signed PS256 (item 3; the ADR-0027
  amendment).
- `adapter-gcp-asset` now reaches the platform's metadata server at its fixed link-local address,
  with the same client the token step uses (item 4).

The implementation rows are
[#526](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/526),
[#529](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/529),
[#530](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/530) and
[#532](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/532). Beside them:
- synthetic stream fixtures for the `microsoft-graph` binding

- an end-to-end test of `export --scope` on the PostgreSQL kind

## Compatibility

| With | What holds |
|---|---|
| An engine configuration | Versions 33 and 34 are added: `tokenStep.signedBy` and `subject`, and the path placeholders `{numericId}` and `{alnumId}` (33; item 2), and `tokenStep.assertionAlgorithm` (34; item 3). A configuration that loaded under v0.33.0 loads as before, except where item 1 refuses it at start. A member of version 33 or 34 is refused by name under an earlier version, and a v0.33.0 gateway refuses a file of version 33 or 34 by its number. |
| A PostgreSQL store of v0.33.0 (schema version 6) | Is served as it is. There is no migration, and the schema is unchanged. |
| The format | Unchanged: receipts, seals, registry lines and records are as in v0.33.0. |
| Older verifiers and the corpus | Unchanged. No vector is added or changed, and the verifiers of v0.33.0 verify what this release writes. |
| Receipts and stores written before this release | Keep their bytes and verify as before. |
| Judgment Pack Runner and other `/acquire` clients | Unchanged for a request that worked before against a started gateway. A gateway whose scoped platform has a live tool not declared `read-external` no longer starts (item 1). |

| The runtime in the engine image | Unchanged: the `Dockerfile` pins `0.46.0`, as in v0.33.0. The image and the release archives carry the changed `adapter-http` and `adapter-gcp-asset`. |
| PostgreSQL | 16 is the version tested, in CI's two `postgresql` legs. |

## Changes for operators upgrading from v0.33.0

1. **Breaking: a platform fixed to a scope identifier takes only live tools declared
   `read-external`, whatever the front** (#530; ADR-0046).
   - **The rule.** v0.33.0 held only a scoped MCP front to this (ADR-0044). Now each live tool
     of a platform with a `scope` declares effect `read-external` in every configuration,
     including one with no `mcp` member.
   - **What refuses.** Any other live tool (`propose`, `act`, or undeclared) stops `serve` and
     `gateway mcp` at start. `connect` will not write it, `connect --replace` included, since it
     keeps the `scope`. The tool is refused by name and is never quietly dropped from a source
     that starts. No engine configuration version changes: the rule applies to a file of any
     version from 20.
   - **The refusal** names no scope identifier. **Match it on its stable prefix,
     `platform <name>: tool "<tool>" is not declared effect read-external`**, not on the whole
     sentence. The prefix is v0.33.0's first clause. The rest of v0.33.0's sentence is replaced,
     so a match on the whole old sentence no longer matches.
   - If the tool only reads, declare it `read-external` (for instance `{"operation": "read",
     "effect": "read-external"}`) in the binding's `toolTaxonomies`, and approve the binding again
     with `connect --replace`.
   - Otherwise take it off the scoped platform. Either pin a binding whose live operation names
     only reading tools, or remove the platform's `scope`. Its receipts then carry no scope, and
     its callers must reach the sources of none. **The shipped `postgres` binding's
     `execute_sql` is an act, so a scoped postgres platform starts only under one of these two
     fixes.**
   - A platform of no scope identifier is unchanged, except behind `mcp.scopeFrom` (v0.33.0).
     Under `mcp.scope`, the platforms fixed to another scope identifier are now held as well.
   - The rule holds a declaration, not a behaviour: what keeps a `read-external` tool to reading
     is still its credential. The steps are in
     [`docs/design/engine-config.md`, "A platform's scope (engine version 20)"](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/v0.34.0/docs/design/engine-config.md#a-platforms-scope-engine-version-20),
     under "Live tools are reads".
2. **A token step signed by the credentials API for a delegated subject, at engine configuration
   version 33** (#526; ADR-0045). A token step may name
   `signedBy: {"kind": "credentials-api", "serviceAccount": "..."}`, with a fixed `subject` and
   `requestScope` and no `clientId`. It is exactly one of `signedBy`, `privateKey`,
   `federatedTokenFile` and `federatedToken`. The steps are in
   [`docs/design/engine-config.md`, "A token step with a delegated subject (engine version 33)"](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/v0.34.0/docs/design/engine-config.md#a-token-step-with-a-delegated-subject-engine-version-33).
   - **The flow.**
     1. The compute's access token from the metadata server, at ADR-0043's fixed address.
     2. `signJwt` at `https://iamcredentials.googleapis.com`, built in, for exactly `iss`, `sub`,
        `scope` and `aud`, with `exp` five minutes after `iat`.
     3. The JWT-bearer grant at the configured token endpoint.

     No key is read or held. The metadata token and the signed JWT stay in one run's memory, and
     the access token is sealed under the live credentials file's `sealKey`.
   - **The signed claims are read back exactly:** each of the six members by its exact name,
     once, and no other. A claim named in another case, a claim named twice, or one claim more
     is refused (#528, L1).
   - **Scopes and accounts.** Only the five read-only Admin SDK scopes are admitted; any other is
     refused by name. `admin.directory.user.security` is left out, with the tokens resource,
     since that scope also revokes tokens. Only a user-managed service account is accepted, not a
     default one.
   - **Path placeholders.** `{numericId}` (1 to 32 digits) and `{alnumId}` (1 to 64 lowercase
     letters and digits) join ADR-0040's `{id}`, which is unchanged, and a path holds at most one
     placeholder. An address is never a path segment; it goes in a query member.
   - **Catalog.** `google-workspace-directory` and `google-workspace-reports`, `GET` alone, each
     admitting exactly its read paths.
   - **Domain-wide delegation** acts as the subject over the whole domain, within the scopes the
     administrator granted. The binding narrows what is asked, not what the grant allows.
   - **The identity is the compute's, not the platform's user's.** Every process on that compute
     can ask the metadata server for the same access token and call `signJwt` as that identity,
     for any subject and any granted scope. The separation by the platform's user does not hold
     for this form (SECURITY.md; ADR-0045, consequences). Keep the delegation's scopes to the
     read-only list and the subject to an administrator whose role only reads.
   - **Failures.** Every failure is the no-credential sentence, and a 429 or 503 is ADR-0029's
     throttled answer. No token request follows a failure. When `HTTPS_PROXY` is set, the call to
     the credentials API goes through it, with TLS still to that host.
3. **PS256 for the certificate form's client assertion, at engine configuration version 34**
   (#529; ADR-0027, amendment). Beside `privateKey`, a token step may name
   `assertionAlgorithm`, `"RS256"` or `"PS256"`. `adapter-http --assertion-alg=PS256` signs
   RSASSA-PSS with SHA-256, MGF1 SHA-256 and a 32-byte salt.
   - **Without the member**, the algorithm is the key's, as before. RS256 signs byte for byte as
     before, and a version-33 file loads and derives its argv unchanged.
   - **Refused by name**, repeating no value: an unknown value, the member beside another kind of
     assertion, and the member below version 34.
   - **Either value beside a key that is not RSA** is no credential, before any token request, in
     a sentence naming the algorithm asked:
     - a P-256 key: `... is EC P-256, which signs ES256; --assertion-alg=<alg> is for an RSA key`;
     - an EC key on another curve: `... EC key is not on P-256; --assertion-alg=<alg> is for an
       RSA key` (#528, R2);
     - any other key: `... is neither RSA nor EC P-256; --assertion-alg=<alg> is for an RSA key`
       (#528, L6).
   - The token's seal is bound to the algorithm when one is asked.
4. **`adapter-gcp-asset` reaches the metadata server at its fixed address** (#532). Its
   `metadata` token source asked `http://metadata.google.internal`, so a resolver chose the
   address. It now asks `169.254.169.254`, with the client the token step uses
   (`adapters/internal/metadataclient`). That client:
   - uses no proxy;
   - refuses any other address at dial, and makes no client for a base that is not an IP literal
     over http;
   - follows no redirect, and bounds the header.

   **One tightening:** an answer carrying `Metadata-Flavor` twice is now refused, as one without
   it is, with the same kind and sentence. Scopes, failure kinds and the 64 KiB body bound are
   unchanged.

   **A metadata emulator reached by a name no longer works.** One that a hosts file or DNS
   entry for `metadata.google.internal` pointed at is not asked, since the address is pinned
   to `169.254.169.254`.
5. **Tests and data only:**
   - **Stream fixtures** (#527): `testdata/microsoft-graph-streams/` holds 14 synthetic streams of
     two pages each, and four case files: an expired delta token, a throttled answer, an
     unlicensed answer and a present-but-empty stream. `go/graph_streams_test.go` drives them
     through the gateway with the shipped `microsoft-graph` binding. Every name, id and host is
     invented.
   - **`export --scope` on PostgreSQL** (#531, tightened in #528): the export of one scope's
     sessions, its two refusals, and a restore that verifies by the scope as the store does.
   - **`connect`'s hint names the placeholder's own version** (#528, R1). A binding with a
     `{numericId}` or `{alnumId}` template, such as `google-workspace-directory`, refused under an
     earlier file now says to raise `engineVersion` to `"33"`, not `"31"`.
   - **Carried LOWs** (#528): the seal-tamper helper flips a middle byte, so a test never
     rewrites base64 padding into the same bytes. The RS256 pin's hand-built check no longer
     depends on the capture. The comments on the service-account form and on the proxy are
     corrected.

## Decisions

- **ADR-0045** (#526): a token step's assertion signed by the credentials API for a fixed
  delegated subject; engine version 33.
- **ADR-0046** (#530): a scoped platform's live tools are declared `read-external`, whatever the
  front. It supersedes ADR-0044's decision 5 sentences on a configuration with no `mcp` and on
  another scope identifier's platforms, widens its decisions 1, 2 and 4, and needs no engine
  version.
- **ADR-0027, amendment** (#529): PS256 for the certificate form's client assertion; engine
  version 34.

ADR-0045 and ADR-0046 are accepted (autopilot; the maintainer may revise), as their records and
the index say. ADR-0027, amendment included, stays `proposed`, as its record says.

## What this release does not establish

- That anything of version 33 meets the live services as the stand-ins do. Every test runs
  against in-process stand-ins for the metadata server, the credentials API and the token
  endpoint. Two assumptions stand: that `signJwt` returns the payload unchanged, and that group
  ids are lowercase letters and digits.
- That PS256 is taken by the live identity platform.
- That a `read-external` tool only reads: the rule holds its declaration, and the credential holds
  the behaviour (item 1).
- That a refused `401` or `403` tells why: it is still a `400` whose sentence carries the status.
  A fixed answer carrying the endpoint's error code from a closed list is planned for the next
  release (#524, with #514).
- Federation, throttling of the list call and refresh failures stay in #492.
- Of the open items v0.33.0 listed, #440, #444, #447, #474 and #450 stand. #519 is closed by
  #530.
