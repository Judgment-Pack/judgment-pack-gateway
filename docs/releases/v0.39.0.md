# v0.39.0 (draft)

This draft is started from ADR-0054's "What the release notes must say". It states what is built so
far; the item under "Not yet served" lands with the specification release and is listed so that it
is not left out of the final notes.

## Built

- **Approval citations in the format.** An action receipt may carry `action.approvals`, 1 to 8
  `{kind, id, digest}` entries, `kind` `"single"` or `"standing"` (SPEC.md §1.2a). Each entry is the
  requester's claim, checked for form only. v0.38.0 verifies such a receipt `ok` and shows no
  approvals.
- **The dry-run receipt** (SPEC.md §1.2c) is signed under `judgment-pack-gateway/dry-run/1:` and is in
  no session and no store. It is checked with `gateway verify-dry-run` or verify-ts's `verifyDryRun`,
  whose reports carry `dryRun: true`. Every receipt verifier, including v0.38.0, calls it `malformed`.
  It says nothing about the action key.
- **The new observation is `approval-cited-again`**, on an action receipt that cites a single approval
  another action receipt of the store also cites.
- **The read-back scope check.** A read-back resolves its action only where both carry the same
  `scope`, or neither does; otherwise `action-reconciliation-unresolved`. v0.38.0 does not make this
  check, and no gateway mints such a pair.
- **Corpus.** Ten `v3/stores` vectors for approvals and a new `dry-run` family of eight vectors, each
  recording v0.38.0's verdict.

## Built: `/act` takes a scope identifier

- From engine version 43 (`actScopeVersion`), a platform may set `scope` with
  `write: true`. It then needs `identity.callerScopes` as an object and its own `decisionRecords`,
  apart from the gateway's and from every other scope's. `/act` then takes `scope` as `/acquire`
  does, and its receipts carry `scope` and `scopeSalt`. A configuration of that version is refused
  by an earlier release.
- A scoped action's key is a different key from the same key in another scope or in none. It is
  kept in its scope's own journal, `actions/scopes/<hash>/`. A re-created scope starts with no keys.
  `remove-scope` refuses, naming each key, while a key there is pending, and removes the scope's
  journal after its sessions.
- A scoped action cites only receipts of its own scope, and finds its decision record in its
  platform's directory alone. `/verify` looks for that record in its scope's directories alone.
- `gateway journal compact` compacts each scope's journal by the same rule as the journal of none.
- `/act` has a body-level `scope-identifier` refusal that answers `400`. The pre-body
  `scope-identifier` keeps its `403`.
- An action receipt of no scope, and the journal of no scope, are byte for byte as before.
- **Changed for `/acquire`:** into a session this gateway holds of another scope, or of none, it now
  answers the other-scope sentence even when that session is sealed, where it answered `session is
  sealed` before. `/act` answers the same way.
- **Corpus.** `v3-action-scope-valid` and `v3-action-scope-seal-mismatch`; four read-back scope
  vectors; five malformed approvals vectors; and two dry-run vectors, `version-missing` and
  `version-two`.

## Built: the dry-run and approvals on `/act`

- From the same engine version, `/act` takes `"dryRun": true` and answers `{dryRun, request, salts}`,
  with no `receipt`. A dry-run runs the write's checks, signs a dry-run receipt under the serving key
  and sends, reserves and records nothing: no key, label, session directory, sink delivery, dispatch
  marker, grant use or executor. Under a delegation its admission read is at `"count": false`. Under a
  key service each dry-run is one signing call. It says nothing about the action key.
- While the session holds a receipt the receipt sink has not acknowledged, a dry-run is refused as
  the write is, `503` with the same code and sentence. The dry-run reads the held receipt and does
  not send it.
- `/act` takes `approvals`, which the receipt carries as `action.approvals`. Each entry is the
  requester's claim, checked for form only.
- A key reserved with approvals records identity version `"3"`, and replaying a key with other
  approvals than it was reserved with, or with approvals where it was reserved with none, is
  `action-key-conflict`. A key reserved with no approvals is the same journal bytes as before.
- A key reserved by an earlier release and replayed with `approvals` is `action-key-conflict`, because
  a request with approvals has no version 1 identity. It fails closed: nothing is sent.
- A key reserved with approvals is refused `action-journal-invalid` by an earlier release. Settle such
  keys before a rollback.
- `/act` has new `refusedAt` values, `dry-run` and `approvals`.

## ES256 delegation statements

Part of spec RFC 0030's amendment of 2026-11-22 (*Signing with a P-256 key*). It takes one engine configuration version, 41 (`delegationP256Version`), and no PostgreSQL migration.

- **The statement.** A delegation statement a P-256 key signs holds `alg: "ES256"` inside what it signs and digests, and its signature is `r||s` at low S. A statement an Ed25519 key signs is unchanged, byte for byte. The gateway verifies each link by the algorithm its `alg` names, under a key pinned with that algorithm, so a chain may mix the two link by link (SPEC.md §11.1).
- **The refusals** are the existing names: an `alg` other than the string `"ES256"`, and a DER-encoded signature, are `malformed`; a high-S signature is `signature-mismatch`; a link whose `keyId` names a pinned key of the other algorithm is `key-mismatch`.
- **The pin** (engine version 41): `delegation.hosts[].keys` takes `{"alg": "ES256", "key": <66 lowercase hex>}` for an issuing host's P-256 key, beside Ed25519 keys as strings, as `retention.acknowledgedBy` does. A bare 66-character string is refused, naming both forms; an unsound point is refused as `is not a sound P-256 public key`; before version 41 the object is refused by name (SPEC.md §11.2).
- **The cases.** `testdata/delegation/es256-statements.json` is a byte-for-byte copy of the spec repository's `conformance/delegation/es256-statements.json`: 55 cases of the amendment's tables 1 and 2, made once by Python's `cryptography` 44.0.0, independent of this repository, and frozen. The 39 Ed25519 cases of `testdata/delegation/statements.json` pass unchanged.

### ES256: what changes at every version

- A statement holding a top-level `alg` other than the string `"ES256"` was tolerated and signed with the rest; it is now `malformed`, as the RFC states.
- An Ed25519-signed statement holding `alg: "ES256"` verified before; it is now `key-mismatch`.

A statement that holds no `alg` keeps its verdict.

### ES256: upgrade

Upgrade the gateways before an issuing host signs with a P-256 key, then pin the host's P-256 key at version 41 beside its Ed25519 key, and only then let the host sign with it. An earlier gateway refuses every ES256 link `key-mismatch`, and a version-41 file by its version.

## A key history that marks each store continuation (ADR-0055, #578)

- **Default unchanged.** `/publickey/history` answers version `"1"`, byte for byte as before, unless
  `keyHistoryVersion: "2"` is set in an engine configuration of version 42. Every version `"1"` history,
  carried `.key-history` file, `gateway.key_history` row and `keyHistoryDigest` verifies as before.
- **Version `"2"`.** The answer lists the history one store at a time; each store after the first carries
  its registry's store continuation line, signed as it is, naming the history before it by
  `keyHistoryDigest`. A consumer refuses a rotation given twice or passed over from the history alone.
- **Upgrade every reader first.** v0.38.0 refuses version `"2"` in two places. A consumer of v0.38.0 or
  earlier refuses a version `"2"` answer whole. A gateway of v0.38.0 on a store that carries a version
  `"2"` history answers `500` at `/publickey/history`, and refuses `rotate-key`, its SIGHUP form,
  `store rotate-key` and `store rotate`, until it is upgraded again. Operators therefore upgrade every
  reader before opting in.
- **No way back after a store rotation.** A store's key-history version only moves forward. Once a store
  rotation carries a version `"2"` history, that store and every store after it answer `"2"` whatever the
  configuration says, with the member removed too.
- **Several instances on one database.** Set the member on every instance before rotating. Until the
  first continued rotation an instance that has not opted in answers `"1"`, which is still valid for that
  store; nothing refuses the mixed state.
- **`base`.** A version `"2"` history that continues a version `"1"` one carries it as `base`. Inside
  `base`, ordinals are still held to their form alone.
- **verify-ts gains a key-history check.** `checkKeyHistory(bytes, pin, {requireVersion})` checks both
  versions and is exported beside the store verifier. The Go check and verify-ts name the same eight
  refusal classes, which the corpus compares.
- **`requireVersion: "2"`.** A consumer can set it to refuse a version `"1"` answer. Set it only once the
  gateway answers `"2"` and the member stays.
- **Store the version beside the pin.** A consumer keeps the version of the last history it accepted
  beside the key it pins. Once it has accepted `"2"`, it sets `requireVersion: "2"` from then on, so a
  later answer of version `"1"` is refused rather than checked under the older rule.
- **Opting in at a store rotation.** `gateway store rotate` given by its flags carries `"2"` only where the
  old store already does. To opt in at the rotation, give `--config`. The flags name no
  `keyHistoryVersion`, so a rotation by flags of a store whose configuration names `"2"` still carries a
  version `"1"` history while the old store's is `"1"`. stderr says so after such a rotation.
- **Size.** The answer grows by about 1 KiB per store rotation.
- **Corpus.** A verify-only family, `corpus/key-history`, of 29 vectors, and corpus rotation key 3,
  published by the existing seed rule.
- **Not established.** Neither version shows that a continuation's `previousLines` and `previousDigest`
  name the real old registry (`gateway verify --previous` holds that), that there is no fork by a key
  holder, or that the answer holds the latest rotation.

## Per-scope request limits (ADR-0057, #507)

- From engine version 44, a top-level `limits` member sets, for each scope identifier, for
  `"unscoped"`, or by `default`, a request rate (`requestsPerMinute`, `burst`), a cap on requests in
  flight (`inFlight`), and the same for each caller within the scope (`perCaller`), beside one
  gateway-wide cap on the requests not yet tied to a scope (`beforeScope`, 1024 when left out).
  Without it, nothing changes.
- `/acquire`, `/act` (dry-runs included), `/seal` and `/verify` may answer `429` with `Retry-After`
  and `{"error", "code": "limit_reached", "limit"}`, and `/act` with `"refusedAt": "limit"`. Every
  route but `/publickey` and `/publickey/history` may answer `429` `gateway-in-flight` while the
  gateway-wide cap is full; `/registry` among them. The sentence is fixed, and `Retry-After` comes
  from the caller's own scope, or from the gateway-wide cap where that refused. Nothing is minted,
  journaled or forwarded for such an answer.
- A request holds a gateway-wide slot only until its token is read, never across its body. `/verify`
  from a caller of several scopes is charged to every scope it reaches, all or nothing.
- The limits are counted by each instance alone, in this release. N instances admit up to N times
  each limit, so an operator running several instances sets each limit divided by N. Shared
  counting is gateway #593 (v0.41.0).
- `/act` is still `501` on the PostgreSQL kind. Its count applies there once it is served.
- A delegated request, and a reservation sender, are counted in `"unscoped"`, each by its own sender.
- `/posture` adds `request-limits` and `limits`, judged over the caller's own scopes, and
  `unauthenticatedRefusals`, the count of requests refused at the gateway-wide cap or answered `401`,
  given to every caller.
- The limits bound one scope's effect on another. They do not remove it.
- `perCaller` needs an identity, and a `scopes` key must name a configured scope.
