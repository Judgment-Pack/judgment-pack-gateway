One change. The registry writer now reads the registry the way the verifier reads it when it decides whether a session is already sealed, so a stray registry line naming a session no longer leaves that session unsealable. A gateway configured as before keeps its receipts, its registry and its policies, and nothing that started under `v0.9.0` refuses to start.

## What an operator must do

- **Nothing.** No configuration, policy, receipt or registry format changes, and no start-up check is added.
- **If a registry holds a stray line naming a session** (a seal whose signature does not verify, a seal under a `keyId` that is not this gateway's, or a line missing a member), `/seal` for that session now answers `200` with the seal, where `v0.9.0` answered `400 session already sealed`, and `/verify` then grades the session as sealed. The stray line stays where it is; the new seal is appended beside it. A session whose seal loads is still refused a second seal.

## Seal a session that only a discarded registry line names, as the verifier reads it (#208, closes #138)

Before this release, `registryWriter.seal` refused `session already sealed` when any registry line parsed as a JSON object whose `sessionId` was the session, reading neither its `keyId` nor its signature. The specification loads a seal only when its `keyId` is the gateway's own and its signature verifies under the gateway's key (§4 step 2), and says a discarded line establishes no seal for `/acquire` (§6). So a stray line naming a session left it permanently unsealable, and `/verify` reported it `unregistered-session`, the verdict it gives a session that was never sealed at all.

- **The writer reads with the verifier's loader.** It refuses a second seal only when a seal for the session loads. There is no second reader to diverge: `splitLines` and `trimSpace`, which only the writer used, are gone.
- **§3 states it.** A session is already sealed when the registry holds a seal for it that §4 step 2 loads; a line that names the session and is no such seal establishes no seal for `/seal` either, as it establishes none for `/acquire`; the gateway appends the new seal beside that line and answers `200` with the seal record, and §4 step 2 loads the new seal, since it is the session's first seal that loads.
- **Tests** hold four discarded-line shapes over HTTP (a bad signature under the gateway's own `keyId`, a foreign `keyId` signed by the gateway's key, another gateway's real seal, and a seal with no signature member), each guarded so that the line parses, names the session and is not loaded; and the reseal of a session whose only seal is whole but for its trailing newline, which is still refused.

What it establishes: the writer and the verifier agree on what a seal is. What it does not: appending a stray line needs write access to the registry, and anyone with that access can already truncate the registry, which the gateway refuses to run past (§3), so this release adds and removes no capability against such a writer. It aligns the reference with the specification.

## Verification

CI ran the Go suite on Linux, macOS and Windows, the adapters, the engine image, the release-contents check, both plugins and `verify-ts`, and `gateway conform` reported no disagreement with the corpus.

- **Mutation checks:** eight single-change variants of the writer and the loader, each caught by a named test; the record is in the pull request.

Not exercised: a registry written by a gateway earlier than `v0.2.0`, which this gateway reads but did not write.
