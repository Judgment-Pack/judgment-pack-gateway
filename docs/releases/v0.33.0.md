# v0.33.0

This release closes what one scope identifier could learn of another through a shared gateway,
and adds three engine configuration versions. **It has one breaking change:** an MCP server that
names `mcp.scope` or `mcp.scopeFrom: "caller"` now serves only live tools declared effect
`read-external`, and refuses to start otherwise (item 1). The disclosures closed are the MCP
listing, `/seal` through a front fixed to one scope identifier, and `/posture` (#483, #494;
ADR-0041). A seal of a scope identifier's session is now of version 3: it names the scope over a
salt the session's receipts carry and the registry does not hold, so the open registry alone
tests no guessed identifier (ADR-0042). Version 30 lets a `gcp-asset` source resolve grants
through groups, opt-in and bounded (ADR-0039, third Amendment). Version 31 lets an `http` source
bind path templates and follow the links an endpoint hands out, and the catalog ships one
read-only binding, `microsoft-graph` (ADR-0040). Version 32 lets a token step's federated token
come from the platform's metadata server (ADR-0043). `gateway verify` and `gateway export` select
one scope identifier's sessions, and verify-ts's `verify` does as well (#478). The implementation
rows are
[#509](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/509),
[#499](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/499) (its design,
[#498](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/498), changed no code),
[#511](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/511),
[#518](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/518),
[#520](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/520),
[#512](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/512) and
[#521](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/521). Beside them: a test of
the MCP front's caller scopes
([#517](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/517)), a guide to a seed on
a read-only secret mount
([#515](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/515)), a faster CI for pull
requests ([#497](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/497)), and the review
LOWs this release carried.

## Compatibility

| With | What holds |
|---|---|
| An engine configuration | Versions 30, 31 and 32 are added: `groups` on a `gcp-asset` live operation (30; item 4), a path template in an `http` binding's `paths` (31; item 5) and `tokenStep.federatedToken` (32; item 6). A configuration that loaded under v0.32.0 loads as before, except where item 1 refuses it at start. A member of version 30, 31 or 32 is refused by name under an earlier version, and a v0.32.0 gateway refuses a file of version 30, 31 or 32 by its number. |
| A PostgreSQL store of v0.32.0 (schema version 6) | Is served as it is: no migration, and the schema is unchanged. Neither the schema's definitions nor its migration code differ from v0.32.0, and ADR-0042 states no schema change. But once this release writes a seal of version 3, no gateway of v0.32.0 or earlier may run on the store (item 2). |
| The format | Receipt versions 2 and 3 are unchanged. A receipt of version 3 of a session of a scope identifier carries the optional member `scopeSalt` (SPEC.md §1.2a), under its signature. A **seal of version 3** is added (SPEC.md §3 and §3c): the gateway of this release writes it for a session of a scope identifier whose receipts carry a salt, and for that session's seal after an interruption. It writes a seal of version 2 only for a session whose receipts an earlier release minted, which carry none. A seal of version 2 already written verifies as before. A session of no scope identifier is sealed as before, byte for byte. A `session-removal` record of a session sealed with version 3 carries the salt as a tenth member. A request to an `http` source by `link` is committed to by the statement `{"method","path","rawQuery"?,"body"?}`; a request by `path` is as before (item 5). |
| Older verifiers | The Go verifier and verify-ts of v0.31.0 and v0.32.0 tolerate `scopeSalt` in a receipt but load no seal of version 3 and reject a `session-removal` record of ten members. For a session the store holds, they report `unregistered-session`: they fail closed. For a session removed from the store they fail open: they load no seal naming it and find none of its receipts, so a store holding nothing else they refuse is `ok` to them (ADR-0042). Give the store's readers this release's verifiers. |
| The corpus | 24 vectors are added to `v3/stores` (164 to 188): `v3-scope-salt-*` (5) and `v3-seal-salted-*` (19), signed by a signer written from SPEC.md alone. 15 more are added for a verdict by scope (188 to 203): `v3-cut-*`, each with a `scope` the runner passes as `--scope` and a `cut` in `expected`, one of them a session of the scope whose receipt's signature does not check. The expected answers of the earlier vectors are unchanged. |
| The Go verifier and verify-ts | Both read seals of version 3 and receipts that carry `scopeSalt`, and agree on every vector. Both take `--scope` (item 7), and verify-ts's corpus test replays all 203 stores with it. |
| Receipts and stores written before this release | Keep their bytes and verify as before. |
| Judgment Pack Runner and other `/acquire` clients | Unchanged for a request that worked before, with four exceptions. A query object's `$` reaches an `http` source's endpoint as `$`, where it was `%24` (item 5; every `http` source, whatever its engine version). `/seal` takes an optional `scope` member, read where `/acquire` reads it, and answers a session of another scope identifier, or of none, `no such session` when it is named (item 3). `/posture` is judged over the sources a caller reaches (item 3). A request may name `link` in place of `path` and `query` (item 5). |
| MCP clients | A scoped front that serves a live tool not declared `read-external` does not start (item 1). A caller's listing is made from the platforms it reaches, bounded as that caller alone would be, so it is the same whatever another scope identifier holds (item 3). |
| The runtime in the engine image | Unchanged: the `Dockerfile` pins `0.46.0`, as in v0.32.0. The image and the release archives carry the changed `adapter-gcp-asset` and `adapter-http`. |
| PostgreSQL | 16 is the version tested: CI runs PostgreSQL 16.15 pinned by digest, in two legs (item 9). |

## Changes for operators upgrading from v0.32.0

1. **Breaking: a scoped MCP front serves only live tools declared `read-external`** (#520; ADR-0044).
   An MCP server that names `mcp.scope` or `mcp.scopeFrom: "caller"` serves only live tools
   declared effect `read-external`. Any other live tool it would serve (`propose`, `act`, or
   undeclared; under `scopeFrom`, platforms of no scope identifier included) refuses `gateway mcp`
   and `serve` at start, and `connect` refuses to write it. The refusal reads `platform <name>:
   tool "<tool>" is not declared effect read-external, ...`, and names no scope identifier.
   - If the tool only reads, declare it `read-external` (for instance `{"operation": "read",
     "effect": "read-external"}`) in the binding's `toolTaxonomies`, and approve the binding again
     with `connect --replace`.
   - Otherwise take it off the scoped front: pin a binding whose live operation names reading
     tools alone, or serve the platform with no scope identifier behind an `mcp` of neither form.
     A shipped binding whose live operation names an act (the postgres binding's `execute_sql`) is
     not served by a scoped front at all.
   - A front of neither form, and a configuration with no `mcp`, are unchanged. The rule holds a
     declaration, not a behaviour: a tool declared `read-external` that writes is served, and what
     keeps it to reading is the credential the operator gives it. It is the front's rule: a
     direct `/acquire` of a scoped platform's live act tool, in a configuration with no `mcp`, is
     not held here (#519). The steps are in
     [`docs/design/engine-config.md`, "The MCP server on scoped platforms (engine version 28)"](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/v0.33.0/docs/design/engine-config.md#the-mcp-server-on-scoped-platforms-engine-version-28),
     under "Upgrading".
2. **Seals of version 3: no going back, and no older verifier** (#518; ADR-0042).
   - A seal of version 2 names its session's scope by an unkeyed digest over the identifier and
     the session id. `/registry` is open, so anyone who guessed an identifier could test it against
     every such seal. From this release a session of a scope identifier carries a per-session
     `scopeSalt` of 32 random bytes in each receipt, and its seal of version 3 takes the digest
     over the salt, the identifier and the session id. The salt is in no registry line, so the
     registry alone tests no guess, and two sessions of one scope have unrelated digests. A holder
     of the session's receipts still checks the seal's scope with the public key alone.
   - Seals of version 2 already in a registry stay testable by a guess: that cannot be undone
     without rewriting signed history. Keep to identifiers of at least 128 bits of entropy
     (SPEC.md §6).
   - Stop every v0.31.0 and v0.32.0 instance before the first instance of this release serves,
     and do not start one again on the store afterwards
     ([`docs/postgresql-store.md`, "Several instances on one database"](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/v0.33.0/docs/postgresql-store.md#several-instances-on-one-database)).
     The schema is unchanged, so it does not refuse an older instance; an older gateway reads no
     seal of version 3. Give the store's readers this release's verifiers: see "Older verifiers"
     above for what the earlier ones make of it.
   - `gateway seal-open` seals a session whose receipts carry a salt with version 3, and one whose
     receipts an earlier release minted with version 2. `gateway remove-scope` takes the salt from
     the session's receipts, on both storage kinds.
3. **What one scope learns of another, closed on three surfaces** (#509; #483, #494; ADR-0041).
   On a gateway shared by callers of different scope identifiers, a caller of B is answered the
   same whatever A holds.
   - **The MCP listing** in the caller form: each scope identifier's platforms, and the platforms
     of none, are bounded on their own at start, within 8 MiB each, and each caller's listing is
     assembled from the platforms it reaches. A caller reaching several scopes can be listed
     fewer descriptions than each scope alone is. The server holds up to (the number of scope
     identifiers + 1) x 8 MiB of described entries, with no cap of its own.
   - **`/seal`** takes an optional `scope` member, read where `/acquire` reads it, where some
     source is fixed to a scope identifier; elsewhere it is refused as a member `/seal` does not
     read, and a `scope` that is not a string is refused `400`. A session of another scope
     identifier, or of none, is answered `no such session: <id>`. A front fixed to one scope
     identifier names it on every seal it forwards. A session this process does not hold that is
     sealed in the registry is still said to be sealed, to every caller, since `/registry` shows
     that seal to anyone.
   - **`/posture`**, served to a caller that does not reach every source, judges every line over
     the sources the caller reaches: its state, its counts and the sources or platforms it
     names. The installation's caller, `"unchecked"`, and a gateway without `identity` are
     answered as before. A host's `gateway posture` reads the whole.
   - **Unchanged:** the seal's signed form (but for item 2), registry lines and the store layout.
     SPEC.md §6 and §11.9 and the posture design doc say so.
4. **Grants through groups, at engine configuration version 30** (#499; ADR-0039, third
   Amendment, designed in #498). Nothing changes until it is configured; a source that does not
   opt in keeps its command line and its start lines. The steps are in
   [`docs/design/engine-config.md`, "Grants through groups on a gcp-asset source (engine version 30)"](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/v0.33.0/docs/design/engine-config.md#grants-through-groups-on-a-gcp-asset-source-engine-version-30),
   and the adapter's flags in
   [`adapters/README.md`, "Grants through groups"](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/v0.33.0/adapters/README.md).
   - Raise `engineVersion` to `"30"` and add `groups: {"resolve": true, "depth"?, "members"?,
     "unresolved"?}` to the live operation. `depth` is 0 to 4 (default 2), `members` 1 to 50 000
     (default 5 000), `unresolved` is `"serve"` (default) or `"refuse"`. At most 64 groups are
     read, in at most half of the adapter's `--timeout` and 10 seconds. Under version 29 or
     earlier the member is refused by name.
   - Each `group:` member of a binding whose role is outside the read-only list, on an
     `IAM_POLICY` page, is resolved with `groups.lookup` and `groups.memberships.list`, breadth
     first, through a third token of scope `cloud-identity.groups.readonly`, held sealed beside the
     list token. A group the source's principal is found in refuses `credential-bound-at-resource`
     and closes the source, as a direct grant does. **Let the principal view the memberships of the
     groups that matter**: the gateway neither grants nor verifies that, and the third token's
     read-only property rests on its scope alone, since no write check covers the directory.
   - A group read whole is resolved. Anything else leaves it unresolved by one reason, and the
     page is served with the unresolved count reported, or, under `"refuse"`, the acquisition
     fails as a failed source with `group-unresolved` and the source is not closed. No group's
     name, email or member leaves the adapter.
   - **`/posture`**: each `readOnlySources` entry gains `groupBindings` (`off`, `checked`,
     `unchecked`), `groupsUnresolved` and `groupReason`, on every source, `off`, `0` and `null`
     where it does not opt in. `unchecked` lasts until the engine restarts, and
     `read-only-credentials` is `partial` while any source is unchecked; its counts cover the
     sources the caller reaches.
5. **Path templates, links, and a read-only `microsoft-graph` binding, at engine configuration
   version 31** (#511; ADR-0040). The steps are in
   [`docs/design/engine-config.md`, "Path templates and links on an http source (engine version 31)"](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/v0.33.0/docs/design/engine-config.md#path-templates-and-links-on-an-http-source-engine-version-31),
   and the binding in
   [`catalog/README.md`, "microsoft-graph"](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/v0.33.0/catalog/README.md#microsoft-graph).
   - **A path template** carries one `{id}`, a whole segment, which a request's path fills with a
     GUID (8-4-4-4-12 hexadecimal digits, either case) and nothing else. Two placeholders, `{id}`
     within a segment, any other brace and a templated `checkPath` are refused when the binding is
     loaded, and a template under version 30 or earlier is refused by name at the start and at
     `connect`, which does not raise the version.
   - **A link**: a request may name `{"link": "<absolute URL>", "method"?, "body"?}` in place of
     `path` and `query`. It is sent only when its scheme, host and port are the endpoint's, it
     carries no user and no fragment, and its path has no percent sign, backslash, dot segment or
     empty segment and is one the binding admits; its path and query are sent byte for byte. Each
     refusal is one fixed sentence that names nothing of the link. A link is no configuration
     member, and no version gates it. For a source with a token step the engine refuses such a
     request before it obtains a token.
   - **`$` in a query object is sent as written, not as `%24`**, so OData system options reach the
     endpoint by name. This holds for every `http` source and is gated by no version. The
     statement, which records the object, is unchanged, and the receipt's adapter digest is what
     fixes the bytes. An endpoint that told the two apart would see another request.
   - **`microsoft-graph`**: `GET` alone, 24 v1.0 paths of which four are templates, the bearer
     from a token step. What it may read beyond that is the permissions the operator grants the
     application the token step signs in as; the binding names none. Pinning it needs engine
     version 31.
6. **A token step's federated token from the platform's metadata server, at engine configuration
   version 32** (#512; ADR-0043). In place of `privateKey` and `federatedTokenFile`, a token step
   may name `federatedToken: {"kind": "metadata", "audience": "..."}`; exactly one of the three.
   The steps are in
   [`docs/design/engine-config.md`, "A live operation's token step (engine version 21)"](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/v0.33.0/docs/design/engine-config.md#a-live-operations-token-step-engine-version-21).
   - At each token request `adapter-http` asks the metadata server at the link-local address
     `169.254.169.254`, an IP literal built into it. No configuration member, flag or environment
     variable names an address, and no resolver or proxy is used. The answer is taken only with
     `Metadata-Flavor: Google` exactly once, no redirect, status 200, at most 16 KiB, a compact
     JWS whose `aud` is the audience and whose `exp` is more than 60 seconds ahead. The claims are
     read, not verified; the token endpoint verifies the token. The audience is 1 to 256 ASCII
     letters, digits and `.` `_` `~` `:` `/` `@` `-`.
   - The identity token is held in the adapter's memory for that one request and written nowhere.
     The signer still holds the access token, sealed, as before. **The live credentials file now
     holds `sealKey`, at least 32 bytes**, the key that seal uses; a missing or short one is refused
     by the adapter at the source's first acquisition or `--check`, not at load.
   - Any failure to get the token is the fixed no-credential sentence and no token request is
     sent; a `429` or `503` that carries the flavor header is a throttled answer.
   - **The identity token is the compute's, not the platform user's.** Every process on the
     compute can ask for one, so the separation by the platform's user that the file form has does
     not hold for this credential. A deployment that needs it keeps `federatedTokenFile`.
     IPv6-only compute is not served. Off a cloud host, anything on the link can answer at that
     address with the header and a well-formed token, and only the token endpoint's verification of
     the token stops it.
7. **`gateway verify --scope`, `gateway export --scope` and verify-ts's `verify --scope`**
   (#521; #478).
   - `verify --scope S` runs the whole verdict, then attributes every session by what the gateway
     signed: a seal of version 3 through the salt the receipts carry, a seal of version 2 by
     recomputing its digest. A session that cannot be attributed is named in `cut.unattributed`,
     its findings are reported, and the verdict is not `ok`.
   - `export --scope S` writes S's sessions, their artifacts, the removal records, and, from the
     registry, the rotation statements and S's lines. It refuses by name an unattributed session,
     a registry walk with a finding, a session of S holding receipts an earlier release minted
     (of another scope or none), and a session of S holding a receipt file that fails one of the
     first six orders of SPEC.md §1.4. It writes each receipt's bytes as it checked them, and takes
     an artifact only from what the gateway signed (a receipt's `resultDigest` and its descriptor
     provenance), never from what a source reports. It carries nothing of another scope beyond
     the key's rotations.
   - Completeness rests on the exporter's attribution: a reader holding the registry can bound it
     but cannot close it (SPEC.md §4, §5a and §7; ADR-0042, decisions 6 to 9).
   - The PostgreSQL legs and both Windows shards passed on #521. The export by scope reads each
     storage kind through that kind's cut, the one the whole-store export takes; its own tests
     run on the filesystem kind, and no test yet runs an export by scope end to end on the
     PostgreSQL kind.
8. **A seed on a read-only secret mount** (#515). A guide, with no behaviour change:
   [`docs/seed-from-a-secret-mount.md`](https://github.com/Judgment-Pack/judgment-pack-gateway/blob/v0.33.0/docs/seed-from-a-secret-mount.md).
   `serve` still refuses a seed that is not the gateway's own user's private file; the supported
   practice is to copy the mounted seed at start into a private file on an in-memory volume that
   user owns, and to point `seed` at the copy.
9. **Tests, CI and the carried LOWs.**
   - #517 adds a test of the MCP front's caller scopes over an operator's read-only tool servers.
   - #497 changes CI only: macOS is off the pull-request and merge-group path, and runs on a push
     to main and nightly; the check list runs in two lanes, Windows tests in two shards, and
     PostgreSQL in two legs, superuser and non-superuser. A release takes the push to main's
     evidence (docs/releasing.md).
   - The review LOWs carried into this release: the seed guide says `/run/gateway` is an example
     on an in-memory volume the platform provides, and `/run` may be neither; the caller-scope test
     puts the other caller's scope in every tool's arguments and under `io.judgment-pack/scope` in
     `_meta`, and changes one tool's effect to show the refusal is that tool's; a test holds that
     `connect --replace` refuses an act live tool behind a front fixed to a scope, not only under
     `scopeFrom: "caller"`.
   - SECURITY.md gains "What holds between scope identifiers on one gateway, and what does not":
     what a caller reaches, what ADR-0037, 0041, 0042 and 0044 hold, and what does not (one
     process, key, store and registry, no limit per identifier, the shared session namespace, a
     direct `/acquire`). Its sentence on a platform's `scope` now says the identifier authorizes a
     caller where `identity.callerScopes` is checked, and is a label where it is not.

## Decisions

- ADR-0039, third Amendment (#498, built in #499): grants through groups on a `gcp-asset` source,
  opt-in and bounded, from the source's own third token; unresolved groups are reported, never
  read as read-only; engine version 30.
- ADR-0040 (#511): path templates a GUID fills, and links held to the endpoint and the paths
  before a connection; engine version 31.
- ADR-0041 (#509): a caller of one scope identifier is answered the same whatever another holds,
  on the listing, `/seal` and `/posture`; the session namespace stays shared, recorded.
- ADR-0042 (#518, and #521's decisions 6 to 9): a seal names its scope over a salt the registry
  does not hold; a verdict and an export by scope.
- ADR-0043 (#512): a token step's federated token from the platform's metadata server, at a fixed
  address; engine version 32.
- ADR-0044 (#520): a scoped MCP front serves only live tools declared `read-external`.

Each is accepted on merge (autopilot; the maintainer may revise), as its record and the index say.

## What this release does not establish

- That a scope identifier cannot be told apart by another: the session namespace is shared, so a
  caller can learn that some other scope, or none, holds a session of a name it guessed, and by
  the time `/seal` takes. Choose session ids and identifiers of at least 128 bits (ADR-0041,
  decision 4).
- That a seal of version 2 already written hides its scope (item 2).
- That a direct `/acquire` of a scoped platform's live act tool, with no `mcp` member, is held to
  reads (#519).
- That a credential is read-only in every respect, and that groups resolve as expected: a 403 is
  not a filtered subset, the page bound of the full membership view, the forms of the lookup's 404
  and 403, whether the basic view omits a member's type, and the third token's scope from metadata
  and key have not been confirmed in a live run (ADR-0039, G9). Nesting past the depth, `domain:`
  grants, principal sets and pools, groups the credential cannot read, and asset types the source
  does not serve stay outside.
- What `microsoft-graph` meets in a live service: the certificate assertion (PS256 is asked, RS256
  or ES256 is signed) and which status an expired delta token gets (`410` or a `40X`
  `syncStateNotFound`).
- That the metadata server answers as the tests' stand-in does: every test of version 32 runs
  against an in-process server.
- Federation, throttling of the list call and refresh failures stay in #492.
- Of the open items v0.32.0 listed, #440, #444, #447, #474 and #450 stand; #483 is closed by
  #509, and #478 by #521.

## Verification

push to main and nightly, not on a pull request), the `dev.json` checks the changed paths map to,
the `postgresql` job against PostgreSQL 16, verify-ts against the corpus, and the storage scenario
through the binary. The tagged commit's main-push CI runs the whole list, macOS included, and is
what the release takes. New safeguards were mutation-checked in scratch copies, each mutant failing
a test: six of #499's, five of #511's, six of #520's, nine of #512's, and two of #521's.
