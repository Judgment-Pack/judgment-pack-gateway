# v0.36.0

This release builds ADR-0048 (retention by acknowledgment, and store rotation) and ADR-0050 (an external signer in a key service). It also adds seals at the receipt sink and the gateway's key history. It takes three engine configuration versions, 36 to 38, and two PostgreSQL migrations, 7 and 8.

**On the PostgreSQL kind, run `gateway store migrate` before starting this release.** A database at schema version 6 or 7 is refused at start until it is migrated (item 1). Nothing else changes for a configuration of version 35 or earlier: it loads and serves as before.

- **Key service** (engine version 36; #536; ADR-0050, proposed): `signingKeyVersion` names an Ed25519 key version in Cloud KMS, which signs in place of the seed's key. `signingPublicKey` pins its public key (item 2).
- **Seals at the receipt sink** (engine version 37; #557; ADR-0049, accepted): `receiptSink.seals: true` delivers each seal to the sink after its session's receipts (item 3).
- **Retention** (engine version 38; #552; ADR-0048, accepted): `gateway retain` and `gateway store retain` remove a sealed session once a line signed under a pinned key acknowledges its seal and the window has passed (item 4).
- **Store rotation** (#554, filesystem kind; #546, PostgreSQL kind; SPEC.md §3d): `gateway store rotate` seals what is open, starts a new store and links its registry to the old one. `gateway verify --previous` checks the link (item 5).
- **Key history** (#560; ADR-0052, proposed; SPEC.md §3e): `GET /publickey/history` answers every key the registry proves the gateway signed under, carried across a store rotation (item 6).
- **Removing a scope under a key service** (#555): `gateway store remove-scope` takes `--config` in place of `--seed` (item 7).
- **Batch fixes** (#558, #541, #542, this release's review LOWs): `connect --replace` re-pins every platform on the binding it replaces. `seal-open --store` with no `--config` asks for `--no-sink`. Further fixes are in item 8.

ADR-0051 (#551, proposed) is a decision record only: session names as labels in their scope. It is built in v0.37.0 (#550).

## Compatibility

| With | What holds |
|---|---|
| An engine configuration | A file of version 35 or earlier serves as before. Versions 36, 37 and 38 each add one optional member: `signingKeyVersion` with `signingPublicKey`, then `receiptSink.seals`, then `retention`. A file below the member's version that carries it is refused by name. |
| A PostgreSQL store of v0.35.0 (schema version 6) | **Refused at start until `gateway store migrate` applies migrations 7 and 8.** Migration 7 adds `gateway.rotated`, the mark of a store rotated away from. Migration 8 adds `gateway.key_history`, the key history a rotation carries. Both are additive, and no existing row changes. The migration applies `grants.sql` as well: the run-time role gets SELECT and INSERT on `gateway.rotated`, and SELECT alone on `gateway.key_history`. |
| A filesystem store of v0.35.0 | Is served as it is. |
| The format | Receipts, seals and the records of v0.35.0 are unchanged. Two lines are new. A `store-continuation` line opens a rotated store's registry (SPEC.md §3d) and names the carried key history by `keyHistoryDigest` (§3e). A `retention-ack` line is the operator's input to `retain` and is never written into a store. |
| Older verifiers and the corpus | An older verifier reads a `store-continuation` line as a seal that loads nothing, so a rotated store verifies `ok` without its link checked. This release's verifiers (Go and verify-ts) check the link, and `--previous` checks it against the old registry. The corpus adds the store-continuation vectors and the key-history-digest refusals. Every earlier vector stands. A store after `retain` reads its removed sessions as `session-removed` to a verifier of v0.29.0 or later. |
| Receipts and stores written before this release | Keep their bytes and verify as before. |
| Judgment Pack Runner and other `/acquire` clients | Unchanged where no new member is configured. With `receiptSink.seals: true`, `/seal` answers only once the sink acknowledges the seal, and is refused `503` `receipt_not_forwarded` otherwise (item 3). |
| The runtime in the engine image | Unchanged: the `Dockerfile` pins `0.46.0`. |
| PostgreSQL | 16 is the version tested, in CI's two `postgresql` legs. |

## Changes for operators upgrading from v0.35.0

1. **PostgreSQL: migrate first** (#546, #560).
   - Stop every instance. Run `gateway store migrate` with the migration login (docs/postgresql-store.md). Name the run-time role, as at every migration. It applies `0007_rotated.sql`, `0008_key_history.sql` and the grants in one transaction, and moves the schema to version 8. Then start.
   - Until then, a start refuses a database at schema version 6 or 7 by name (`apply the store's migrations`). So does every command that opens it.
   - The filesystem kind needs nothing.
2. **A signer in a key service** (engine version 36; #536; ADR-0050).
   - **What it adds.** `signingKeyVersion` names one Ed25519 key version in Cloud KMS (`EC_SIGN_ED25519`, the software protection level). `signingPublicKey` is required beside it: the key version's public key, as 64 lowercase hexadecimal characters. `signingKeyVersion` without `signingPublicKey` is refused at load. A key version that answers another public key signs nothing.
   - **Where it signs.** Receipts, all seal forms, descriptor statements, the rotation statements and the stopped-gateway commands given `--config`: `remove-artifact`, `remove-scope`, `seal-open`, `export`, `connect`'s capture, `retain`, `store retain`, `store remove-scope` and `store rotate`. Every signature is verified under the gateway's key before anything is written with it. `rotate-key` stays seed-only.
   - **Rotating the key.**
     - On the filesystem kind: write the next version and its key into the configuration, then send SIGHUP.
     - On the PostgreSQL kind: stop every instance, change the configuration, start. An instance on another key version than the instances serving is refused at start by name.
     - A rotation that stops part way is settled as ADR-0050 and SPEC.md §3b say.
   - **What to do.** Nothing, unless you move to the key service. Then set the version to 36 or later, add both members, and give each stopped-gateway command `--config`, not `--store`/`--seed`: only `--config` names the key version.
3. **Seals at the receipt sink** (engine version 37; #557; ADR-0049, accepted; SPEC.md §6a).
   - **What it adds.** `receiptSink.seals: true` delivers each seal to the sink after every receipt of its session, acknowledged by its digest. That covers `/seal`'s seal, the start's seal after an interruption, and `seal-open --config`'s seal.
   - **When the sink does not acknowledge.** `/seal` is refused `503` `receipt_not_forwarded` with the seal's own sentence. The seal is in the registry and held. The session's next `/seal`, the next start, or `seal-open --config` delivers it again. The store keeps a marker for each seal pending, and the PostgreSQL kind needs no migration for it.
   - **What to do.** Nothing, unless you want seals forwarded: then set the version to 37 or later and add `"seals": true`. A sink without it is sent receipts alone, as in v0.35.0.
4. **Retention by acknowledgment** (engine version 38; #552; ADR-0048, accepted).
   - **What it adds.** `retention: {"window": <days, 7 to 36500>, "acknowledgedBy": [<1 to 4 Ed25519 public keys>]}`. The acknowledgment line and a worked example under a synthetic key are in docs/design/engine-config.md, "Retention by acknowledgment".
   - **The commands.**
     - `gateway retain --config <engine.json> --acknowledgments <file> [--scope <id>] --by <label>` is for the filesystem kind, with the gateway stopped.
     - `gateway store retain (--connection-file <path> | --connection-env <NAME>) --owner <role> --runtime <role> --config <engine.json> --acknowledgments <file> [--scope <id>] --by <label> [--timeout <seconds>]` is for the PostgreSQL kind. It runs as the migration login, in one transaction under the migration lock and the start lease. It reads the store a series at a time (#558 batch).
   - **What is removed.** A sealed session of one scope identifier, whose seal a verifying line names exactly, once the window has passed since the later of the seal and the acknowledgment. Each removal writes ADR-0034's `session-removal` record and nothing else.
   - **What is refused.** The whole call is refused, before anything is written, for: a line that does not verify, an open session, a seal that is not the store's, a session of no scope, a receipt that cites a session the call would remove, a session with conflicting seals, and a store rotated away from.
   - **What to do.** Nothing: with no `retention` member nothing is removed by age, and nothing runs on a timer. To use it, set the version to 38 and add the member, then run the command from your own scheduler.
5. **Store rotation** (#554, #546; ADR-0048 S2; SPEC.md §3d).
   - **Filesystem kind.** `gateway store rotate (--config <engine.json> | --store <dir> --seed <file> --registry <file> --authority <authority>) --new-store <dir> --new-registry <file>`, with the gateway stopped.
   - **PostgreSQL kind.** `gateway store rotate --config <engine.json>` with the migration login's connection to a new, empty database, given as `store migrate` takes it. It refuses while any instance's start lease on the old database is live.
   - **On both kinds,** the command seals each open session, then starts the new store with a `store-continuation` line linked to the old registry's last line. It marks the old store rotated, and a start or a command on that store is then refused by name.
   - **Checking it.** `gateway verify --previous <old registry> …` checks the link. On the PostgreSQL kind, read both stores through `gateway export --config` first.
   - **A rotation that stops.** docs/postgresql-store.md says which reruns finish it. If the old database's mark was not written and an instance started on it before the rerun, the rerun is refused. Drop the new database, make it again empty, and rotate again.
   - **What to do.** Nothing, unless you rotate. Point the configuration at the new store afterwards, and keep the old store until it is past your own retention.
6. **The key history** (#560; ADR-0052; SPEC.md §3e).
   - `GET /publickey/history`, with no token, answers canon of `{keyHistoryVersion: "1", keys: [...]}`. Each later key comes with the two statements of the rotation to it, and the list is carried across a store rotation. On the filesystem kind it is carried in `<new registry>.key-history`, and on the PostgreSQL kind in `gateway.key_history`.
   - A history that cannot be read or does not hold is answered `500` with a fixed sentence, never in part. The reason is on stderr.
   - From this release, the history's checks also hold the times in order: each rotation is later than the one before, and a store's continuation falls within its old store's last key (#558 batch).
   - **What to do.** Nothing. A client that pins `/publickey` can read the history to follow a rotation.
7. **`gateway store remove-scope --config`** (#555).
   - The command takes `--config <engine.json>` in place of `--seed <file>`. Exactly one of them is given, and both together is a usage error.
   - With `--config`, it signs under the key in force: the seed, or the key service's version held to `signingPublicKey`.
   - **What to do.** Under a key service, give `--config`. Every command line valid in v0.35.0 means what it did.
8. **Batch fixes** (#558, #541, #542; this PR).
   - **`connect --replace` re-pins every platform on the binding replaced** (#542). With two or more platforms on one binding whose file changed, `--replace` for one re-pins them all in one write and names each. This replaces v0.35.0's hand edit for the `microsoft-graph` digest.
   - **`seal-open --store` with no `--config` asks for `--no-sink`** (#541). Run that way, it cannot tell whether the store's gateway forwarded receipts to a sink, so it is refused by name unless `--no-sink` is given.
     - With `--no-sink`, it seals as before and says delivery was skipped.
     - Given `--config`, it delivers first, as before.
     - **What to do:** a script that runs flag-only `seal-open` on a store with no sink adds `--no-sink`. Where a sink is configured, give `--config`.
   - **Seal sentences** (#558 L3). A `/seal` waiting behind a seal delivery still in flight is answered, on timeout, with the held seal's own sentence. The seal sentence no longer says the session's next seal delivers it: after a restart, the start or `seal-open` does.
   - **Key service follow-ups** (#536's review).
     - At a PostgreSQL start, every scope's store is held to the key, not the main store alone.
     - The start reads each series' lowest entry in one query, where it took 1+2N reads for N series.
     - The readiness line names the key in force: a SIGHUP rotation that comes before it no longer leaves it naming the key at start.
     - SPEC.md §3b states how a stopped key-service rotation is settled.
   - **`/publickey/history`** caches a failing answer as it caches a good one, so a broken history is not re-walked per request.
   - **`store rotate` on the PostgreSQL kind** refuses a new database holding a carried key history alone, or rows of a store alone, each by its sentence. This was already the behaviour; it now has a test.

## Decisions

- **ADR-0048** (#533), accepted in v0.35.0, is built here: retention (#552) and rotation (#554, #546).
- **ADR-0049** (#538), accepted, with the 2026-11-19 amendment for seals (#557).
- **ADR-0050** (#536), proposed: an Ed25519 key version in a key service signs in place of the seed, at the software protection level.
- **ADR-0051** (#551), proposed: a session name is a label in its scope, mapped to a minted session id. Built in v0.37.0 (#550).
- **ADR-0052** (#560), proposed: the key history beside the public key.

## What this release does not establish

- That a live key service answers as the in-process stand-in does. Every key-service test runs against a stand-in for the metadata server and the service.
- That a live sink acknowledges seals as the stand-in does.
- A coordinated live rotation across PostgreSQL instances (#537). Stop every instance to rotate.
- `/act` receipts and seals at the sink (#539).
- Of what v0.35.0 did not establish, these stand:
  - the live directory service's error codes;
  - that anything of version 33 meets the live services as the stand-ins do;
  - that PS256 is taken by the live identity platform;
  - that a `read-external` tool only reads.
