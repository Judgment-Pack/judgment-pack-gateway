# v0.41.0 (draft)

This draft states what ships in v0.41.0.

## Engine configuration versions

Engine configuration version 52 and PostgreSQL schema version 11. A configuration that runs on v0.40.0 behaves as it did there, except as stated below.

- **Request limits counted together by the instances of one database** (gateway #593, ADR-0061).
  From engine version 51, `limits.shared: true`, valid only on PostgreSQL with `storage.instances`
  `"several"`, counts each scope's limits across the instances. The rate is leased from a row of
  the new `gateway.limit_rates` (migration `0011_limit_rates.sql`, schema version 11, applied by
  `gateway store migrate` with every instance stopped; one-way, as v0.40.0 refuses the database
  after it) in batches of b = ceil(rpm/600), 1 to 64 and at most the burst, refilled off the
  request path. Bounds: over a window W at most B + ceil(W/T) + N·b, never above the rate over
  time; in flight and per caller ceil(limit/N) per instance, at most cap + N − 1 in flight. A
  database that does not answer within 2 seconds leaves each instance counting alone at
  ceil(limit/N), said on `/posture`, until a refill succeeds. `beforeScope` stays per instance.
  Below 51, on the filesystem and with one instance the member is refused by name; without it
  nothing changes, byte for byte.
- **`/act` resolves cited approval records** (gateway #581, ADR-0063; SPEC.md §1.2a, §6). From
  engine version 52, `approvalRecords` names a directory the operator fills: the gateway's, and a
  scoped write platform's own. Each scoped write names its own once the gateway names one. The
  directories are held apart and ownership-checked as `decisionRecords` are. A citation's record is
  the file `<dir>/<kind>/<id>`, at most 1 MiB, whose SHA-256 is its digest. No link is followed at
  any level, and a kind or id must be one path segment of code points below U+0300; ids outside that
  range are refused (#624 tracks every NFC id). Each is matched by its exact name in the directory's
  listing, so on a filesystem that folds case `CHG-1` is not resolved by `chg-1`. Every citation
  of an action of that scope must resolve before anything is sent, and a dry-run's too. Otherwise
  the action is refused `400` at `approvals` with one sentence that names no directory or path.
  The receipt then carries `action.approvalsResolved: true` under the signature. `gateway verify`
  and verify-ts read the mark, and five corpus vectors hold it (`v3-action-approvals-resolved`,
  `-claimed-only`, `-resolved-false`, `-resolved-string`, `-resolved-without-approvals`). The
  action key and its identity are unchanged. Below 52 the member is refused by name. Without it a
  citation is the requester's claim, and every answer and receipt is unchanged, byte for byte. A
  v0.40.0 verifier tolerates the mark and does not report it.

## Refusal-entry forwarding

Follow-ups to the refusal-entry forwarding source (ADR-0059 section 9, #611). No answer, receipt or entry changes, and the sink is sent what it was sent before.

- **On the PostgreSQL kind, a forwarding pass takes no pool connection.** The forwarding cursor's
  read, and its compare-and-set under the journal's advisory lock, now run on the source's own
  connection, the one it reads entries and takes the lock on, and no longer on the pool that answers
  use. The compare-and-set is a statement of the transaction that holds the lock, so `remove-scope`
  can no longer take a journal and its cursor between the lock and the cursor's move. Before, where
  the pool stayed saturated past the idle bound, that could leave a cursor naming an entry no journal
  holds, and forwarding of the scope's next journal stopped at it, named once on stderr. No
  transaction is open across a delivery.
- **One read of a journal per forwarding pass.** A pass reads the entry at the cursor and the batch
  after it in one read, on both kinds. On the filesystem kind a pass starts where the journal's
  last read ended, once it has checked that the file is the same one and still holds that line,
  so a pass over a journal that has not changed reads no entry past the cursor's; a file replaced,
  cut back or rewritten is read whole, as before. The source keeps one line for each configured
  journal.

## Refusal journal operations

- **A staged key file of any journal's name is removed** (gateway #611). The start removes,
  before any key is read, every staged key file a start ended mid-draw left in the store's root
  (`.<journal>.key.<pid>.<12 lowercase hex>.tmp`), whatever journal it names. A scope no longer
  configured no longer leaves its file behind. Only a regular file of exactly that form is
  removed: never a link, a directory or a near miss, and only one last written five minutes ago or
  longer. Several gateway processes may serve one store, and a younger file may be another's
  draw under way. `gateway remove-scope` of a scope also removes that scope's staged files and
  says so on stderr. A staged file holds a key no entry was ever made under, so nothing is lost.
- **A way out for the refusal journal of the sources of no scope** (gateway #611). Where that
  journal's key is lost, as after a restore from a full export, which carries no keys,
  `gateway journal reset --config <file> --unscoped --by <label>` (filesystem) and
  `gateway store journal-reset --unscoped` (PostgreSQL, with the connection and role flags of the
  other store commands) remove that journal, its key and its forwarding cursor, with the gateway
  stopped. They take no scope argument: `--scope`, or any other argument, is a usage error.
  Before anything is removed they write a signed operator entry of the new kind
  `refusal-journal-reset`, naming the journal's bytes by `refusalJournalBytes` and
  `refusalJournalDigest`; `gateway verify` and verify-ts read it alike, and three corpus vectors,
  `v3-journal-refusal-journal-reset`, `v3-journal-refusal-journal-reset-half` and
  `v3-journal-refusal-journal-reset-extra-member`, hold it. No
  receipt, session, removal record or other journal is touched. The next start draws a new key and
  journals the refusals of the sources of no scope again. A filesystem run cut off after its entry
  is completed by a second run or the next start. The manual step of moving `<name>.jsonl` aside on
  the filesystem kind is gone from `docs/design/store-contract.md`.

- **`remove-scope` and `journal reset` refuse a store any gateway serves** (gateway #611). Each
  gateway process serving a filesystem store holds the store's directory lock shared, under its own
  registry. `gateway remove-scope` held only its configuration's registry, so it refused a gateway
  serving under that registry and not one serving the same store under another, which then lost the
  removed journal's key mid-run and started write-failed. Both commands now also take the store's
  lock exclusive, as `gateway journal compact` does, and refuse with `store-served` while any
  gateway process serves the store, before anything is read or removed. Where the platform keeps no
  such lock (Windows), nothing changes: the commands say the gateway was to be stopped.

## Key history

- **A command-line check for a fetched key history** (gateway #584; ADR-0055, amendment of
  2026-11-24). `gateway verify-key-history [--public-key <key> [--public-key-alg ES256]]
  [--require-version 2] <file|->` and verify-ts's `main.ts verify-key-history`, with the same
  arguments, hold the answer of `/publickey/history`, from a file or from standard input for `-`,
  to the consumer's check that the library already makes, and write one line of JSON on
  standard output: `{"accepted":true,"version":"1","keys":3,"inForce":"<keyId>"}`, or
  `{"accepted":false,"refused":"<class>"}` with one of the eight classes of ADR-0055 section 9. The two
  commands write the same bytes for every `corpus/key-history` vector. `--require-version 2` holds a
  gateway to version `"2"`; without `--public-key` the first entry's key is taken, so the check proves
  that each entry follows from the first and not that the first is the gateway's. An input over 16 MiB
  (16,777,216 bytes) is refused before it is parsed, as a usage error. `gateway` exits 0 for a history
  that holds, 1 for a refusal and 2 for a usage error; verify-ts exits 0, 1 and 64. No engine version,
  no migration, no change to the answer, the check or the corpus.

## Upgrading a PostgreSQL store

Migration 0011 is one-way, and v0.41.0 needs it on every PostgreSQL store, whether or not
`limits.shared` is set: its start refuses a database at schema version 10 until the migration is
applied. v0.40.0 and earlier refuse a database at schema version 11, by the start and by
`gateway store migrate`. Before migrating, stop every instance and take a backup of the database;
rolling back to v0.40.0 after the migration needs a restore from that backup, and what was written
under v0.41.0 since is not in it. Then run `gateway store migrate` as the migration login and start
the instances. Migration 0011 is this release's only one. The filesystem kind has no migration.

## Compatibility

- **A reservation sender may reconcile a scoped delegated key** (gateway #596; SPEC.md §11.8;
  ADR-0054, amendment of 2026-11-24). The subject, the issuing host or an operator names the key's
  scope identifier in `/act`'s `scope` member beside its `reservation`. It is served evidence and
  read-back in that scope, never a dispatch, only where the issuing host's `scopeIds` lists the
  identifier, the subject's caller entry grants it and the sender's own token reaches it. An operator
  is granted the scope in its caller entry first. Anywhere else the answer is byte for byte the one
  given for a scope identifier that exists nowhere, before any standing, key or journal is read. No
  engine version. A request that names no scope is answered as before, and so is every request where
  no issuing host names `scopeIds` or no write source is fixed to a scope identifier. Recorded
  reservations are unchanged. Two things differ from v0.40.0 there. `/posture` adds
  `delegation-scoped-reservation`. A subject that names a scope its conditions do not admit gets the
  scope sentence without a standing read; v0.40.0 read the standing first.

- **The staged key files.** A v0.40.0 start removes only its configured journals' staged files;
  a later v0.41.0 start removes the rest. Nothing else in the store's root is touched.
- **`remove-scope` refuses a store served under another registry.** A call that a v0.40.0
  `remove-scope` ran while a gateway served the store under another registry is now refused with
  `store-served`; stop every gateway process serving the store, then remove.
- **The `refusal-journal-reset` entry.** A v0.40.0 `gateway verify` or verify-ts reads an operator
  journal holding a `refusal-journal-reset` entry as `journal-entry-forged` at that entry, as
  v0.39.0 read v0.40.0's `remove-scope` entry carrying the refusal journal's members. Verify such a
  store with v0.41.0 or later.
