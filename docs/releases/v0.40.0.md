# v0.40.0 (draft)

This draft states the operator journal (ADR-0056, #543) and the delegation scope binding (#591), which ship in v0.40.0.

## Built

- **The operator journal** (ADR-0056, #543), on both kinds. From engine version
  45 (`operatorJournalVersion`), and on any store that already holds the journal,
  `retain`, `remove-scope`, `remove-artifact`, `seal-open` and `store rotate` (in the store rotated
  from) each write one signed, chained entry to `journals/operator.jsonl`. `store rotate` begins the
  journal of the store rotated to with a `store-continued` entry, which names the new registry's first
  line and the old journal's length and digest, so an archived old store can be matched to the new
  one. A `retain` entry holds the
  SHA-256 of the acknowledgment file and the configured key ids, so both are read back from the store.
  A removal's entry is staged in `journals/operator.pending` and committed after its records; the
  next journaled command settles a staged entry, and the start names one on stderr and serves.
- **`gateway verify` step 9.** New findings `journal-entry-forged`, `journal-order`,
  `journal-entry-mismatch` and `journal-entry-missing`; `journal-missing` under the new option
  `--require-journal <name>`; the new observations `journal-from` and `journal-torn-tail`. A removal
  file that ends in an unterminated line which loads as no removal record is no finding: the next
  removal call covers it. One that loads as a record is `journal-entry-missing`, and removal calls
  refuse to run on it, naming the file and saying to cut it back to its last complete line. A store
  with no journal is reported exactly as before.
- **verify-ts and the corpus.** verify-ts makes step 9's check and takes `--require-journal`; six
  `v3/stores` vectors carry a journal, and `gateway conform` passes a vector's `requireJournal` on.
- **Export.** A full export carries `store/journals/operator.jsonl`, of either kind; an export by scope
  carries none.
- **Older readers.** A verifier of v0.39.0 passes `journals/` over: it does not check the journal, so a
  forged or missing journal goes unreported by it, and it refuses `--require-journal` as a usage error.
  `gateway export --check` of v0.39.0 refuses an export that holds the journal: `manifest: a file is
  not one an export writes`. Roll commands back to v0.39.0 only with the version lowered on a store
  that holds no journal.
- **The PostgreSQL journal table.** Migration 0010 (schema version 10) makes `gateway.journal_records`,
  a row per journal entry, admitted only at the end of its journal's chain. The run-time login holds
  SELECT and INSERT on it, and the start refuses one that may update, delete or truncate it.
- **The operator journal on the PostgreSQL kind.** `store retain` and `store remove-scope` insert
  their entry in the transaction of their records; `seal-open`, and `store rotate` in the database
  rotated from, insert theirs after the last seal, as the run-time login, fenced on the start lease;
  `store rotate` writes `store-continued` in the migration's transaction that makes the new registry.

## Delegation chains bound to one scope identifier

Part of spec RFC 0030's amendment of 2026-11-22 (*Binding a chain to one scope identifier*; §3, clause 9). It takes one engine configuration version, 46 (`delegationScopeBindingVersion`), and no PostgreSQL migration.

- **The statement.** `scope` may hold `scopeId`, a scope identifier, never `"unscoped"`; any other form is `malformed`. Clause 9 holds a chain to its root's binding: an unbound child of a bound link, a bound child of an unbound one, and a child bound to another identifier are `widened` (SPEC.md §11.1).
- **The request check**, `scope-id-mismatch`, on `/acquire` and `/act`, before step 8 and any admission read: under a bound chain a request names `scopeId`, and under an unbound chain it names none. It is answered with `/acquire`'s wrong-scope sentence, `400`, and nothing is read or counted. On `/act` it is made at the scope step (ADR-0054, step 8), before the session, the platform and any admission read, and answered at `scope-identifier`.
- **A delegated `/act` may now name its chain's scope** (ADR-0054, decision 1, *Who may name it*). Under a chain bound to a scope identifier that the issuing host's `scopeIds` lists and the subject's caller entry grants, `/act` names that identifier on a write fixed to it, and its receipt carries `scope` and `scopeSalt`; a dry-run under it is admitted as a dry-run, and an uncertain action's read-back is acquired in the action's scope. Naming none, naming another, or reaching a write source of another scope is refused with the same sentence. A reservation's sender has no chain and still names no scope identifier.
- **The configuration.** `delegation.hosts[].scopeIds` lists the scope identifiers a host's chains may be bound to; none by default. A chain bound to another is refused at binding and at a call (docs/design/engine-config.md).
- **The cases.** `testdata/delegation/spec-scope-binding.json` is a byte-for-byte copy of the spec repository's `conformance/delegation/scope-binding.json` (table 3), and `testdata/delegation/agent-scope-binding.json` of the agent library's `contract/vectors/principal/scope-binding.json`; the gateway decides every row of each that applies to it. `testdata/delegation/es256-statements.json` follows the spec's revision, which names the link of its two chained `chain-broken` cases.

### What changes at every version

- A delegated request under a chain bound to no scope identifier that names a scope was admitted where `identity.callerScopes` is `"unchecked"`; it is now refused, as the RFC's request check states.
- A statement whose `scope` holds `scopeId` was `malformed`; it now verifies when the form holds, and a request under it is refused unless the host's `scopeIds` names it.

## The refusal journal (ADR-0059)

- **Built.** A new optional member, `refusalJournal` (engine version 48). With it, a refusal of a request charged to a scope is signed into that
  scope's own refusal journal after the answer is flushed. Every answer is the one without the member;
  the test compares status, headers but Date, the length and the body, with the journal on, off and
  failing. One header difference remains possible on the wire: a held refusal is written with an
  explicit Content-Length, so its header lines may come in another order (RFC 9110 §5.3).
- **Timing (accepted residual).** No cover traffic is sent. Under a key service an answer's signing
  can wait behind one journal signing, up to ADR-0050's 5 seconds; and a key service quota shared
  with the journal can make signings fail, not only slow. Size the quota for one signing for each
  request charged to a scope, plus one tally a minute per scope.
- **Verify, export and the corpus.** `gateway verify` and verify-ts judge each refusal journal; the
  corpus gains ten `v3-journal-refusal-*` vectors. A full export carries the journals, without
  their keys; an export by scope carries none. A verdict by scope reports only its own scope's
  refusal journal, and says nothing of another's (`v3-cut-a-refusal-journals-of-others`).
- **`remove-scope` while the gateway serves.** The writer stops writing that scope's entries, and
  counts each one it drops as `write-failed` in the scope's tally, until the gateway starts again;
  it never writes into the removed journal or into one that no key opens. A run of `remove-scope`
  cut off after its operator entry is completed by a second run, which removes the refusal journal
  that entry names.
- **The resolved tool.** An entry made after the route resolved the request's tool to one its
  source's configuration names carries `tool`, and, where the operation pins a descriptor snapshot,
  that tool's `descriptorDigest`. An entry made before resolution names neither. Both readers refuse
  a `descriptorDigest` without a `tool`.
- **New commands.** `gateway journal name --scope <key>` and `gateway journal open`.
- **Older readers.** From this release, verify and the export reader refuse a journal they do not
  read by its name (below), so a later release's journal is never passed over. A v0.39.0 verifier
  passes `journals/` over whole, refusal journals included.
- **Not yet built.** Forwarding refusal entries to the sink is a later change; delivery version
  "3" (below) is the envelope that carries them.

## Memory sizing

- **The request tee.** While the refusal journal is configured, the request body a refusal entry
  commits to is held in memory until the request is answered and its entry handed off: up to 1 MiB
  for each request in flight.

## Journals this release does not read

`gateway verify` and verify-ts report each file of `journals/` other than `operator.jsonl`,
`operator.pending`, and a refusal journal, its key, its forwarding cursor (`.forwarded`) and a
cursor's staging file (`.forwarded.<pid>.<12 hex>.tmp`, left by a process ended mid-write and
removed by the forwarder's next start) as `journal-unknown`, `{status, file}`, and the verdict fails. A journal of a
later release, or a file put there, is never passed over as though it held. `gateway export`
refuses a store holding one, naming it, and an export reader refuses an export that carries one,
by its path. Either of the two names, where it is a link, a directory or a pipe, is
`journal-unknown` too, rather than read as no journal. On the PostgreSQL kind, `gateway export`
refuses a store whose `gateway.journal_records` holds rows of any journal but `operator` and the
refusal journals, naming each: the export carries those alone, so the copy would otherwise verify
without them. v0.39.0 and earlier pass `journals/` over whole, as their notes say.

A store rotation stopped by a crash can leave `journals/.operator.jsonl.rotating` in the store it
rotates to. That file is now `journal-unknown`: `gateway verify` fails and `gateway export` refuses
that store until the rotation is run again, which writes the journal in the file's place.

## Delivery version "3" at the receipt sink

Issue #539; ADR-0059 section 9. It takes engine configuration version 50 (`sinkDeliveryV3Version`),
after the refusal journal's 48 and the call reference's 49, and no PostgreSQL migration.

- **The member.** `receiptSink.deliveryVersion: "3"` sends one envelope, `{deliveryVersion, kind,
  digest, ...}`, for each acquisition receipt, action receipt and seal, acknowledged by `digest`, a
  SHA-256 under a domain prefix of its own. An action receipt travels as `actionReceipt`.
- **`/act`** answers only once its receipt is acknowledged. Not acknowledged, it answers `503`
  `receipt_not_forwarded`: the action was carried out, its receipt is in the store and held, and
  the same `actionKey` answers it once the sink acknowledges it. A seal is refused while an action
  receipt of its session is held.
- **`receiptSink.refusalEntries: false`** declines refusal entries, under `"3"` alone. The refusal
  journal (above) makes the entries; forwarding them to the sink is a later change.
- **A sink not moved to `"3"`** receives exactly what it receives today. A sink moved to `"3"`
  before it reads `"3"` acknowledges nothing, and every acquisition is refused. Upgrade the sink
  first, then the gateway, then the configuration.

## Upgrading a PostgreSQL store

Migration 0010 is one-way. v0.39.0 and earlier refuse a database at schema version 10, by the start
and by `gateway store migrate`. Before migrating, stop every instance and take a backup of the
database; rolling back to v0.39.0 or earlier after the migration needs a restore from that backup.
Then run `gateway store migrate` as the migration login and start the instances.

## A call reference passed to a binding (ADR-0060)

A platform may set `callReference: true` from engine configuration version 49. Each call through
that platform's binding then carries a fresh per-call reference and the session identifier in the
`tools/call` request's `_meta`, as `judgment-pack/callRef` and `judgment-pack/sessionId`, and the
version 3 receipt signs the same reference as `callRef`. A platform without the member, and its
receipts, are unchanged. The Go and TypeScript verifiers hold `callRef` to 64 lowercase hex
characters. A verifier from before this release reads a receipt carrying it as it reads any signed
member it does not know (SPEC.md §1.2a), and does not check its form.
