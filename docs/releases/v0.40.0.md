# v0.40.0 (draft)

This draft states the operator journal (ADR-0056, #543), which ships in v0.40.0.

## Built

- **The operator journal** (ADR-0056, #543), on both kinds. From engine version
  45 (`operatorJournalVersion`), and on any store that already holds the journal,
  `retain`, `remove-scope`, `remove-artifact`, `seal-open` and `store rotate` (in the store rotated
  from) each write one signed, chained entry to `journals/operator.jsonl`. `store rotate` begins the
  journal of the store rotated to with a `store-continued` entry, which names the new registry's first
  line and the old journal's length and digest, so an archived old store can be matched to the new
  one. A `retain` entry holds the
  SHA-256 of the acknowledgment file and the configured key ids, so both are read back from the store.
  A removal's entry is staged in `journals/operator.pending` and committed after its records; the
  next journaled command settles a staged entry, and the start names one on stderr and serves.
- **`gateway verify` step 9.** New findings `journal-entry-forged`, `journal-order`,
  `journal-entry-mismatch` and `journal-entry-missing`; `journal-missing` under the new option
  `--require-journal <name>`; the new observations `journal-from` and `journal-torn-tail`. A removal
  file that ends in an unterminated line which loads as no removal record is no finding: the next
  removal call covers it. One that loads as a record is `journal-entry-missing`, and removal calls
  refuse to run on it, naming the file and saying to cut it back to its last complete line. A store
  with no journal is reported exactly as before.
- **verify-ts and the corpus.** verify-ts makes step 9's check and takes `--require-journal`; six
  `v3/stores` vectors carry a journal, and `gateway conform` passes a vector's `requireJournal` on.
- **Export.** A full export carries `store/journals/operator.jsonl`, of either kind; an export by scope
  carries none.
- **Older readers.** A verifier of v0.39.0 passes `journals/` over: it does not check the journal, so a
  forged or missing journal goes unreported by it, and it refuses `--require-journal` as a usage error.
  `gateway export --check` of v0.39.0 refuses an export that holds the journal: `manifest: a file is
  not one an export writes`. Roll commands back to v0.39.0 only with the version lowered on a store
  that holds no journal.
- **The PostgreSQL journal table.** Migration 0010 (schema version 10) makes `gateway.journal_records`,
  a row per journal entry, admitted only at the end of its journal's chain. The run-time login holds
  SELECT and INSERT on it, and the start refuses one that may update, delete or truncate it.
- **The operator journal on the PostgreSQL kind.** `store retain` and `store remove-scope` insert
  their entry in the transaction of their records; `seal-open`, and `store rotate` in the database
  rotated from, insert theirs after the last seal, as the run-time login, fenced on the start lease;
  `store rotate` writes `store-continued` in the migration's transaction that makes the new registry.

## Journals this release does not read

`gateway verify` and verify-ts report each file of `journals/` other than `operator.jsonl` and
`operator.pending` as `journal-unknown`, `{status, file}`, and the verdict fails. A journal of a
later release, or a file put there, is never passed over as though it held. `gateway export`
refuses a store holding one, naming it, and an export reader refuses an export that carries one,
by its path. Either of the two names, where it is a link, a directory or a pipe, is
`journal-unknown` too, rather than read as no journal. On the PostgreSQL kind, `gateway export`
refuses a store whose `gateway.journal_records` holds rows of any journal but `operator`, naming
each: the export carries the operator journal alone, so the copy would otherwise verify without
them. v0.39.0 and earlier pass `journals/` over whole, as their notes say.

A store rotation stopped by a crash can leave `journals/.operator.jsonl.rotating` in the store it
rotates to. That file is now `journal-unknown`: `gateway verify` fails and `gateway export` refuses
that store until the rotation is run again, which writes the journal in the file's place.

## Upgrading a PostgreSQL store

Migration 0010 is one-way. v0.39.0 and earlier refuse a database at schema version 10, by the start
and by `gateway store migrate`. Before migrating, stop every instance and take a backup of the
database; rolling back to v0.39.0 or earlier after the migration needs a restore from that backup.
Then run `gateway store migrate` as the migration login and start the instances.
