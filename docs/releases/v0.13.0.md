A gateway can now reach a remote MCP server over Streamable HTTP, as a source and as the executor (ADR-0015, accepted), and two connections ship on it for a desk's reads at decision time: Databricks, over the REST API and the Databricks-provided MCP servers, and Azure DevOps, over the REST API and its remote MCP server. Two catalog bindings let a decision write back to either, under a decision policy, through a platform whose `parameters` fill the binding's placeholders (engine configuration version 8). The stdio form of `adapter-mcp` writes the records it wrote before, byte for byte, and nothing that started under `v0.12.0` refuses to start.

## What an operator must do

- **Nothing**, unless a gateway is to reach a remote MCP server, offer a Databricks or Azure DevOps connection, or write back to either. No receipt, registry, witness or connection format changes for anything configured before.
- **To reach a remote MCP server**, give `adapter-mcp` its third form, `--url https://…`, exclusive with `--image` and a command after `--`: `https`, or `http` on a loopback literal (`localhost` refused); no redirect followed; `--ca-file` as `adapter-http` has it; the bearer named by `--bearer MEMBER` from the `--credentials` file and held to RFC 6750's token68 form; `--header NAME=VALUE` for a fixed header, the credential's, the protocol's and the transport's names refused; `--tools`, `--check`, `--probe`, the descriptors capture and the output bound as before. The acquisition records `transport: "http"`, the endpoint as configured, the TLS identity the answer came under and the server's name and version; over stdio those members are absent, so earlier records read as before. A catalog binding's `mcp` operation may name `"server": {"url", "bearer", "headers"}` in place of an image.
- **To offer a Databricks connection**, `gateway-connections --provider databricks`: the workspace URL, a warehouse, a personal access token or a service principal (client id and secret, scope `all-apis` unless given; a Unity Gateway service needs `ai-gateway`), and, for the MCP profile, the servers to enable by exact name with a tools allowlist each: `sql`, `genie:<space>`, `functions:<catalog>.<schema>.<function>`, `ai-search:<catalog>.<schema>.<index>`, `unity-gateway:<catalog>.<schema>.<service>`. Know what Databricks says of them: the four workspace endpoints are listed as legacy behind the Managed MCP Servers preview, Databricks recommends Unity Gateway for new Genie and SQL work, a Unity Gateway service may be an external connector that writes, and only Genie is stated read-only; a warehouse's and Unity Catalog's grants on the identity are what keep a profile to reads. The Genie and function servers' tool names are not on a reference page; `test` lists what each server offers.
- **To offer an Azure DevOps connection**, `gateway-connections --provider azure-devops`: the organization URL in either documented form, the project, and a personal access token or an Entra access token with its expiry; the MCP profile reaches the organization's remote server (`https://mcp.dev.azure.com/<organization>`) under an Entra token only, since the page says the remote server takes no personal access tokens, sending `X-MCP-Readonly: true` by default. A read-only PAT is what keeps the API profile to reads; the header is the server's promise. For an unattended principal, the README documents the local server as an operator-level `adapter-mcp` source.
- **To write back**, raise `engine.json` to `engineVersion` 8 and give the platform `parameters` (`organization` for Azure DevOps; `workspace`, `catalog`, `schema`, `function` for Databricks), a `write` credentials file whose `token` member is the bearer, `write: true`, and a `decisionPolicy` per tool (ADR-0011, ADR-0012); `connect --parameter NAME=VALUE` writes them and captures the server's descriptors at the resolved URL. A policy cannot yet fix a value or close an argument set (#258), so the worked Azure DevOps policy binds the whole arguments to a `writeBack` fact the record states. Raw SQL is no write tool: Databricks writes are Unity Catalog functions, one per binding.
- **Know what a connection's receipt establishes** (SECURITY.md; `docs/design/connection-catalog.md`): bytes from that endpoint under that TLS identity, for that statement, listing or tool call, at that time, under the credential the operator configured where one is. Not that the data is true or current, that the credential's grants are what the operator intends, or that a call read rather than wrote. An action receipt establishes who asked, which judgment was cited and found verifying, and what was sent to which resolved endpoint; not that the target applied it: only an accepted tool result is receipted, `isError` included, and an HTTP or JSON-RPC failure after the call is sent mints nothing even though the write may have been applied. A reconciliation read is how an operator sees it.
- **Deferred findings, open as issues**: #250 (the remote form's configured output bound applied after the body is parsed; an 8 MiB transport bound holds), #251 (one endpoint grammar across the adapter, the signer and both verifiers), #254 (a safeguard test's path assertion inactive for Unity Gateway paths), #258, #259 (the local Azure DevOps server as a catalog binding), #260 (the postgres binding's `execute_sql` write is raw SQL).

## A remote MCP server as a source and as the executor (#249, closes #245; ADR-0015)

- The `--url` form, the credential and header rules, the session id handled by the client and recorded nowhere, the check report over HTTP, the executor over a remote binding with `action.tool.endpoint` carrying the URL; SPEC §1.2a and §6 state the remote members and both verifiers hold them; nine corpus vectors `v3-mcp-remote-*`; a golden test holds the stdio form's records byte for byte.
- After the review: the bearer held to token68 when read; `--probe` held to `--tools` before the server is started, for the stdio form too; a session id reflected by the server refused in decoded answers and redacted in diagnostics; the docs' credential claim qualified to "where one is configured".
- What it establishes, from ADR-0015: byte lineage from that endpoint under that TLS identity, for that tool and those arguments, at that time. Not that the bytes are true; that the tool read rather than wrote (`--tools` is the only thing that keeps a source to reads); that the server is honest or the vendor's.

## Write-back platforms under decision policies (#257, closes #248)

- `parameters` on a platform (engine configuration version 8) fill `{name}` placeholders in a remote binding's `url` and `tools`; a placeholder without a parameter, a parameter without a placeholder, a placeholder in the host or the scheme, a value out of form, or a resolved URL out of the endpoint form refuses the start; the resolved URL is what the receipt and the acquisition carry. ADR-0015 is amended in place for its question 1. `catalog/azure-devops.json` (the remote server's three work-item write tools) and `catalog/databricks.json` (one Unity Catalog function, its tool `<catalog>__<schema>__<function>` per Databricks' example code). A binding may state `write` alone. `connect --parameter`.
- After the review: a remote snapshot records the resolved endpoint its check reached, and a pin whose endpoint differs from what the parameters now resolve to is refused until recaptured; the connect line names the resolved URL and holds the adapter's reported endpoint to it; the executor note states the protocol-failure rule above.
