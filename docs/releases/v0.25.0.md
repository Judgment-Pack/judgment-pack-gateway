# v0.25.0

This release admits every delegated call under its platform's connection grant: a write through
`/act` (#368), an acquisition through `/acquire` and the read-back of a delegated key's uncertain
action (#372). It adds offline compaction of the action journal (#359), and carries the LOWs of the
v0.24.0 grant and publisher review (#362) and of the clean room of #373 (#374). The release tag is
also the milestone. The implementation rows are
[#370](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/370),
[#371](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/371) and
[#373](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/373), and the pre-release batch
[#375](https://github.com/Judgment-Pack/judgment-pack-gateway/pull/375).

## Upgrade

1. No `grant` means every delegated call on that platform is refused `grant-unknown`: /act,
   /acquire and read-backs, for every sender. A refused read-back answers 409
   `action-reconciliation-unavailable`. Keys left uncertain across the upgrade stay uncertain until
   a grant is named. This reverses the v0.24.0 note "grants cover the custody only".
2. The image ships no gateway-connections and no custody user. A config naming a grant does not
   start, and one naming none refuses every delegated call, so the image serves no delegated call.
3. `connect --replace` drops `grant`. `connect` never raises a file to 16, so edit `engineVersion`
   by hand.
4. New offline command: `gateway journal compact --store --archive --retention`.
5. Both serve commands take a shared store lock. A start during a compaction is refused
   `action-journal-held`.
6. A store whose filesystem refuses flock is refused at start (`action-journal-unavailable`).
   v0.24.0 gateways take no store lock, so stop every one of them before compacting.
7. engineVersion 16. `grant` is refused by name under 15 and below.
8. The custody program must be v0.25.0's gateway-connections; an older one answers
   `grant-unreadable`. It is held like an adapter and runs as a distinct `grant.user`, never root,
   the signer, the MCP user or a platform's user. Each delegated call may wait up to 2×30s on it.
9. Grant state now refuses delegated calls: quarantined, revoked, idle-expired, excess-scope, owner
   removed or unknown. Each admit records a use. The first in-scope call after the idle bound
   revokes the grant and deletes its credential. The operator's own calls are not checked.
10. Delegation issuers: to read back, the actor's chain must name `<platform>/live` and the read
    tool. Otherwise a key found uncertain is refused `action-key-unauthenticated` (including a
    crash-window marker or a lost claim). Only the request's own dispatch answers 409.
11. New wire values: `refusedAt: "grant"`, and `grant-unknown`, `grant-unreadable`,
    `grant-quarantined`, `grant-revoked`, `grant-idle-expired`, `owner-removed`, `owner-unknown` and
    `excess-scope` (403) on /act and /acquire.
12. Publisher:
    - A domain publisher at or under `sch.uk` is refused when the binding loads, so serve --config,
      connect, posture and mcp refuse to start where v0.24.0 accepted it.
    - npm and GitHub reads follow no redirect, so a renamed or transferred repository or package
      reads `unknown`.
    - Repository names now compare without case.

## Delegated writes under the grant (#371; closes #368)

A platform names the custody connection its delegated calls are admitted under with a `grant`
member (engine configuration version 16: `provider`, `connection`, `stateDir`, `principal`,
`user`). The signer never reads the custody, so the engine runs `gateway-connections` as
`grant.user`, with an empty environment, twice around the delegation's counting admission:

- `--grants check`, after the session is admitted and before the issuing host is read: the grant's
  state alone (drift, quarantine, idle expiry, excess). A grant refused here counts nothing.
- `--grants admit`, once the admission answers `admit`: the state again, the owner read and the
  record of the use. When the issuing host and the owner read would both refuse, the host's
  refusal is reported and the owner read is not made. A call the owner read refuses is not sent,
  and its count stays used, which fails closed.

A refusal answers `403` with `{"error", "refusal", "refusedAt": "grant"}`. The error is the
refusal's name and a fixed sentence, never the custody's own text. `grant-unreadable` covers a
custody that cannot be read, a program that cannot start, a failure, a timeout and an answer of
another form: a could-not-read is never taken for not-there. The operator's own `/act` is
unchanged, and its platform's credentials file is all it is held to.

## Delegated acquisitions and read-backs under the grant (#373; closes #372 and #362)

- A delegated `/acquire` follows the same order as a delegated write: `check`, the counting
  admission, then `admit`.
- The read-back of a delegated key's uncertain action makes no admission read and counts nothing.
  It runs `--grants admit` alone before its program starts. A grant that is not live, or whose
  owner is refused, serves no read-back: the key stays uncertain and answers `409`
  `action-reconciliation-unavailable`, naming the refusal, with its uncertain record. Nothing is
  sent again. This holds for every sender the key authenticates.
- Before the grant is asked, the run's actor is held to the read-back's own source and tool (spec
  #292): every link must name `<platform>/live` and the declared read tool.
- A platform's `grant` attaches to all its sources, and no longer requires `write: true`.
- The #362 LOWs: no liveness read follows a redirect that leaves HTTPS, and the npm and GitHub
  reads follow none; `sch.uk` is treated as a wildcard public suffix; a repository's name compares
  without case. Four LOWs are documented in `docs/design/connection-grants.md`, not changed.

## The clean room of #373 (#375; closes #374)

- A key found uncertain without this request's own dispatch (a dispatch marker without its answer,
  or an attempt another request claimed first) is refused `action-key-unauthenticated` to a link
  outside the read-back's scope, as SPEC.md §11.8 says. That request still mints the uncertain
  receipt into its own session and records it as the key's, but is not given it.
- A delegated `/acquire`, or a delegated `/act` the key lookup did not refuse (one with no
  `actionKey`, or one whose key holds a reservation in its scope), that the chain's own scope check
  refuses is no longer told the grant's state. On a platform that names a grant, its admission
  answers `out-of-scope` unless the issuing host refuses it first.
- `docs/design/connection-grants.md` lists as a departure that the operator's own calls on a
  platform whose grant is quarantined still run.

## Offline journal compaction (#370; closes #359)

`gateway journal compact --store <dir> --archive <dir> --retention <duration>` carries out steps 3
and 4 of the documented procedure in
[action reconciliation](../design/action-reconciliation.md#compaction). It retires entries that were
never sent, and answered entries (or an indexed entry's `action.json`) whose receipt was served
longer ago than the retention period. Each retired entry moves to the archive with a
`retirement.json` record. Nothing is deleted, no receipt is touched, and `actions/index/` is left
as it is. Every uncertain or begun entry is kept, and an entry that does not read is kept. A journal
the command cannot read refuses before anything moves. The archive must be private, outside the
store and on its filesystem. Each retirement is made durable in four steps, and a rerun finishes
one a crash stopped.

A serving gateway holds a shared `flock(2)` on its store; the command takes it exclusive. No
receipt, seal, registry line or corpus vector changes, and the verifier reads neither the journal
nor the archive. A key retired past the retention period can be sent again, and its response is no
longer replayed, as the documented procedure already said.

## Corrections to the v0.24.0 notes

The v0.24.0 notes are not edited after publication; these lines correct them.

- "Grants cover the connection custody only": from this release a delegated `/act`, `/acquire` and
  read-back are each admitted under the grant their platform names, and refused `grant-unknown`
  where it names none (Upgrade, item 1). The operator's own calls still use no grant.
- "A delegated write uses no grant", and "A delegated write's grant checks (gateway #368)" among
  what v0.24.0 did not establish: #368 is built in this release (#371).

## What this release does not establish

- No issuing host ships with this release, and the engine image serves no delegated call (Upgrade,
  item 2).
- Quarantine and the owner live in the custody's `connection-grants.json` alone: a deleted file
  brings grants back active with no owner (`owner-missing`), as `docs/design/connection-grants.md`
  records.
- Reassignment out of quarantine, and acceptance, are not built.
- Retention and the journal's growth limits are defined, not enforced, beyond the offline command.
  The store lock is advisory, and as good as the filesystem's `flock(2)`; a v0.24.0 gateway takes
  none.
- A real power loss during compaction: its tests stop a retirement at each step in the process,
  and durability is the system-call order on Linux.
