The postgres binding no longer offers a write operation: its one write tool took a raw SQL statement, which no decision policy can hold argument by argument, and a platform marked `write: true` against a binding with no write operation is now refused at start rather than silently ignored. A write receipt to a remote MCP server now names its transport (`action.tool.transport: "http"`), and both verifiers hold such a receipt's endpoint to the one form of SPEC §1.2a, with six new corpus vectors; a stdio write's receipt is byte for byte what it was. The catalog records that it ships no binding of the local Azure DevOps MCP server. A verifier from `v0.14.0` reads every new receipt as before, and every released vector verifies as before.

## What an operator must do

- **Nothing**, unless a postgres platform was configured with `write: true`; none is known. Such a platform is refused at start, naming the platform and the rule: drop the flag. A pin of `catalog/postgres.json` by its old digest is re-made with `gateway connect`, since the file's bytes changed; `history` and `live` are unchanged, their image digests included.
- **Know what `action.tool.transport` says.** It is `"http"` exactly when the executor reached a remote MCP server; a verifier then requires the receipt's `endpoint` to be a string of §1.2a's form. It is absent for a stdio write, whose `endpoint` stays the platform's own text, or `null`. A transport of another value, `null` included, or the member on a tool whose shape is not `mcp`, is `malformed`. The member names the transport the executor used; it does not establish that the server at that URL is the one the operator intended, which the engine's configuration establishes before the write is sent.
- **Write-back to Azure DevOps** goes through the organization's remote server under a Microsoft Entra token, as the catalog binding states; the local server (`@azure-devops/mcp`, over stdio) stays an operator-level source for reads, and the catalog ships no binding of it (#259, recorded in `catalog/README.md`).
- **Open as issues**: #267 (whether a policy should hold a container's shape, deferred to the output-dialect work).

## The postgres binding's raw-SQL write removed (#271, closes #260)

- `catalog/postgres.json` loses its `write` operation, which named dbhub's `execute_sql`; the server offers no narrower tool, so no replacement ships, and a function or procedure write returns when a server offers one. The catalog-shape test refuses any `write` operation naming a tool with `sql`, `query` or `statement` in its name, and holds postgres to no `write`; a test that puts the operation back shows it caught.
- The engine refuses, at start, a platform with `write: true` whose binding has no `write` operation, naming the platform and the binding; before, it derived no write source and said nothing. Without the flag such a binding loads as before.
- `catalog/README.md` (the write row and credentials paragraph rewritten with a dated note; the write-back section names postgres as holding to the rule), SECURITY.md, README.md, `engine-config.md`, `executor.md` and `mcp-server.md` no longer claim a postgres write.
- After the review: the comment above the credentials check describes the refusal at start, not the behaviour removed. One finding was declined with its reason: the v0.13.0 and v0.14.0 notes list #260 as open because it was open at those releases, and the files are the records of those releases; this note records its closure.

## No catalog binding of the local Azure DevOps server (#270, closes #259)

- A dated paragraph in `catalog/README.md`'s Azure DevOps section, and a sentence in the adapters' README where the local server is documented. The catalog's bindings take two forms, an image pinned by digest or a remote server named by URL and transport; a local executable or package is neither, and shipping it would mean the project building, licensing and re-pinning an image of a third-party package. Revisit if an operator who can hold only a personal access token needs write-back.
- After the review: the reason first given, that the catalog pins images, was corrected to the two forms above, in the new paragraph and in the older sentence beside it.

## A write receipt names its transport (#272, closes #268)

- The engine sets `tool.transport: "http"` when it builds the write source from a binding that names a URL, next to the endpoint; `act.go` copies it into the receipt, inside `tool` in canonical order, covered by the digest and the signature. A golden test written from `v0.14.0`'s code holds a stdio write's receipt byte for byte, with the platform's endpoint named and with `null`.
- `gateway verify` and verify-ts hold the rule above. Six vectors under `corpus/v3/stores/`, signed with `TEST-SEED`: transport with an endpoint of the form (`ok`); transport with `https://:443/`, a transport of `"stdio"`, a transport of `null`, and the member on a tool of shape `http` (each `malformed`); and no transport with the endpoint `https://:443/` (`ok`), which holds that a stdio endpoint is free text and catches a verifier that applies the form without the member. The released action vectors carry no transport and verify as before.
- SPEC §1.2a's `tool` row and §6 state the rule; ADR-0015 carries a dated amendment paragraph (its second of the day, after #266's); `executor.md`, SECURITY.md and the README follow. `peerIdentity` on the action stays out of scope (ADR-0015, question 2).
