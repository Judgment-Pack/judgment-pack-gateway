# v0.38.0 (draft)

This draft is started from ADR-0053's "What the release notes must say", and is completed with the rest of the release.

This release builds ADR-0053: from engine configuration version 40 a key service's ECDSA P-256 key version, `EC_SIGN_P256_SHA256` at the `HSM` protection level, signs the gateway's records. It takes one engine configuration version, 40, and no PostgreSQL migration.

- **The P-256 signer** (engine version 40; #562; ADR-0053, accepted): `signingKeyAlgorithm: "ES256"` beside `signingKeyVersion`. The start refuses the key version at any protection level but `HSM`, naming the level answered. The service's DER answer is turned into r||s at low S and checked against the pinned key before it is used. The seed and the witness stay Ed25519.
- **The `alg` member**: every record a P-256 key signs carries `alg: "ES256"` inside what it signs; a §3 seal signs five members; a rotation names the next key's algorithm in `nextAlg` and the previous key's in `previousAlg`. A record an Ed25519 key signs is unchanged, byte for byte.
- **The Go verifier** verifies each record by the algorithm it names, under a key it was given with that algorithm.
- **verify-ts** verifies each record by the algorithm it names too: `crypto.verify` with `sha256` named and `dsaEncoding: "ieee-p1363"`, the key's type checked against `alg` first, and low-S checked before the call, since the library does not. Its pin of a P-256 key is `{alg: "ES256", key: <66 lowercase hex>}` beside the 32-byte Ed25519 key, and `main.ts verify --public-key-alg ES256` reads the 66 characters on standard input, as `gateway verify` does. Every finding is the Go verifier's.
- **The corpus** gains two families and the P-256 test key, made once by Python's `cryptography` 44.0.0, independent of this repository, and verify-only: `p256/stores/*.json`, 15 store vectors (a rotation from Ed25519, a receipt and its five-member seal, a scoped seal, and refusals of a high-S, DER, unknown-`alg`, wrong-key and `alg`-less receipt, a stripped seal, four rotations and a version 2 receipt holding `alg`), one of them pinned with `"publicKeyAlg": "ES256"`; `retention-ack/*.json`, 6 acknowledgment lines run in process; `TEST-P256-SCALAR`, `TEST-P256-PUBLIC-KEY` and `p256-vectors.json`, signatures each with its high-S twin.
- **The process contract** gains `CMD verify [--public-key-alg ES256] ...`, given first, passed exactly for a vector giving `"publicKeyAlg": "ES256"`, with the 66 characters of `TEST-P256-PUBLIC-KEY` on standard input. An implementation that gives no verdict under it is reported `store <name>: no verdict under --public-key-alg:`, and the run goes on.
- **`retention.acknowledgedBy` at version 40** lists a P-256 key as `{"alg": "ES256", "key": <66 lowercase hex>}` beside Ed25519 keys as strings; a bare 66-character string is refused, naming both forms. An acknowledgment line under a P-256 key carries `alg: "ES256"` inside what it signs, its signature `r||s` at low S.
- **Rotation across algorithms**: Ed25519 to P-256, P-256 to P-256 and P-256 back to Ed25519, by SIGHUP on the filesystem kind and by `gateway store rotate-key --from-key-algorithm ES256` on the PostgreSQL kind.

## What changes for a verifier and a consumer

- An earlier verifier, Go or TypeScript, refuses a P-256 store with `rotation-break`, `key-mismatch` or a record that loads nothing, never naming P-256; a newer verifier is needed.
- `/publickey` answers `"algorithm": "ES256"` for a P-256 key, beside `"ed25519"`; a consumer that matches the value breaks.
- A consumer of v0.37.0 refuses a whole `/publickey/history` that holds a P-256 entry.
- The pin of a P-256 key: `gateway verify --public-key-alg ES256` and `main.ts verify --public-key-alg ES256` read the 66 lowercase hexadecimal characters of the compressed point on standard input; verify-ts's library pin is `{alg, key}`.
- An implementation driven by `gateway conform --impl` that does not take `--public-key-alg` disagrees with the one vector that pins a P-256 key, and the run goes on.
- A version 2 receipt holding `alg` is now `malformed`.
- No record or option lets a relying party require ES256 after a rotation, and the protection level is not attested.
- A rotation from an HSM key back to a non-HSM key is allowed and named on stderr.

## Compatibility

| With | What holds |
|---|---|
| An engine configuration | A file of version 39 or earlier serves as before. Version 40 adds `signingKeyAlgorithm`, beside `signingKeyVersion` alone; an earlier gateway refuses a version-40 file by its version. |
| A store of v0.37.0, either kind | Is served as it is. No migration. |
| The format | Ed25519 records are unchanged. A P-256 record names `alg`; a version 2 receipt never does. |
| Older verifiers and the corpus | Read every Ed25519 store as before and refuse a P-256 one (above). Every earlier vector stands; the new families are added beside them. |
| `retention.acknowledgedBy` | Versions 38 and 39 read it as before and refuse an object; version 40 takes the object form for a P-256 key. Every Ed25519 acknowledgment line verifies as before. |
