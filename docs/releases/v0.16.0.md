Gateway v0.16.0: the release workflow publishes by id after comparing the draft's assets by the digests the releases API reports and re-reads them after publication; the connection catalog's version 4 declares each adapter's research capabilities, and each search connection's status row declares what it serves.

## What an operator must do

- **Nothing.** Acquisition, receipts, policies and write-back are unchanged; the version-2 and version-3 catalogs are byte-identical to v0.15.0's. An installation that reads the catalog keeps reading its version.
- **An installation that will bind a published research source** (RFC 0018 §4.4 as amended on 2026-10-15) reads the capabilities from the catalog's version 4 (`gateway-connections --catalog-v4`) and, for a connection, from its status row's `research` member, which carries the capabilities the connection serves and, for a grounded-answer provider, its model. A profile copies the connection's status member, never the catalog's union.

## The release workflow (#276, closes #274)

- The draft-creating job records the draft's release id, reading the releases listing again until the draft appears. The publish job reads the release by that id through the API with no download (draft state, tag, title, notes, each asset's `digest`), compares it with the run's own files, refuses on any difference with both digest sets printed, publishes by id, and re-reads the published assets' digests. Two failures are told apart by name: "does not hold what this run packaged", with both digest sets, and "could not be verified", with the API error and no diagnosis.
- `docs/releasing.md` states the residual window between the last read and the publish call, who can act in it, and what a maintainer does on each failure. This release is the first run under the new step.

## Research capabilities (#277, part of #275)

- Catalog version 4 carries, on each provider's `source` contract and each `sources` entry, `capabilities` from the closed set `answer`, `search`, `page` in that order: `web` declares `page`; `web-search` declares `answer` and `search`; every other adapter declares none, which means no research contract the gateway declares for it, not that it serves none upstream: selected reads (Notion, Drive, Gmail, Obsidian, S3) are the dialect's `selected-file` kind, and the Databricks and Azure DevOps MCP paths are unclassified, bound by no research source. An unknown, repeated or out-of-order name is refused by name and no catalog is made.
- Each web-search status row carries `research` in RFC 0018 §5.1's profile-member form for a connection acquisition would admit: Tavily `{"capabilities":["search"]}`; Google `{"capabilities":["answer","search"],"model":…}`. It is computed, never stored, refused from a caller by `configure`, and absent for a connection refused as setup-required. Status stays at version 1.
- ADR-0017 (proposed) records that the set is the specification's, the gateway declares and the Runner checks; `docs/web-search.md`, the connection catalog design and the adapters README say the same.
